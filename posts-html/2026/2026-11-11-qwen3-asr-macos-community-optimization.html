0结论速览

一句话：在 Mac 上跑 Qwen3-ASR，不要走官方 PyTorch/MPS，走 MLX 或 GGUF/Core ML；量化用「decoder 4-bit + encoder 8-bit」这条社区反复验证过的配方；流式与长音频的瓶颈在切分和 KV 复用，不在算子。

四个值得记住的判断

  1. 官方 MPS 不是「慢一点的可用路径」，是不可用。 MacWispr 实测 HF PyTorch 0.6B (MPS) 处理约 10 s 音频要 39 s、RTF 1.31；qwen3-asr-server 干脆把 DEVICE=mps 归一化成 cpu。
  2. 正确性比速度更早成为问题。 早期 MLX 移植用标准 nn.RoPE 代替 Qwen3 的 interleaved MRoPE（sections [24,20,20]），输出「看起来合理但质量下降」；这才是 mlx-qwen3-asr 选择逐层重写而非包装的根本原因。
  3. 量化敏感点在 audio encoder 与 embed_tokens，不在 decoder。 全 4-bit 的 0.6B WER 2.63%，encoder 保 8-bit 回落到 2.37%（fp16 2.33%），只多 90 MB。日语场景 4-bit embed_tokens 会出现 ~172% CER 的幻觉。
  4. 社区数据是「自报基准」，不是统一评测。 不同芯片、不同 checkpoint、不同精度、不同协议混在一起；跨项目比较 RTF/WER 前必须先看测试条件。详见第 9 节证据分级。

1起点：官方边界与 MPS 为何不可用

Qwen 团队于 2026 年 1 月开源 Qwen3-ASR 家族（Apache 2.0，技术报告 arXiv:2601.21337）：0.6B / 1.7B 两个识别模型 + Qwen3-ForcedAligner-0.6B 非自回归对齐器，支持 30 语言 + 22 中文方言（共 52 种），离线/流式统一，单条长音频最长 20 分钟。0.6B 在并发 128 下官方宣称 TTFT 低至 92 ms、1 秒可转写 2000 秒语音。

维度官方提供对 macOS 的含义
推理后端qwen-asr 的 transformers / vLLM 两套；流式仅 vLLMvLLM 官方安装指向 CUDA nightly wheel（cu129），Mac 无对应路径
设备与算子示例 device_map="cuda:0"、flash-attn（仅 fp16/bf16）、gpu_memory_utilizationFlashAttention 2 与 CUDA graph 均不可用
实际 fallback官方文档未列 Apple GPU 支持transformers 后端在 Mac 上落 CPU，社区实测比 MLX 慢 7–20×
服务端兼容路径—SGLang-Omni 的 Torch/MPS 只是「compatibility and correctness path」，且限制很多（见 6 节）

来源：Qwen 官方博客、QwenLM/Qwen3-ASR、mlx-qwen3-asr 项目背景（DeepWiki 整理） 一手 第三方整理

关键对照： MacWispr 的 M5 系列 ~10 s 音频阶梯测试里，HF PyTorch 0.6B (MPS) 为 39 s / RTF 1.31，项目直接标注「Not viable for dictation」；同条件下 MLX 0.6B 8-bit 约 0.4 s / RTF ~0.04，差距约两个数量级。另 guoqing1988/qwen3-asr-server README 明确写 DEVICE=mps 会直接归一化为 cpu，macOS 走 vendored QwenASR Rust（CPU）。

5量化：收益、代价与最优配方

社区在量化上做了两轮独立实验，结论高度一致：别整模型一刀切 4-bit，encoder 与 embedding 要区别对待。

最优配方：decoder 4-bit + audio encoder 8-bit（group size 64）。 0.6B 全 4-bit 是 2.63% WER，把 encoder 提到 8-bit 后回落到 2.37%（fp16 2.33%），代价只多 90 MB。mlx-qwen3-asr 官方预量化产物就按这个配方发布：0.6b-4bit 517 MB / WER 2.37%，0.6b-8bit 801 MB / 2.33%（与 fp16 完全一致），1.7b-4bit 1.2 GB / 1.73%，1.7b-8bit 2.0 GB / 1.94%。混合精度权重需要 mlx-qwen3-asr >= 0.4.3 的 per-module loader，旧版本会 shape error。

两个量化陷阱：
① 日语幻觉：embed_tokens 量化到 4-bit 时，日语等语言出现 ~172% CER 的幻觉（mlx-community 4-bit 为 174%），是 4-bit embedding 的固有局限，不是某个转换脚本的问题。做中日韩多语种要保留 8-bit/bf16 embedding。
② mlx-audio 的 model_quant_predicate 硬编码：return not path.startswith("audio_tower") 无条件禁止 audio_tower 量化，导致自定义混合精度权重会被静默加载进未量化 Linear，shape 不匹配并产出空转写。该模型卡给出的绕过方案是：先加载 bf16 基座 → 手动 nn.quantize(...) 两次（audio 8-bit / text 4-bit）→ model.load_weights(saved, strict=True)。

6踩坑清单与已知限制

#坑现象规避 / 现状严重度
1标准 RoPE 代替 interleaved MRoPE输出「读着通顺但 WER 变差」，极难从单条样本发现用带 parity 门的实现；核对 sections [24,20,20] 与 stride-3 频率分配高
230 s 特征截断（mlx-audio Issue #459，第三方整理提及）长录音只转出前 30 s选支持低能量点 30 s chunking 的实现，或用 SGLang 的 max_audio_clip_s高
3ffmpeg@7 + TorchCodec（SGLang Apple Silicon）无版本化 ffmpeg 会装到 FFmpeg 9，而 torchcodec==0.11.1 只支持 FFmpeg 4–8；ffmpeg@7 是 keg-only，必须显式加 DYLD_LIBRARY_PATHbrew install ffmpeg@7；不要替换成非版本化 formula；用 M4A/MP3 测解码，WAV 可能不触发 FFmpeg 加载而掩盖问题高
4macOS SIP 剥离 DYLD_*经 SIP 保护的可执行文件启动服务时环境变量丢失把 DYLD_LIBRARY_PATH 设在最终的 sgl-omni 进程上，例如在 /usr/bin/time 之类 wrapper 之后放 /usr/bin/env DYLD_LIBRARY_PATH=...高
5Torch/MPS 兼容路径能力受限tp_size=1、greedy、eager torch_native/sdpa；无 radix caching / chunked prefill / CUDA graphs；KV 预算 2048 tokens；native 与 streaming 都卡 60 s；无 token logprobs长音频用 stream=false 让服务端按 30 s 分块；要性能就 SGLANG_USE_MLX=1中高
6语言 hint 严格不支持的 hint 直接 HTTP 400（不静默回落英文）；22 种中文方言名不能强制，只能用 Chinese/zh预先规范化；旧写法 cn / zh-* 会被接受为 Chinese中
7流式质量与稳定性final text 比 offline 差约 2pp（多语 11.3% vs 9.5%，长音频 11.9% vs 10.6%）；stable_text 设计上单调，缩短已稳定前缀的修正不会应用对最终稿再跑一次 offline 或 tail re-decode；SRT/VTT 仅离线模式支持中
8投机解码负收益短/10 s 片段 0.53–0.55×保持关闭，等 draft encoder 开销被优化低
9长音频重复（SGLang Issue #2150）长录音出现循环重复；repetition_penalty > 1 可压制但会伤干净音频准确率仍 open，缺少可复现的原始片段；MLX 路径的 repetition_penalty 转发在 #2157中
10realtime WebSocket 未完成 Apple 双后端资格验证VAD、partial/final、clear/cancel、断连恢复、长会话缺完整矩阵；#2214 只有 M4/16 GB 的 MLX smoke不要把 uploaded-file SSE 的证据当作 live PCM 的证据中
11Core ML encoder 15 s 上限 / ANE 不独占长音频必须切块；官方模型卡明说部分算子可能跑在 CPUGlimpse 自动切分；不要把「Core ML」直接等同于「省电 ANE」低
12版本与口径漂移早期媒体稿写 441 tests / 4-bit 提速 4.7× / 2.5 s 音频 0.46 s；当前 README 是 735 tests / 1.71× / 0.17 s（不同版本与 workload）引用时必须带版本、芯片、片段长度与测试协议；以仓库 docs/benchmarks/ 的 JSON artifacts 为准中

8选型建议与你的场景

目标推荐理由 / 注意
命令行批处理、CI 可复跑、写技术结论mlx-qwen3-asr + 0.6b-4bit（encoder 8-bit）唯一把每个优化都绑 quality gate 并留下 JSON artifacts 的实现；docs/BENCHMARKS.md 有 exact commands
要服务化、多并发、OpenAI Audio APISGLang-Omni + SGLANG_USE_MLX=1；或 mlx-qwen3-asr serve前者有分块调度与并发护栏（max_total_audio_s=3600 等）；后者更轻，长音频用 async job API 避免 HTTP 超时
做 macOS/iOS 原生 App、追求首延迟ontypehq/mlx-swift-asr（最小）或 soniqo/speech-swift（双后端）Metal shader warmup、MLState KV 常驻；注意 Swift 库要 macOS 15+ / Swift 6.2+；别忘 warmup 的 3–5 s 要放在启动阶段
不想引入 Python / 需要 Intel Mac 也能跑transcribe.cpp GGUF（Q8_0 或 Q5_K_M）1.7B Q5_K_M 1.41 GB、WER 1.65%；GGUF 无原生流式，需自己做 VAD 分块
中文方言 / 长会议 / 要词级时间戳1.7B 8-bit 或 bf16 + 30 s 能量切分 + --diarize-device mps1.7B 多语相对改善 30%，延迟 1.9×；8-bit 在 test-clean 与 fp16 输出一致；diarize 不支持 streaming/mic
DSH 插件 / 常驻语音输入参考 dsh-plugin-local-voice 的进程模型常驻 worker + 懒加载 + 空闲回收 + 平台探测降级，是「模型 2.47 GB 不能每次重载」的正确解；若你做新插件，可考虑把后端换成 mlx-qwen3-asr 以拿到 WAV fast path 与原生 aligner
Reachy Mini 之类本地语音链路（Mac MPS）0.6B 4-bit MLX + 流式窗口（默认 2 s chunk / 30 s context）RTF 0.08 有充足余量给 VAD 与 TTS；注意 streaming 与 offline 约 2pp 质量差，最终文本可再跑一次 offline 修正
三个「不要」：① 不要直接用官方 qwen-asr + device_map="mps" 期待 GPU 加速；② 不要对日语/韩语用 4-bit embed_tokens；③ 不要为 1.7B 打开投机解码（当前净变慢）。另外，跨项目比 RTF 之前先确认是否含模型加载/Metal warmup——Swift 线普遍标注「inference only」，而 Python 线常含冷启动。
