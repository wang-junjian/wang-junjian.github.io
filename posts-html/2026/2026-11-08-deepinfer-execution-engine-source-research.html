一句话结论（本报告观点）

DeepInfer 是一份高质量、可复跑、结构极清晰的执行引擎参考实现，也是目前唯一能读到「置信度调度推测解码 + YOCO 有界重放 + 零开销调度」如何协同工作的公开代码；但它不是可复制的生产服务方案，把仓库跑起来离复现官方成本结构，还差一整套缓存与路由系统。

三条判别式

① 模型绑定深度

通用引擎把模型当配置；DeepInfer 把 CED 编码器/解码器分层、YOCO consumer、Engram 词表分片、DFlash draft cache 写进了调度器与 cache_engine。

判据：能否只换 config.json 跑另一个模型？答案是否。

② 有无在线服务面

公开入口是 LLM(...).generate() 离线批式 API，没有 HTTP server、没有 OpenAI 兼容路由、没有持续批处理的服务端入口。

判据：Issue #147 正在请求「最小 OpenAI 兼容 chat server」。

③ 有无缓存与路由层

仓库里有 KV 的算子（state cache、block 读写），但没有分布式 KV 缓存系统，也没有 4 类负载均衡器。

判据：README「Required for a complete inference service」一节。

03理论根基：为什么必须是这个形状

好的理论章要能推出具体工程动作。DeepInfer 的每一个主要设计，都能从两条一阶关系推出来：算术强度决定 decode 的并行规模，边际期望收益决定验证长度。

推导一：decode 的吞吐–延迟前沿

MoE 模型 decode 每步必须把被激活专家的权重从显存读入，这部分流量近似与 batch 无关；增大 batch 提高算术强度、摊薄单 token 的权重读取成本。于是：

单步时间 T(B) ≈ T₀ + α·B　（T₀ 含固定的权重读取与通信）
每用户速度 ≈ 1 / T(B)；每卡吞吐 ≈ B·τ / T(B)

两式相乘的方向相反：B 增大时吞吐上升、单用户速度下降——这正是官方 decode Pareto 曲线从 (105 tok/s/user, 26.3k tok/s/GPU) 一路滑到 (325 tok/s/user, 2.5k tok/s/GPU) 的形状，而不是任何一方的工程妥协。

由此推出的工程动作是「让每步的 T₀ 变小，而不是把 B 调小」：Wide-EP 把专家分散到更多卡，降低单卡每步的 MoE 权重流量；EPLB 让最慢 rank 靠近均值，避免同步空转。官方给出的边界同样自洽：EP 超过 32 后收益停滞，因为显存带宽不再是瓶颈，通信与同步开销开始主导。

推导二：推测解码的验证长度是可优化的，不是超参数

固定验证 5 个 draft token 时，第 i 个 token 被用上的概率是前 i 个都接受的前缀存活概率，取累计乘积 P_i = ∏_{j≤i} p_j。期望产出 τ(B) = Σ_{i≤B} P_i 随 B 增速递减，而 T(B) 仍在线性增长。最优验证量应最大化：

B* = argmax_B　 τ(B) / [ baseline(B) + slope·B + sampler_ms ]

这不是报告的比喻。csrc/engine/mtp_varlen.hpp:228-258 的 update_best() 逐项累加 cur_expected += acc.first、cur_bsz += 1，用 cur_throughput = cur_expected / time_ms 取最大值，其中 time_ms = baseline_ms + slope_ms * graph_size + sampler_ms。变量名一一对应。

这条推导能直接解释官方表格里最反直觉的一格：并发 16 时动态验证反而 −1.5%。低并发下固定开销占比大、验证长度调整的可用预算小，调度决策的估计误差与 kernel 开销可能吃掉收益；并发升到 60–96 时，节省下来的验证 token 才转化为 +5.4% ~ +11.0% 吞吐。换句话说，DSpark 是一个高并发优化，不是通用加速器。

权重构成：510 GB 里有两个 94.5 GiB 的「巨无霸」

V4.1-Flash-1017 共 48 个 safetensors shard、510,311,045,295 B（510.31 GB / 475.26 GiB）、96,085 个张量。索引里最反常的是最后两个 shard 各约 94.5 GiB，却各自只装 6 个张量——都是 layers.1.engram.* 与 layers.14.engram.*。这两张 Engram 表合计 203.07 GB，占整个 checkpoint 的 39.8%，也解释了 V4.1 权重为何远大于 V4 时代的 160 GB。

对「要不要单独上传 target model」的直接回答

不需要。 DeepSeek-V4-Flash-DSpark 仓库本身是「完整主 checkpoint + 附加 DSpark drafter 模块」，不是只有 drafter 的独立模型；第三方 GGUF 转换说明也明确其来源是「the DeepSeek-V4-Flash checkpoint plus the DSpark drafter module」，只是转换时只取了 drafter 张量。到了 V4.1-1017，DeepSeek 更进一步把 3 个 MTP stage 直接合并进同一个 48-shard checkpoint，连独立仓库都不再需要。

所以那 7GB 既不是量化差异，也不是一个「小一号的完整语言模型」，而是挂在主模型末层特征上的半自回归提议头：读第 37/38/39 层 hidden、投影后跑 3 层小 MoE（128 experts / top-3）、用 Markov rank=256 建模块内依赖、再用 confidence head 给出每个 draft 的接受概率。

精度口径提醒：「7GB」是十进制 GB；若按 GiB 是 6.77 GiB。V4.1 侧的 7.933 GB 与 V4 侧 7.269 GB 不完全相等，因为两代模型结构不同（V4.1 有 Engram、层数与专家数不同），drafter 的 MoE 规模也不同——两者只在数量级与构成上互相印证，不应相加或视为同一个数。

调度器逐行还原：一个在线的吞吐最大化搜索

MTPVarlen::schedule()（mtp_varlen.hpp:150-267）做的事，可以逐步复述：

  1. 时间估计：用两个滑动中位数估计器消化实测值——SamplerRuntimeEstimator 取最近 9 个采样耗时的中位数（至少 5 个样本才生效）；ForwardRuntimeEstimator 维护 5,000 步窗口，先按 graph size 分组取中位数、再对组中位数取中位数，用两个 multiset 做 O(log n) 动态维护。步耗时 = baseline(graph_size) + slope·graph_size + sampler_ms。
  2. 置信度入队：把每个请求每个 draft 位置的接受率估计 p 压进两个优先队列。为避免「后面的 confidence 影响前面 token 是否被验证」，算总预算用 N−2 轮的值、分配每请求长度用 N−1 轮的值，靠 schedule_cnt / process_cnt 配对判断数据滞后几轮——源码注释把这件事讲得非常清楚。
  3. 搜索最优批大小：按接受率降序排序，从「只验证 golden token」开始逐个加入 draft，每加一个就重算 cur_expected / time_ms，取最大值得到 best_bsz。
  4. 分配：每请求基础长度 1，把 best_bsz − num_seqs 个额外验证位按第二个队列的顺序分给期望收益最高的请求，得到 seqlens_q。
  5. ZOS 下再修正：CPU 排 schedule(N+1) 时第 N 步的 confidence 还没回，因此 CPU 只定总预算；GPU 上由 TileLang kernel 做 cumprod → 稳定降序 argsort → rank < extra_budget 的 top-k → 按 remap scatter，把每请求长度写回 pinned buffer（zos.cpp:279）。
参考实现 compute_seqlens_q_by_confidence_rates_ref() 只有 30 行，却完整给出了语义：新请求 confidence 视为 0，cum_rates = cumprod(gathered_rates)，稳定排序后 wins = (ranks < extra_budget).sum(dim=1)，seqlens_q = 1 + wins。仓库还自带 9 组形状参数化测试逐元素比对 GPU kernel 与参考实现，以及 5 档 benchmark 参数化。可复跑

07SWA Bounded Replay 与 KV 缓存经济

如果说 DSpark 优化 decode，这一节优化的就是 prefill 与缓存成本。它同时是 V4 → V4.1 架构演进中最有信息量的一处取舍：放弃精确，换取常数代价。

SWA 状态槽位的物理布局是精算过的：StateBlock 分成「需保存区（SWA）」与「丢弃区（YOCO consumer SWA + C2 压缩边界累加器）」，V4.1 保存前 20 层，每层 134 token（128 窗口 + 6 投机回退）、MXFP8 格式 528 B/token，合计 20 × 134 × 528 = 1,415,040 B / 序列。只在 128 token 整数倍位置存储；decode 阶段在显存另开副本区，每跨一个 128 边界就拷一次窗口，最多越过边界 5 个 token，由 ring 多出的 6 个位置吸收。

命中长度的规则同样精确到 token：输入长度 L 的最大命中 ≤ L − 134；先查 Block KV 得 L1（128 的倍数），若 L1−128 .. L1 区间存在 SWA KV 则命中 L1，否则退一块命中 L1−128 并重算 128 token。

关键路径上只剩「匹配」藏不掉

官方把命中开销拆成三段，并说明哪段能被重叠掉：匹配（Entrypoint 本机 CHECK 角色做哈希链前缀匹配，只查元数据，但命中长度必须在路由前算出，无法隐藏）→ 取 KV（独立进程异步把 KV 从 3FS 搬进宿主机 shm）→ 换入（engine 内线程做 shm→HBM，目标是把逐层 H2D 与前向计算重叠；因 CUDA copy engine 对细粒度块拷贝表现差，换入用 GDR，让 RDMA 网卡打满 PCIe 且不占 SM）。

版本兼容靠元组，不靠迁移

缓存可用性由 (部署配置, 模型权重, 用户组) 标识；模型权重、block 字节布局、tokenizer、或改变 KV 值的框架变更都会让旧缓存失效。官方明确：生产从未做过缓存格式迁移。写失败不上报引擎，但读取时严格校验。

为什么不上 CXL L2

V4.1 的 KV 已被大幅压缩，读取又与请求排队、引擎计算重叠，官方判断集中式 CXL 缓存对 TTFT 改善有限，SSD 成本远低于 DRAM。唯一可能的好处是减少 SSD 写入、延长寿命，但当前未采用。

本报告最关心的精度空白：Bounded Replay 明说得到的是「近似 SWA KV cache」，但官方 Q&A 与评测文档都没有给出近似带来的质量损失量化（没有 logprob 偏移、没有任务分数对照）。仓库的 test_kl.py 与 PPL 逐样本基线是回归测试，不构成对「近似 vs 精确」的独立评估。这是评估该技术用于高精度场景时最应补的实验。

12结论与判断

以下为本报告观点，不是业界共识，也不是官方立场。

判断一：这是一次「把服务栈的确定性部分交出去」的开源

DeepSeek 交出的是 kernel 怎么切、并行怎么排、验证怎么调度、回放怎么截断——这些是最难被复制、也最能建立技术标准话语权的部分。留下的是缓存与路由，也就是与内部基础设施、与真实流量分布、与数据强耦合的部分。这个边界划得相当理性：它足以让第三方把 V4.1-Flash 跑快，却不足以让第三方直接复制官方的成本结构。

判断二：对绝大多数团队，正确的用法是「读」而不是「部署」

SM100 / Ascend 950 的硬件门槛、128 GPU 的最小高效单元、三件套缺口，三者叠加后，能照着跑的团队本就很少。但 mtp_varlen.hpp 的预算搜索、schedule_mtp_varlen.py 的 GPU 侧重分配、ZOS 的流水线性守护、xgrammar 的安全注释，这些是与硬件无关的、可读可移植的工程知识。把它们读进自己的调度器，收益比编译一次这个仓库大得多。

判断三：最值得警惕的不是功能缺口，而是数据口径

官方对 benchmark 方法学的披露其实相当诚实（连 profiler 退出后 7–11% 残余减速都写了）。风险在于二次传播：把 full-acceptance 的 decode 吞吐、按 0.75 接受率换算的 Pareto 曲线、以及生产自报的 155 万亿/天混在一起引用，会得出完全错误的容量结论。本报告在图 8 与第 9 章专门把这三套口径拆开，正是为此。

判断四：DSpark 的 7GB 问题，答案比预想的更「省」

它不是一个独立 draft 模型，而是挂在主模型末 3 层 hidden 上的 3 个半自回归 stage，共享 embedding 与 lm_head，靠 projection + Markov head + confidence head 工作。V4 时代需要单独一份 DSpark checkpoint（本质是主模型 + 这 7GB 附加层），V4.1 已合并进同一份 48-shard 权重。对做权重分发、缓存与加载的工程团队，这意味着不需要为 draft 单独管理一份 target 权重。

最后一个观察：仓库只有 6 次提交，却包含中文注释的 C++ 调度器、双硬件后端的 TileLang kernel、逐样本 PPL 基线、YoCo 等价性 L1/L2 验证、以及一份仍在修订（v0.2）的部署 Q&A。这不像一个为发布而拼凑的开源项目，更像把一份成熟内部代码树做了一次脱敏后的快照。因此它的价值密度远高于 commit 数所暗示的水平，而它的可维护性风险也恰好来自同一件事。
