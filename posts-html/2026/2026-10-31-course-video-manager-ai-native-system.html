三个反直觉的事实

反直觉 1

「AI 没写一行代码」也可能是成功

ADR 0008 明确把「零提交的智能体运行」从失败改判为成功：PRD 的子 issue 之间不独立，第 4 个子 issue 描述的活儿往往已经被第 2 个子 issue 那次提交做掉了。旧启发式 result.commits.length === 0 → fail 曾真的炸过（PRD #853 / run 26230340854）。

docs/adr/0008-agent-implement-zero-commit-runs.md
反直觉 2

「manual」不等于「人来敲」

ADR 0022 把 Deliverables 日历从「人工」重新定义为「非派生（underived）」：智能体通过 cvm deliverable create/update/archive 写日历，与人在 UI 里编辑是同一种刻意创作行为。它甚至明知 archive 不可逆（全产品无任何入口能撤销），仍然开放给智能体——因为不给的话，智能体会用 cancelled 当软删除，从而污染状态语义。

docs/adr/0022-deliverables-are-agent-writable.md

侵入式禁掉的恰恰是「聪明做法」

写给智能体的测试文档里明令：不许用 turbo --affected 或 vitest --changed 去猜「这个 diff 可能破坏了哪些测试」。理由：这种 git-diff 启发式会退化成跑整个包，比手动指定路径更慢。

03实践一：把「智能体契约」做成三层金字塔，顶层只留 81 行

这个仓库没有 AGENTS.md，也没有任何 cursorrules / .windsurfrules / Copilot 配置文件——全仓搜索无结果。 它对「多份约定文件互相漂移」这一现象的答案不是「同步它们」，而是只承认一份：CLAUDE.md。

L1：CLAUDE.md 是一份「指针清单」而不是「百科全书」

81 行里没有一行在教怎么写代码，全是在说「去读哪」和「绝对不能做什么」。几个典型的两句式：

章节原文要点（依据 CLAUDE.md）
Agent skills / BacklogIssue 与 PRD 就是 GitHub issue，通过 gh CLI 管理，详见 docs/agents/backlog.md
Landing a change「每次改动都必须从干净的 worktree 出发，PR 只有在分支与 main 同步且 check 绿时才合并。开工前和合并前各读一遍 docs/agents/merging.md」
Verifying a change「任何在 UI 上看得见的改动，在开 PR 之前必须在浏览器里用 verify-cvm 跑一遍。测试通过和 check 变绿都不能替代它。没有 UI 变化的改动就写一行 No UI change」
Coding standards「写代码时读，不是只在评审时读——『每个 any 都是一处泄漏』这句话约束的是写那个 cast 的手。它放在仓库根目录而不是 .sandcastle/，正是为此」
cvm CLI「只有一种传输，作者调用和智能体调用共用；不许加进程内 fallback。所有 import []的检查一个都逃不掉」
证据：CLAUDE.md（81 行，仓库根目录）
可迁移要点 CLAUDE.md 的价值不在「写得多全」，而在「把长文档变成按需查阅的指针」。81 行意味着它每次都会完整地挂在上下文里，而 CODING_STANDARDS.md 的 410 行只在真的写字时才被拉进来。把体积最大的内容放在最不需要常驻的层级，是这个三层结构的全部秘密。

L3：先有统一词汇，才有能交流的智能体

GLOSSARY.md 不是文档，是给人和机器共享的概念表：578 行、134 个术语条目，每个条目除了定义还明确列出要避开的同义词。摘一条：

Lesson: A single learning unit within a Section. A Lesson is known by its title, which is unique among its siblings.

Avoid: Exercise, Tutorial, Step

GLOSSARY.md · Course structure 一节

这条约束被直接写进了智能体干活时的执行层：improve-codebase-architecture-project 技能要求「领域语言必须用 GLOSSARY.md 的词汇」，而 domain.md 更进一步规定——当你的输出（issue 标题、重构提案、测试名称）里出现某概念时，必须用术语表的叫法。

这里有一个被很多团队忽略的细节 docs/agents/domain.md 第 11 行写着：如果 GLOSSARY.md / docs/adr/ 不存在，就静默继续，不要报错、不要建议创建。
理由：术语和决策是被实际解决的问题催生出来的，不是预先设计出来的。让智能体在缺文件时不啰嗦，是这套体系能长期不被文档债拖垮的前提。

05实践三：人机分工边界是用「权限」而不是「礼貌」划定的

大部分团队写「人机协作」时说的是态度；这个仓库说的是谁拿什么 token、能调用哪个动词。

3.1 中央设计法则：编排器持有所有写权限，运行器只产出文件

The central design rule: the orchestrator owns every tracker/VCS mutation (labels, comments, pushes, PR creation, issue closing). The agent runner only emits files. This seam is what makes the runner swappable and the system testable — the agent never holds a GitHub token and never calls the GitHub API to mutate state.

docs/agents/afk-agent-platform-spec.md:27-30

这条被划得有多干净？看实施提示词：.sandcastle/implement/prompt.md 最后一行是 「Do not close the issue yourself.」——连关闭自己刚做完的 issue 都不行，因为那是一次 tracker 变更。

3.3 三个 token 的分工与「降级契约」

# Use AGENT_PAT so pushes can include changes to files under
# .github/workflows/ (GITHUB_TOKEN lacks the `workflows` scope).
# Falls back to GITHUB_TOKEN if AGENT_PAT is unset; in that case

降级路径也很明确：先试 PAT，失败打印 AGENT_PAT label add failed …; falling back to GITHUB_TOKEN.——此时标签会落地，但下游 workflow 不会自动触发，得人手动再贴一次。这是被规范（§3.4 Degradation contract）承认并写死的行为，不是意外。

10实践八：把「拒绝」设计成默认动作，而不是失败后的补丁

八个 workflow 的共同结构是：Preconditions & refusals 排在 Step sequence 前面。也就是说「我凭什么不该跑」是第一步，不是异常分支。

拒绝情形行为
已有 open PR 引用了 Closes #N拒绝，不进入 agent:in-progress，comment 说明原因
嵌套 PRD（PRD 自己是子 issue，或子 issue 又有子 issue）拒绝 + agent:blocked
agent:queued 被贴到子 issue 上移除 queued、加 blocked、comment 说明「queued 对子 issue 无意义」
还有别的阻塞没关静默跳过（GitHub UI 已经显示了剩余阻塞），不留 comment
push 被拒绝且判定为租约冲突写入 failure_reason.txt「Branch advanced during review run.」，race=true
任何失败failure() 步加 agent:blocked + comment；always() 步移除 agent:in-progress

最后一条很关键：agent:in-progress 既是状态标签也是分布式锁——「加锁是『接受』的一部分，解锁必须是 always()」，否则一次崩溃就把这个 issue 永久焊死了。

失败信息必须能被拿到

失败处理的第一步是读 ${RUNNER_TEMP}/failure_reason.txt，缺失时不是假装没事，而是回落到字面说明：

"(no reason file written — check workflow logs)"
afk-agent-platform-spec.md §3.7

恢复路径也写得毫不含糊——comment 永远以这句结尾：Re-add \`agent:implement\` to retry.。失败要给出一条明确的人工恢复动作，而不是一句「something went wrong」。

13代价、文档漂移与风险｜这个体系里已经出现裂缝的地方

复盘如果不写代价就是广告。以下是实际在仓库里能核对出的问题。

风险 1

文档与代码已经漂移（至少 3 处）

  • ADR 0008 落后于代码：它的第 5 行说单 issue 流程「follows the same rule by omission: it has no commit check」，但 .sandcastle/implement/implement.ts:29-34 里有 git rev-list --count main..HEAD == 0 → fail。规范 §4.2 已经跟上了，ADR 没有。
  • 模型名漂移：附录 A 写 claudeCode("claude-opus-4-6")，8 个脚本里实际全是 claude-opus-5。
  • CI 复用缺失：8 个 agent workflow 各自内联重复了 .github/actions/setup 的三步。

对策：把这三处做成 CI 里的断言脚本（就像 check-effect-tsc.ts 对 tsc 补丁做的那样）——「文档是否还能描述现实」本身也应该是机器可验证的。

风险 2

自证式测试：AI 写实现，也写「证明它对」的测试

规范写得再严，TESTING_STANDARDS.md 拦不住「一个只可能由于当前实现才会失败的测试」。这正是 verify-cvm 存在的理由——它是一条不经过被测代码作者的路：真浏览器、真数据库、账单式的 Write Ledger。

已经做到的：把「UI 有可见改动必须在浏览器验证」写进 CLAUDE.md 硬约束 + PR 模板要求。
还没做到的：这条约束目前依赖诚实 reporting——No UI change 是一行自我声明，没有机器校验。

风险 3

白名单可能变成「合法性外壳」

170 处放行命中 + 至少 42 处 shell 内嵌条目，合计超过 200 个例外。虽然「只减不增」堵住了增长，但它不能阻止人们在一个已有条目范围内继续堆代码（例如 complexity 白名单某个文件的计数上限是某个数字，在那个范围内还可以加）。

对策：给白名单条目加过期日期，或让 CI 定期生成「最老的 10 条债务」报告。

风险 4

人类审批是吞吐瓶颈，而且是单点

全流程唯一的 merge 出口是 Matt 本人；连快照生产数据（db:verify-snapshot）也只有他能跑。这对一个单人项目是合理的，但它意味着这套系统的吞吐上限被一个人的注意力钉死——2026-04、2026-06 的 AI 占比跌到 58%/35%，很可能就是这种「人不在」的直接结果。

对策（已在路上）：agent:queued + 原生依赖关系的自动晋升，正是为了减少「等人想起来」的损耗。

最需要诚实对待的一条 这套体系的可靠性来自「人类仍然审查每一个 merge」。它不是「AI 全自动写代码」，而是「AI 全自动准备一个人类只需要花 3 分钟就能有信心批准的东西」。
如果你打算把这套搬到自己的项目上、并顺手拿掉人的审批环节，那么前面所有的机制——1092 行规范、19 个静态守卫、Write Ledger、强制的浏览器验证——都会失去意义。它们存在的价值是降低审批成本，而不是消除审批。

#实践怎么做成本证据
1 单一智能体契约入口 只维护一份 CLAUDE.md（或 AGENTS.md），不要同时存在多份工具专属约定文件。它只放「去读哪」+「绝对不能做什么」，正文全部下推到 docs/ 极低 CLAUDE.md（81 行）

3 把 AI 常踩的坑写成一句话禁令 把 AI 最常撒野的点写成一句话禁令，配上真事故：「新的 any 要在 PR 里写理由」「不许在 ↑ useEffect 里做重定向」 低 CODING_STANDARDS.md:117-133, 316-335
4 先有领域词表，再写代码 一份术语表 + 「要避开的同义词」列。 pit进一步要求：智能体输出（issue 标题、重构提案、测试名）必须用术语表的叫法 低 GLOSSARY.md · docs/agents/domain.md:41-45
5 列出「不值得做的事」清单 不满足系统边界的「哪些东西不许 mock」、五类「不值得写测试」的东西、以及一条针对性的绝对禁令。AI 的毛病通常不是不会做，而是做得太多 低 docs/TESTING_STANDARDS.md:18-27
6 为每一次「类型失效」写一个守卫脚本 凡是有 Leak（as any、反射、字符串拼装）绕过类型系统的地方，配一个 scripts/check-*.sh，并在注释里写明「庄名哪一个 bug」 中 scripts/check-response-body.sh:14-15
7 技术债用「只减不增」白名单编码 引入新规则时把历史债记进 allowlist；守卫要双向校验：多一处失败，少一处也失败（条目过期需下调）。且禁止用 disable 注释绕过这条规则 中 scripts/{effect-guards,complexity,fs-writes}*
8 编排器与执行器之间只通过「文件」通信 env 变量 + 上下文进，产出文件出。编排器（CI）负责所有远端变更，执行器（智能体）不持 token。这让 runner 可替换、可单测 中 afk-agent-platform-spec.md:27-30, §3.8
9 结构化输出：两遍 + 宽进严出 + resume 重试 有副作用（commit/comment）→ 干活一遍不带 schema，提取一遍带 schema；schema 容忍别名与类型转换；语义层面的幻想（不存在的行号/评论 id）由编排层按真实 diff 丢弃；重试是 resume 会话而非重跑 中 .sandcastle/{run-with-extraction,run-with-retry,retry-feedback}.ts
10 把决策写成 ADR，并写出「本决策不覆盖什么」 每个 ADR 必须答两件事：被否决的替代方案为什么被否，以及本决策不覆盖什么。后者比前者更能防止后来的误读——一个未来的读者（包括 LLM）能据此判断边界在哪 中 docs/adr/0022 · 0008
11 拒绝优先于重试 把「我凭什么不该跑」写成第一步；拒绝时不进入进行中状态。锁标签的加锁是「接受」的一部分，解锁必须是 always()。失败 comment 永远以「重新贴某标签即可重试」结尾 较高 afk-agent-platform-spec.md §3.7, §3.9
12 给智能体一个「能撒野但追得到账」的沙箱 真应用 + 数据克隆 + 允许写 + Write Ledger 记账 + 外部服务全部指向注销端口 + 「不得低于 clean 判断」。把「UI 有可见改动必须在浏览器验证」写进 PR 硬要求 高 .claude/skills/verify-cvm/
如果只抄一条 抄 第 7 条——「只减不增的白名单」。它是唯一能用一个文件同时堵住「人的惰性」「AI 的绕过冲动」和「技术债只增不减」三件事的机制，而且不需要任何 LLM 基础设施：一个 JSON、一个 check 脚本、一条 CI 规则就够了。
