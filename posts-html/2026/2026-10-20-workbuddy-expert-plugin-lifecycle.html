Buddy 应用（专家包）技术内幕

这不是一份「点这里、填那个」的操作手册。它要回答的是：一个 Buddy 应用（专家 / 专家团）在磁盘上是什么、在进程里变成什么、以及中间那段代码在干什么。 读完你应当能独立于任何 UI，用文本编辑器从零造出一个能在 WorkBuddy 里真正跑起来的专家。

本文所有结论均来自对本机 WorkBuddy 安装包的实证取证 —— 包括逆向主进程 app.asar、命令行内核 codebuddy-lite-wb.mjs、创作脚本 expert-manager/scripts/*.py，以及对 16 个真实落盘专家包的统计。 凡与官方文档口径不一致处，均以代码证据为准，并在文中明确标出。

Section 01

1 它到底是什么

1.1 四个容易混淆的概念

WorkBuddy 里有四套可插拔机制，它们共享「Markdown 定义 + 目录扫描」这一思路，但运行时待遇完全不同。 分不清这四者，是绝大多数困惑的源头。

概念物理位置运行时载体装载时机能否被 spawn
Skill
技能		 ~/.workbuddy/skills/*/
或插件内 skills/		 指令文本注入上下文
（含 scripts/ 可执行脚本）		 按需 命中描述才加载 否 是工具箱不是角色
Custom Agent
用户级智能体		 ~/.workbuddy/agents/*.md
或项目 .workbuddy/agents/		 独立 agent 配置 启动时 全部注册 是
Expert
专家 / Buddy		 插件包 <expert>/agents/*.md 插件组件 → 装到默认主 agent 上 选中时 动态切换 是（作为主会话人格）
Team
专家团		 expertType: "team" 的专家包 主理人 agent + N 个团员 agent 选中时 另开 Agent Teams 开关 是（成员被逐个 spawn）
关键区分：专家 ≠ 用户级 Agent

两者都能产出「可 spawn 的智能体」，但机制是两套独立实现：

  • 用户级 Agent 走 CustomAgentsProductProvider，直接扫 <home>/agents 目录，不读 plugin.json、不带 PLUGIN_TAG。
  • 专家包走 PluginsProductProvider → AgentExtensionLoader，必须依附于一个插件包，带 PLUGIN_TAG，且受 marketplace 生命周期管理（可下载、可更新、可切换）。

所以「专家」的附加价值不在 MD 本身，而在它是一等公民插件：有版本、有市场、能分发、能打命名空间。

1.2 一句话总纲

核心命题

专家包 = 一个标准的 WorkBuddy 插件，只是额外带了一个 expertType 标记，并且把其中一个 Agent MD 提升为会话的默认人格。

理解这一句，后面所有机制都是它的推论：为什么要注册进 marketplace（因为是插件）、 为什么 bin/ 会进 PATH（因为是插件）、为什么技能有命名空间前缀（因为是插件）、 为什么 team 需要开关（因为是插件之上的额外标记）。

把这句话展开成三层管线，就是本文的骨架：

PHASE 1创作期生成目录骨架、填内容、做头像
→
PHASE 2注册期写 marketplace.json 条目
→
PHASE 3分发期打包 zip / 上传市场 / 下载落盘
→
PHASE 4激活期POST /plugins/switch
→
PHASE 5装载期MD → 智能体注册
一个反直觉的事实

对于本地自建的专家，PHASE 3（分发）是完全跳过的 —— 你的目录就在 my-experts/plugins/ 里躺着，没有下载、没有解压、没有 .downloaded_at。 直接从 PHASE 2 跳到 PHASE 4。这也是为什么本地专家改完立刻生效。

2.2 plugin.json 字段全解

这是整个包的中枢。下面按运行时实际如何使用来分类，而非按文档顺序 —— 标注为「展示态」的字段不参与运行时行为。

身份与类型（运行时强依赖）

字段必填作用与运行时待遇
name必需 包唯一标识，kebab-case 正则 ^[a-z0-9][a-z0-9-]*[a-z0-9]$，至少 2 字符。用于拼 "<name>@<marketplace>" 这个插件 ID。
version必需 语义化版本。官方包用它比对本地落盘版本与 marketplace 条目版本，不一致则重新 materialize。
description必需 英文一句话。它是 marketplace.json 条目的 description，也是卡片兜底文案。
expertType必需 agent 或 team。这是唯一的语义开关：决定卡片显示「专家」还是「专家团」，决定主进程是否注入 CODEBUDDY_CODE_EXPERIMENTAL_AGENT_TEAMS=1 与 X-Expert-Team-Task 头。
agentName必需 主 Agent 名，必须等于 agents/ 下某个 MD 的文件名（不含 .md）。激活时它随 /plugins/switch 请求送给 CLI。禁止用通用名 team-lead。
teamInfoteam 必需 {leadAgent, memberAgents[]}。运行时只认 leadAgent；memberAgents 在整个 app.asar 中出现 0 次，是纯文档/市场字段（详见 §11 第 4 条）。

资源声明（决定加载什么）

字段必填作用与运行时待遇
agents可选 路径数组，如 ["./agents/x.md"]。可以不写 —— 加载器读完此字段后还会兜底扫描 <plugin>/agents/ 整个目录。实证：官方 software-company 包就没有这个字段，照样加载 5 个成员。
skills可选 技能目录数组。同理，加载器也会兜底扫 <plugin>/skills/。
bin死字段 规范里有，扫描器会归一化，但 CLI 侧无任何消费者。bin/ 目录本身是约定自动探测的，不需要也不受此字段影响。

展示态字段（不参与运行时行为）

字段约束说明
displayName必需{en, zh}。卡片标题（花名）。Team 型必须与 profession 完全一致，校验器直接判 error。
profession必需{en, zh}。职业头衔。
displayDescription40-50 字{en, zh}。中文超出 40–50 字区间校验器只给 warning，不阻断。
categoryId必需12 个分类之一；但实际还存在第 13 个 13-TencentZone（见 §14）。
avatar可选相对路径。会被解析成 file:// URL，超过 5 MB 丢弃。注意：官方落盘包普遍不含 avatars 目录（16 个包中 5 个无头像），说明市场包走远程 URL 分发。
defaultInitPrompt必需{en, zh}。必须与 quickPrompts[0] 一致（不一致只 warning）。
tags恰好 3擅长领域标签。多于或少于 3 个 = error。
quickPrompts恰好 3推荐提示词。渲染层会用 quickPrompts[0] 覆盖 defaultInitPrompt，所以两者写不一样时，界面上显示的是前者。
plugin必需必须等于 name。不一致 = error。
members[]team 必需每个含 {id, name, profession, avatar, role}，role 取 lead/member，主理人也必须在内且 role: "lead"。仅用于渲染头像墙，运行时不消费。

2.3 Agent MD 的格式

每个 agents/*.md 文件就是一个智能体定义。结构极简：YAML frontmatter 管元数据，正文就是 system prompt。

description: Reviews code for bugs, security and performance issues.

  en: "Senior Code Reviewer"

1. **缺陷识别**：……
2. **安全审计**：……

1. 先通读 diff 全貌
2. 逐文件审查

- 每条给出行号与修改建议

## 注意事项
- 不做主观风格争论

frontmatter 字段的真实待遇

字段是否生效运行时处理
name生效成为 subagent_type 的名字。缺失时回退用文件名（去掉 .md）。
description生效缺失时回退用 name。加载器还会自动追加来源标签，例如 "... (my-experts:agents)"，用于在模型面前区分同名 agent。
instructions（正文）生效核心：整段正文就是 system prompt。且会做变量替换（见下）。
tools禁用规范明令禁止在 frontmatter 声明。运行时虽会解析，但工具权限由系统统一分配。
maxTurns生效必须正整数，否则丢弃。主理人建议 150–200（因为要编排多轮），普通成员 50。
skills生效预加载技能，解析时会尝试加插件名前缀（见 §8）。
effort生效推理强度，经 normalizeReasoningEffort 归一化。
background生效布尔值，是否后台运行。
isolation生效只有 "worktree" 值被接受，其它一律丢弃。
initialPrompt生效智能体启动后的首条输入。
memory生效记忆配置。
color生效缺失时用 generateColorFromName(name) 按名字生成。
permissionMode忽略这三个字段即使写了也被静默忽略并打 warning：
[AgentExtensionLoader] plugin agent 'x' sets permissionMode, which is ignored for plugin agents.
这是有意设计 —— 插件不应越权改宿主权限模型。
hooks忽略
mcpServers忽略
变量替换：${CODEBUDDY_PLUGIN_ROOT}

正文里的 ${CODEBUDDY_PLUGIN_ROOT}（以及兼容别名 ${CLAUDE_PLUGIN_ROOT}）会被替换成插件根目录的绝对路径。 这是让 MD 能引用包内资源的关键 —— 比如 请读取 ${CODEBUDDY_PLUGIN_ROOT}/references/rules.md。 没有它，智能体无法定位自己的包在哪。

2.4 Team 型的额外约定

文件命名
主理人文件必须带团队前缀：{team}-team-lead.md。 用通用的 team-lead.md 会被校验器判 error —— 因为同名会跨包冲突。
members 包含主理人
members[] 含主理人（role: "lead"），但 teamInfo.memberAgents 不含主理人。校验器会检查「members 里至少有一个 lead」以及「memberAgents 不含 lead」。
settings.json
创作期必需，内容仅 {"agent": "{team}-team-lead"}。 但官方落盘包里一个都不存在（见 §11 第 5 条），它本质是过渡产物。
SOP 写在 MD 里
阶段编排、协作铁律、红线全部写在主理人 MD 正文中，没有任何运行时强制。这就是「代码 = SOP(团队)」的含义。

3 创建流水线：七个脚本

创作期由 expert-manager 这个技能驱动，共 5 个 Python 脚本（外加 2 个测试脚本）串成流水线。 它们全部是纯 stdlib 实现，无第三方依赖。

技能目录结构expert-manager/
resources/plugins/workbuddy-builtin/skills/expert-manager/
├── SKILL.md                     179 行   # 流程与铁律
├── references/
│   ├── plugin-json-spec.md      184 行   # plugin.json 字段规范 + 两套模板
│   ├── agent-md-spec.md         179 行   # Agent MD 结构（普通 / 主理人）
│   ├── team-spec.md             120 行   # 协作铁律、命名、SOP 编排
│   └── avatar-spec.md           162 行   # 头像 prompt 构建策略
└── scripts/
    ├── init_expert.py           485 行   # ① 生成骨架
    ├── validate_expert.py       381 行   # ② 校验
    ├── register_expert.py       271 行   # ③ 注册
    ├── package_expert.py        121 行   # ④ 打包
    ├── batch_create.py          141 行   # 批量编排（模板）
    ├── test_register_expert.py   78 行
    └── test_package_expert.py    95 行
  1. init_expert.py — 生成骨架 按 --type agent|team 生成目录 + 带 [TODO] 占位符的 plugin.json 与 MD 模板。 Agent 型产出 1 个 MD；Team 型产出 {team}-team-lead.md + 一个 member-placeholder.md（需自行改名）+ settings.json。 同时校验 --path 必须是专家目录、name 必须是 kebab-case。
  2. 填充内容 把 [TODO] 换成真实内容。这一步由 AI 或人完成，是唯一有创造力含量的环节。 正文质量直接决定专家质量 —— 因为正文就是 system prompt，没有中间层。
  3. ImageGen — 生成头像 按 avatar-spec.md 从 MD 内容反推 prompt：读角色定义 → 提核心能力关键词 → 转视觉元素 → 拼装。 Agent 型 1 张；Team 型 N+1 张（团队整体 + 主理人 + 每个团员）。同团队共用风格锚定词与背景色调。
  4. validate_expert.py — 校验 会做五大类检查：位置（必须在 my-experts 目录下）、结构（禁止 hooks/、commands/、.lsp.json，禁止资源目录藏在 .codebuddy-plugin/ 内）、 字段（必填项、kebab-case、tags/quickPrompts 恰好 3 个、team 的 profession ≡ displayName）、 一致性（agentName 有对应 MD、frontmatter name ≡ 文件名）、 禁用项（frontmatter 不得有 tools）。
  5. register_expert.py — 注册 二次校验（重点查 [TODO] 残留）后，向 marketplace.json 写入条目 {"name": ..., "source": "./plugins/<dir>", "description": ...}， 并向专家目录写入 .created-by-session 标记文件（值取自环境变量 CODEBUDDY_SESSION_ID）。
  6. package_expert.py — 打包 先跑一遍完整校验，通过后打 zip。会自动跳过隐藏文件（.codebuddy-plugin 除外）、 __pycache__、node_modules、.gitkeep、.DS_Store。
  7. 批量（可选） batch_create.py 提供模板：对每个专家串行执行 init → 填充 → validate → register， 任一步失败即停止。规范明令禁止「只写文件跳过校验注册」和「直接改 marketplace.json」。
铁律：不注册 = 不存在

第 ⑤ 步不是可选项。扫描器以 marketplace.json 为唯一入口，文件缺失直接返回空列表； 即使目录和 plugin.json 都完好，只要 marketplace.json 里没条目，专家在界面上就不存在。 跳过这一步直接手搓文件，是最常见的「我明明写了为什么看不见」的原因。

# 资深代码审查师 - 审稿人

你是一名资深代码审查师。你的职责是从正确性、安全性、性能和可维护性四个维度审查代码，
输出可执行的修改建议，而不是主观风格评判。

## 核心能力

1. **正确性审查**：识别逻辑错误、边界条件缺失、空值处理不当、并发竞态、错误 swallowed。
2. **安全审计**：识别注入（SQL/命令/模板）、XSS、越权、敏感信息泄漏、依赖漏洞。
3. **性能分析**：识别 N+1 查询、循环内重复计算、不必要同步阻塞、内存泄漏风险。
4. **可维护性**：识别重复代码、过深嵌套、命名失义、缺少错误处理。

## 工作流程

1. **通读全貌**：先读完整段代码或 diff，理解意图，不急于下结论。
2. **逐项审查**：按上述四个维度各扫一遍，记录候选问题。
3. **去伪存真**：剔除误报与纯风格问题。只保留能说清危害的问题。
4. **定位与建议**：每条问题给出文件行号、危害说明、以及具体改法。
5. **汇总输出**：按下列模板输出。

严格按以下结构输出，不要省略任何一节：

### 总体结论

### 问题清单
| 严重程度 | 位置 | 类别 | 问题描述 | 建议改法 |
|---------|------|------|---------|---------|
| 阻塞 | `path/to/file.ts:42` | 安全 | 用户输入直接拼接进 SQL | 改用参数化查询 |

严重程度只取四档：`阻塞` / `严重` / `一般` / `建议`。
类别只取四档：`正确性` / `安全` / `性能` / `可维护性`。

### 亮点

- **不做主观风格争论**：缩进、引号、分号这类交给 linter，不出现在报告里。
- **不确定的标注不确定**：疑似问题必须标注「待确认」，不得伪装成确定结论。

## 协作规则

1. 每阶段结束后，将完整产出原文传递给下一阶段成员，不要只传摘要。

C 心智模型总结

如果只记住六句话：

① 专家就是一个插件
所有行为都可从「插件基础设施」推导：为什么要注册 marketplace、为什么 bin 进 PATH、 为什么技能有命名空间。抓住这条，就不需要记忆零散规则。
② MD 正文 = system prompt
没有中间层、没有包装、没有优化。写进 agents/*.md 的每个字都直接进入模型上下文。 正文质量 = 专家质量，这是唯一的杠杆。
③ 团队没有编排引擎
expertType: team 对运行时的全部贡献：开一个环境变量开关 + 打一个 HTTP 头。 SOP、铁律、红线全是 prompt。团队跑不跑得起来，取决于 MD 写得多硬。
④ 激活是会话级的
persist: false 意味着切会话即失效。这不是缺陷而是设计 —— 专家是临时人格，不是常驻配置。
⑤ 注册是必经步骤
扫描器以 marketplace.json 为唯一入口。目录、plugin.json、MD 都齐全， 只要清单里没条目，专家就等于不存在。
⑥ 三套可插拔机制别混用
Skill（工具箱，按需加载）、Custom Agent（用户级角色）、Expert（插件级人格）。 三者的物理位置、加载时机、运行时载体各不相同。

C.1 给工程师的迁移建议

如果你要在自己的产品里实现类似机制，这套设计里最值得借鉴的三点：

  1. 文件即配置：整个包无需一行代码、无需构建、无需 schema 注册，纯文本即可分发。 代价是没有编译期检查，所以才需要 validate_expert.py 这类外部校验来补位。
  2. 把插件系统当作底座：专家不自建加载器、不自建市场、不自建生命周期， 而是复用插件基础设施换取版本、分发、命名空间、PATH 注入等能力。典型的复用优于新建。
  3. 把编排留给模型：团队 SOP 不写进代码而写进 prompt，换来零开发成本的领域适配 —— 换个 MD 就从交易团变成开发团。代价是没有确定性保障，需要在 prompt 里用冗余约束来补偿。 这个取舍是这类系统的核心设计张力。
