01为什么放弃重型流程

先说结论：不是流程错了，是流程的粒度错了。

前两年很流行"给 AI 一套完整研发流程"：需求访谈、方案设计、计划拆解、逐条实现、测试、审查， 每个环节都有模板和门禁。第一次用会觉得踏实，用了一周就会开始烦。

原因很朴素。模型能力在涨，而这些流程是照着"模型很笨所以要管住它"设计的。 一个本来三步就能问清的需求，被塞进一张二十项的检查表，你要读它写出来的每一段， 确认它没有在第三步就跑偏。时间成本翻倍，Token 成本翻三倍。

我自己的体感是：一次中型需求的会话，重型流程能吃掉 三到五倍的额度， 而真正提升质量的只有其中两三个环节。剩下的是仪式感。

这套技能走的是反方向。它不拥有流程，只在四个地方各插一根钉子： 对齐、语言、反馈回路、设计。这四个点对应四种最常见的失败：

失败长什么样根因对应技能
做出来的不是我想要的它没问，你没说grill-me / grill-with-docs
一屏能说清的事写了三段没有共同词汇domain-modeling + GLOSSARY.md
代码跑不通，它开始瞎猜没有反馈回路tdd / diagnosing-bugs
三个月后没人敢改没人管设计codebase-design / improve-codebase-architecture
一个判断标准

好技能和坏技能的区别，不在于它覆盖多少步骤，而在于 你能不能在某一步停下来，自己接手。重型流程的毛病是每一环都依赖上一环的产物， 中间断了就得从头再来。这套技能每个都短到你可以读完、改掉、甚至扔掉。

0227 个技能的地形

先看全局，再决定读哪几个。大部分人的问题不是技能不够，是不知道有哪个。

仓库按用途分了五个桶，但真正在维护、会随插件一起发出去的是前两个： engineering 20 个，productivity 7 个。 剩下三个桶（misc、in-progress、deprecated）分别是边角料、内测和坟场，不用花时间。

比分类更有用的是另一个切分维度：谁能调它。

User-invoked

只有你打斜杠才会跑。它的职责是编排：把几个技能按顺序串起来，管住节奏。

你按下的按钮

Model-invoked

你可以打，模型也能在任务匹配时自己伸手去拿。它装的是可复用的纪律。

它知道的规矩

这条规则还有一条硬约束：User-invoked 可以调用 Model-invoked，但绝不能调用另一个 User-invoked。 所以你不会出现"斜杠套斜杠"的递归，也就不会出现那种点一下触发二十步的失控感。

还有一层容易被忽略的关系：好几个斜杠技能其实是同一块积木的组合。 grilling 是访谈原语，grill-me 只是它的一层壳； grill-with-docs 是 grilling 加 domain-modeling； implement 驱动 tdd 并收尾于 code-review； implement-spec 是同一个动作的并行版。

读法建议

不要一次装全、全部试用。先装，然后只记三个：一个负责问清（grill-me）， 一个负责写清（to-spec），一个负责做对（tdd）。 等你在这三步上稳定了，剩下的自然会缺什么补什么。

03一条主线串起来

这十个技能不是并列的清单，是一条可以顺次走完的路。

下面这条线是我实际用的顺序。它不是强制的，但如果你不确定从哪开始， 按这个走至少不会在第二步就迷路。

1
先被问清楚
grill-me 或 grill-with-docs。它会一轮一轮地问，直到设计的每个分支都有答案。
2
看不清就先做个能点的东西
prototype。状态模型不确定就做逻辑原型，界面不确定就做几套差异极大的界面。
3
把聊定的事落成文字
to-spec。它不访谈，只综合。产出发到你的 issue tracker。
4
切成能单独验收的卡
to-tickets。每张卡说清交什么、怎么验、被谁挡住。
5
按依赖关系做掉
implement 单线做，implement-spec 并行做。内部都跑 tdd。
6
两条轴分开审
code-review。规范一条线，需求一条线，互不污染。
7
换会话前留一份交接
handoff。把定下的事、做到哪、下一步写成一份临时文档。

中间还有两个随时可以插进来的：卡住不动时用 diagnosing-bugs， 每隔几天用 improve-codebase-architecture 扫一遍代码库看哪里在变浅。 这两个不在主线上，但缺了它们，前面六步的成果会在两个月内被磨平。

04十个值得深用的

每个都写：它解决哪个具体问题、实际怎么用、以及一句判断它有没有起效的标准。

01

grill-with-docs：顺手把词义和取舍记下来

一个词有两种读法的时候，先别写代码，先把它钉死。

我拿一个面试产品举例。"知识库面试"这五个字，可以指两件完全不同的事：

  • 照着用户上传的资料出题，考的是资料；
  • 照常做技术面试，只在需要补上下文的时候翻一下知识库。

叫法一样，做出来的东西差着一个量级。这种歧义如果不当场消掉， 它会一路带到数据库表结构里，等你发现的时候已经改不动了。

这个技能做的事，是在访谈的同时做领域建模。它内部其实调了两个模型侧技能： grilling 负责 relentless 地追问，domain-modeling 负责把定下来的词写进 GLOSSARY.md。碰到那种"改起来代价很大、但光看代码又想不明白为什么这么选"的取舍， 它会再写一份 ADR。

我最喜欢的其实是它对表达长度的影响。有了共同词汇之后，同一件事的表述会缩短一个数量级：

改之前：「课程里某一节被『实体化』（也就是在文件系统里给它一个位置）的时候会出问题。」

改之后：「实体化级联有问题。」

这个例子来自作者自己的项目文档，缩写掉的每个词在 GLOSSARY 里都有定义

这不只是省字。变量名、函数名、文件名会跟着用同一套词，代码库对模型来说变得更好导航， 思考时消耗的 Token 也变少。这是这套技能里最被低估的一环。

user-invoked= grilling + domain-modeling产出 GLOSSARY.md / ADR
02

prototype：先点几下，再决定

能用鼠标回答的问题，不要用文字讨论。

一个审批单被驳回了，用户能不能改金额？改完再提交，之前那条审批意见挂在哪？ 这种问题我在文档里写过三次，每次写出来的理解都不一样。后来我改成让它直接做一个页面， 驳回、改金额、重新提交三个按钮摆在那里，每点一次把当前状态打在屏幕上。三分钟就有了答案。

这个技能的关键设计是按问题类型分两条完全不同的路，走错就白做：

它的规则写得很硬，我照抄几条：一次性、从第一天就标注清楚、默认不持久化、跳过打磨。 最有用的是最后一条处理方式：结论验证完，把那条规则折回真实代码， 然后把原型本身提交到一个临时分支（不要进主分支），在需求票里留一个指针指向它。 主分支只保留被验证的结论。

03

to-spec：把昨天聊定的写成明天找得到的

它不访谈你。这是设计，不是缺陷。

举个再普通不过的例子：订单导出。今天聊定了 CSV 有哪几列、谁能导、日期最多查多久。 明天换个会话，这些要求就散了。你总得有个地方能翻到它们。

很多人第一次用会失望，因为它上来就开始写，不问你任何问题。原因在它的定义里： 综合（synthesize），不是访谈（interview）。访谈是 grill-* 的活。 这两个技能的边界切得很干净，我一开始也搞混过。

它真正有价值的动作在写之前，一共三步：

  1. 先翻仓库，理解现状，全文使用 GLOSSARY.md 里的词，尊重相关区域的 ADR。
  2. 先定验收的接缝（seam）。优先用已有的接缝，能用高的就不用低的，接缝越少越好，理想数量是一个。定完要跟你确认。
  3. 再按模板写，发到 tracker，打上 ready-for-agent 标签，跳过额外分诊。

第二步是精髓。大部分规格写不清楚，是因为没定从哪个公开接口验收。 "只导本租户的数据"这种话，只有绑定到一个具体的接口和一条具体的断言上，才是可执行的要求。

user-invoked无访谈seam 优先ready-for-agent
04

to-tickets：一张卡只验一件事

卡不是任务的切片，是验收的切片。

我给第一张卡写的验收条件通常只有一句：拿 A 租户的账号导一次，把 CSV 打开，里面只应该有 A 的订单。 这句话跑通之前，不考虑下一张卡上的日期筛选。一张卡必须能独立变成一个"红变绿"的动作， 这是它叫 tracer bullet 的原因：先打穿一条完整但极细的路。

它会把规格、计划或者刚才那段对话吃进去，然后列出三件事：每张卡交什么、怎么验、等哪张先做完。 你确认拆得对，它才真正发到任务系统。在本地文件模式下，依赖关系写成纯文本； 在真实 tracker 上，用原生的 blocking 链接。

还有一个细节我很喜欢：动手拆之前，它会先找 prefactor 的机会。 "先把改动变简单，再做简单的改动。" 这句话听着像鸡汤，但落在具体代码上往往很实在： 先抽一个函数、先补一条测试、先把那个 if 挪走，后面三张卡都能省一半力气。

user-invokedtracer bulletblocking edges
05

implement-spec：把任务图当成调度问题

并行不难，难的是并行之后还能收敛成一份可审的改动。

如果只有两张有依赖的卡，塞进一个会话按顺序做就完了，用不着这个技能。 它的价值在另一种情况：项目里另有两三张互不阻挡的卡。

这时它会做四件普通实现流程不会做的事：

  • 为整个规格开一条集成分支，所有工作最终汇到这一条线上；
  • 把票当成任务图而不是步骤列表，算出 readiness frontier，让实现子智能体在 frontier 上并发跑；
  • 每个子智能体都从全新的上下文窗口开始，并各自在自己的 Git worktree 里动手；
  • 子智能体之间少说话，多给指针。指向规格、票、笔记、之前的提交，不复制内容。

第三点是硬要求，不是优化。有些运行环境默认把父会话 fork 给子智能体， 那样等于把父会话的上下文原封不动搬过去，而子智能体存在的意义恰恰是逃离那份上下文。

第一点也值得说：它会在第一次合并之后再开 draft PR，因为一个还没有提交的分支没法开 PR。 整份规格做完，才一起审。

前置条件

用之前先确认你手里的工具能不能开子智能体和 worktree。不能的话，退回 implement 顺序做，别硬上。

06

tdd：先让一条测试红给你看

测试一上来就绿，我第一反应不是"真好"，而是"它到底有没有走到那个接口"。

给导出接口补一条 31 天的限制，我会让它先发一条查 32 天的请求，断言应该被拒绝，跑一遍给我看。 旧实现要是照样吐了个 CSV 出来，这条测试就应该是红的。红的看到了，再补校验，再跑一遍转绿。

这个技能真正的内容不是"先写测试"这句口号，而是什么算好测试、测试写在哪、 哪些写法是反模式。几条我常引用的：

  • 测试通过公开接口验行为，不碰实现细节。代码可以整个重写，测试不该动。
  • 好测试读起来像一份规格：用户可以带着有效购物车结账，一眼知道有什么能力存在。
  • 只在预先约定的接缝上写测试，没确认过的接缝一条都不写。你测不完所有东西，先约定接缝才能把力气花在关键路径上。

最新那版加了一条我很受用的规则：提议测试接缝时，顺手说明从这里测能抓到什么、哪类问题还得去别处查。 一句话逼它承认测试的边界，而不是给你一个"全覆盖"的错觉。

07

diagnosing-bugs：先让 Bug 自己跑出来

第一阶段花的时间应该比后面所有阶段加起来都多。

偶发超时。它看了几眼代码，说是 SQL 的问题。我会追问一句： 能不能先给我一条能跑出超时的请求？

这就是这个技能的全部重心。它把"建一条能红的反馈回路"当成第一优先，其它都是机械动作。 顺序是有讲究的：先试失败测试，其次 curl / HTTP 脚本打本地服务，再其次用固定输入跑 CLI 并 diff 输出， 最后才是"一次能把问题点出来的页面操作"。

它还有几条很"工程"的规矩，值得直接抄进自己的提示词里：

  • 能跳阶段，但要说明理由。不允许默默跳过。
  • 先脱敏。所有命令、输出、抓下来的报文，密钥一律写成 <REDACTED>；凭据用环境变量传，不进展示内容。
  • 修完拿原来的输入再跑一遍，合适的话把复现直接转成回归用例。

08

code-review：规范和需求必须分开看

少查了一次租户权限，命名和异常处理写得再规整也没用。

看 Diff 的时候我会把原始 Issue 一起给过去，并且给一个比较基点，比如 main。 然后它把 Diff 拆给两个子智能体：

为什么非要拆成两个子智能体？因为这两件事会互相干扰。一个负责规范的审查者， 看到代码风格整齐，容易默认"这活儿干得不错"，从而放过"少查了一次权限"这种致命缺陷。 反过来也一样。

它还做了两件很实用的工程化动作：开工前先校验比较基点能不能解析（git rev-parse）、 Diff 是不是空的。错的 ref 和空的 diff 应该在这里失败，而不是在两个并行子智能体里面失败。 另外三点 diff（...HEAD）而不是两点，所以比较的是 merge-base，不会被主干上的无关提交干扰。

如果项目里压根没有规格可查，它会退回只审代码约定。这时候你就知道， 前面的 to-spec 那一步是省不掉的。

09

improve-codebase-architecture：找哪里正在变浅

它是普查，不是抢救。老代码库上它找得出真问题，但它不会替你解开那团乱麻。

给 CSV 加一列，接口、文件生成、后台任务三处都得跟着改。碰到这种设计，我会想知道： 前几次改导出字段，是不是也动了这三个地方？

它会从最近常改的代码里找线索，产出一份 HTML 报告，里面列清楚：哪些文件老是一起动、 有没有办法把规则收进一个深模块、收进去之后从哪儿测。报告给几个候选， 你挑一处最想动的，它再跟你逐条讨论怎么拆。

它的方法论有两个我很认同的点。第一是先划范围再看，不搞全库扫描： 加深一个模块的收益来自"以后改它更容易"，所以权重应该压在最近改过的地方。 如果用户已经指名了方向，就直接用，不做推断。

第二是词汇统一。它只允许用 module、interface、depth、seam、adapter、leverage、locality 这几个词， 明确禁止滑向 "component"、"service"、"API"、"boundary"。听着像吹毛求疵， 但这几个词一混用，"把服务拆一拆"和"把接口做深"就会变成同一句话，讨论就没法收敛了。

用法上我建议把它当体检：每隔几天跑一次，一次只看一个候选，做完就停。 想靠它一次性还清历史债，一定会失望。

user-invokeddeepeningHTML 报告survey ≠ rescue
10

handoff：给下一个会话留一份能接手的

好的交接不是总结，是几个指针加一句"下一步"。

还是那个面试产品。聊完要换会话，我想留下的其实就一句话： 首期只绑一个知识库，两个入口保留，底下还是同一个 InterviewSession。

它会把这句连同"已经定的事""现在做到哪""下一步"写成一份文档，存到系统的临时目录 （$TMPDIR，没有就 /tmp）而不是当前工作区。 这个细节有道理：交接文档是一次性的，放进仓库只会变成又一份过期文档。

三条规则决定了它好不好用：

  • 不重复已有产物。规格、计划、ADR、issue、提交、diff 都只写路径或链接。
  • 带一节"建议使用的技能"，直接点名下一个智能体该调哪几个。
  • 先脱敏。密钥、密码、可识别个人的信息一律不留。

它还能接一个参数，用来描述下个会话要做什么，文档会据此调整重点。 这个功能小，但用起来差别很大：不给参数，它写的是"发生了什么"；给了参数，它写的是"你要接着做什么"。

05其余 17 个：什么时候该想起它们

不用全记。记住"什么情况下该想起它"就够了。

技能类型什么时候想起它
grill-me user 计划还没成型、你心里有数但说不清的时候。它是 grilling 的一层最薄的壳，不建文档，只要答案。
grilling model 被别的技能内部调用。核心机制是设计树 + 轮次：一轮只问"前置条件都已确定"的那批问题，每个问题都带一个推荐答案，措辞让"是"就等于接受推荐。事实查询它自己派子智能体去找，不问你。
wayfinder user 一整块活儿装不进一个会话的时候。它把这块活做成一张决策票地图，一次只解一张，直到通往终点的路清晰。
triage user issue 堆积、外部 PR 一堆的时候。它用一个小状态机推着走：分类、验证、必要时开一轮访谈，最后写出 agent-ready 的简报。
implement user 只有一张票或一份小规格的时候。它驱动 tdd 在约定的接缝上推进，提交前用 code-review 收尾。
research model 需要查一手资料、查 API 事实、或者只是想把读文档的体力活外包出去。它跑在后台，产出带引用的 Markdown 落进仓库。
retro user 一次会话结束、感觉哪里一直不顺的时候。它不改代码，改的是智能体的工作环境：导航、自动检查、编码标准、steering 文件、工具链，最严重的排最前。
codebase-design model 要讨论模块该多深、接缝放哪、接口暴露什么的时候。它是一本词典，不是一次会话：module / interface / depth / seam / adapter / leverage / locality，外加删除测试、"接口就是测试面"、"一个 adapter 是假想，两个才是真的"。
domain-modeling model 在讨论术语、写 GLOSSARY.md、记 ADR 的时候。它做的事是主动拿边界场景去压测现有词义，压不住就改词或加词。
pr model 写 PR 描述的时候。三件事：摘要用最小的可视化讲清改动、before/after 证据证明它真的跑得通、以及一句合并风险判断（单向门还是双向门，爆炸半径多大）。
wizard model 有些步骤只有人能执行：开云资源、配 CI 密钥、走一个没见过的第三方后台、做一次性切换。它生成一个交互式 bash 向导，一步一步带着人走。
ask-matt user 你忘了有哪个技能、或者不知道下一步该干嘛的时候。它是整个仓库的路由表。有意思的是它被明确要求：在说某个技能做什么之前，先去读那个技能的 SKILL.md。
wait-what user 它上一段话你完全没接住的时候。一句话：打住，重讲，给我上下文，用平实英语，用 GLOSSARY.md 里的词。
teach user 要跨多次会话学一个东西的时候。当前目录就是有状态的工作区，进度存在那儿，不靠会话记忆。
to-questionnaire user 有个决定你一个人答不了，得问某个具体的人。它把这个决定变成一份 Markdown 问卷，可以异步填，也可以开会一起填。注意它拷问的是"怎么发出去"（给谁、要什么回来），不是主题本身。
writing-for-agents model 写 skill、改 AGENTS.md / CLAUDE.md、或者写任何"靠指针被智能体读到的文档"的时候。这套仓库自己的文档规范就来自它。
setup-… user 每个仓库跑一次。问你三件事：用哪个 issue tracker、分诊时打什么标签、生成的文档存哪。不跑它，前面一半技能会拒绝工作。

表格里"类型"那一栏值得再看一眼。model 那一半几乎都是"纪律"和"词典"，user 那一半几乎都是"动作"和"节奏"。 这个划分不是分类癖，它决定了你该怎么改：动作型技能可以随便重排顺序，纪律型技能最好别动， 因为它被好几个地方引用着。

06五个我踩过或差点踩的坑

都写在技能文件本身里，但不读进去就会中招。

01
装了两遍，每个技能都有两份
插件安装和 npx skills add 二选一。前者自动更新、只读；后者把可编辑的文件拷进项目、要手动更新。两个都装，模型会看到两份同名技能，行为开始飘。
02
没跑初始化，然后怪技能不好用
差不多一半的工程技能第一句就是"tracker 和标签词汇应该已经给你了，没有的话去跑 setup"。跳过这一步，它会停下来让你先去跑，看起来像坏了，其实是在守规矩。
03
指望 to-spec 访谈你
它明确写了不做访谈，只综合已有内容。对话里什么都没有的时候用它，会得到一份空洞的规格，还带着 ready-for-agent 标签，比没有规格更危险。
04
用 tdd 但没先约接缝
规则是"没确认过的接缝上一条测试都不写"。直接让它开干，它会先反问你"公开接口是什么、测哪几个接缝"。省掉这段对话，后面测试会写在你不想维护的地方。
05
在诊断时催它给结论
它第一阶段就是要建一条能红的回路，会显得很慢。这时候催一句"你直接看代码说是哪儿的问题"，整个技能的价值就归零了，你会得到一个自信的猜测。

07装，然后改

这套东西最大的优点是可以直接改，别把它当黑盒。

装法不止一种，按你的智能体选一条就行。插件方式会自己更新，适合只想用不想改的； 把文件拷进项目的方式适合要动刀子的。 

# 插件方式（自动更新，推荐先用这个）
claude plugin install mattpocock-skills@claude-plugins-official

# Codex
codex plugin marketplace add mattpocock/skills
codex plugin add mattpocock-skills@mattpocock

# 其他智能体，或想要可编辑副本
npx skills@latest add mattpocock/skills -a cursor
npx skills@latest update

装完第一件事不是马上用，是在仓库里跑一次初始化。它会问你三件很具体的事： 用哪个 issue tracker（GitHub、GitLab、本地文件，或者你描述的任何东西）、 分诊时打什么标签、生成的文档放哪。这三个答案会写进项目里，后面所有技能都靠它。

值得改的地方

我在自己项目里改过三处，都很有价值：

  • tdd 的接缝清单。把项目里那几条真正的公开接口名字直接写进去，它就不会每次重新猜。
  • code-review 的规范来源。默认读 CONTRIBUTING.md，我改成了指向团队那份更细的规范，外加上几条只有我们知道的红线。
  • grilling 的提问轮次上限。默认会一直问到设计树收敛，小需求上有点过。加一条"三轮内必须收口"的约束，体验好很多。
改之前先看一眼

纪律型（model-invoked）的技能被好几个地方引用。grilling 被 grill-me、 grill-with-docs、triage、wayfinder、improve-codebase-architecture 同时依赖；codebase-design 被 tdd、to-spec、架构普查依赖。 改它们的输出格式，等于同时改五个技能的行为。

08最后

这套技能最不像"AI 工具"的地方，是它反复在讲人的工程判断： 接缝该放哪、这张卡能不能独立验收、这个测试是不是在测实现细节。 它没有替你做这些判断，只是把每个判断都变成了一个必须回答的问题。

所以我不建议一次装全。挑三个，用两周，把不满意的部分改掉。 等你发现自己在某一步开始主动想"这里应该先约个接缝"， 那说明工具已经退到背景里了，剩下的才是你自己的。

以上内容基于对这套技能全部 SKILL.md 与实际使用经验的整理。示例场景为便于说明做过简化， 技能的具体规则以其自身文件为准。
