4 · 错误态改为 DisplayState 的显式 case

Speculative in-process
ElderCalculator/Engine/CalculatorEngine.swift:15-16, 162-170 · 消费方：ContentView.swift:103 / VoiceAnnouncer.swift:27

Before — 两个字段说同一事实

DisplayState
mainText"不能除以零"
errorMessage"不能除以零"

enterDivideByZeroError 分别写两个字段，靠人肉保持同步

After — 错误是显式状态

DisplayState
case normal(mainText, …)
case error(message) — 单一事实来源

红色样式与错误优先播报都从 case 派生

问题

错误态下 mainText 与 errorMessage 同值，两个并行字段表达同一事实，同步靠写入方自觉。

方案

让错误态成为 DisplayState 的显式 case，而不是两个并行字段。收益小，不动也成立。

收益

  • 单一事实来源
  • 现有消费方用法都合理
  • 冗余真实但代价低

已验证足够深，不建议动

  • CalculatorEngine — 接口 3 个成员（press / displayState / history）对约 400 行实现；历史记录、算式拼装、格式化全部内聚；40+ 测试只打接口。
  • ChineseSpeechFormatter — 一个静态方法对约 90 行纯函数实现，测试充分（唯一瑕疵见候选 2）。
  • HistoryDrawer / SettingsView / AppSettings — 称职的薄壳，数据单向流入，无逻辑埋藏，无假想接缝。
  • 屏幕按钮与物理键盘两个适配器共用 press 入口 — 真实接缝（两个适配器、一条路径），行为一致性从构造上保证，不要抽象掉。

最高推荐

候选 1 · 播报词决策与语音合成器分层

语音播报是 CONTEXT.md 钦定的适老化核心功能，却是代码库中唯一"有产品规则、无测试路径"的模块。 分层后播报词决策变成 (key, DisplayState) → String 的纯函数，可以像 CalculatorEngine 一样 TDD； 合成器退到接缝之后，生产用 AVSpeechSynthesizer、测试用记录型假适配器——两个适配器，真实接缝。 成本低（一个文件的重构），收益直接落在产品卖点上。回到候选 1
