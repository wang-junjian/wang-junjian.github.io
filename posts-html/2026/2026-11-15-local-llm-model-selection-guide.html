本地大模型选型参考

这份文档不回答「哪个模型跑分最高」，而是回答「在你这台机器上、你要做的那件事上，应该装哪一个」。榜单名次和下载量在 2026 年已经是两张几乎不重叠的表——前者衡量能力上限，后者衡量可部署性，选型应当以后者为准。

00八条核心论断

先给骨架。下面每条都可以被证伪，后面所有章节都是其中一条的展开。只读这一页，也足够做出第一轮判断。

一句话结论：2026 年 11 月，本地部署的事实标准是 27B 稠密模型 / 30–35B-A3B MoE，对应 16–24 GB 权重；旗舰开源模型（1T 以上）已经和「本地」解耦，它们的作用是前沿参照系，不是装机目标。

  1. 第一约束是内存，不是跑分。「装得下」看容量，「跑得快」看带宽，两个独立问题；4-bit 权重约每 10 亿参数 0.6 GB，但静态权重不等于运行时显存，KV cache 常常才是击穿上限的那一项。
  2. 榜单和下载量是两张表。Kimi K3.1 Pro 在 Artificial Analysis 上是开源第一（46.5），Q4 约 1.4 TB；Qwen3.8-27B 月下载 801 万、18 GB 就能跑。做选型看后者。
  3. 27B 这一档是社区主战场。量化实验、去审查衍生、harness 调优、A/B 评测几乎全部集中在 24–32 GB 档，因为它是「单人单卡能反复迭代」的最大模型。
  4. 许可证比几个点的跑分更重要。Qwen3.8-27B 是 Apache 2.0、DeepSeek V4.1 Flash 与 GLM-5.3 Flash 是 MIT，而 Kimi K3.1 Pro 是自定义许可、MiniMax 是 Community License；商用边界差异远大于榜单差距。
  5. 量化是真正的「第二个模型」。同一权重、同一 harness、同一 4-bit 量化，两次 DeepSWE 1.1 跑出 38.94% 与 31.86%，113 个任务里 32 个结果不同。损伤先表现为方差，而不是平均分下滑。
  6. 厂商跑分普遍缺独立复现。Qwen3.8-27B 模型卡上每一项 benchmark 都由阿里自测，其中 SWE-bench Pro 用的是阿里自行修正并重跑基线的版本，与公开榜单不可比。
  7. harness 才是产品。Docker 的 3,570 场景评测里 Qwen3 14B Q4_K_M 工具调用 F1 达 0.971，但社区在 Open WebUI / Ollama 上仍频繁失败；xLAM-2 8B 因 chat template 不兼容从榜单第一掉到 15%。
  8. 小模型的价值在分工，不在聊天。2B 级做端侧语音与工具输出解析、5B 分类器做事实校验门、27B 做生成——这是本地多智能体里更稳的结构，也和「电子宠物」这类低延迟陪伴场景直接相关。

这份文档的立场

所有「厂商自报」「社区自报」的数字都按原样标注，不冒充独立实测。选型建议给的是起始点，不是结论；最终判断必须来自你自己的任务集 A/B。这是观点，不是社区共识。

02先定约束：容量、带宽、上下文

所有选型错误里，最贵的一类是「按参数量挑模型」。正确的顺序是先算三个预算，再看模型卡片。

容量决定「装不装得下」

Q4 量化约 0.6 GB / 十亿参数，Q8 约 1.1 GB，BF16 约 2 GB。但这是磁盘上的静态权重，不是运行时占用。真实占用 = 权重 + KV cache + 视觉投影 + 运行时开销，工程上建议再留 15–25% 余量。

带宽决定「跑得多快」

自回归解码每生成一个 token 都要把激活权重读一遍，所以 tok/s ≈ 内存带宽 ÷ 每 token 读取量。MoE 每 token 只激活部分专家，在同一台低带宽机器上可能比稠密模型快 5–8 倍，这正是 Strix Halo 这类统一内存设备的存在理由。

把「7.89 GB 权重能在 8 GB 卡上跑 27B 智能体」当作真实用例，是 2026 年 10 月社区讨论里最典型的误读：Saluki 27B 的 2-bit 权重文件确实只有 7.89 GB，但加上约 0.9 GB 视觉模块和随上下文膨胀的 KV cache，标准 8 GB 卡加载即溢出，随后退回系统内存、速度断崖下跌。该发布方未公开评测 harness、校准流程与 llama.cpp 固定 commit，也没有第三方复现。

A 组 · 消费级主力（16–32 GB）

这一组是 2026 年 11 月社区真正的日常主力：单人单卡可反复迭代的最大模型规模。

Qwen3.8-27B

Alibaba Qwen · 2026-08-14 · 消费级主力
社区事实标准Apache 2.0原生多模态27B dense

如果你只装一个模型，装这个。它是目前唯一同时具备干净许可、原生视觉输入、长上下文、消费级体积与最完整社区生态的选择。

架构27B 稠密，原生多模态（文本 / 图像 / 视频 → 文本），Gated DeltaNet 与 Gated Attention 混合，64 层
上下文262,144 token 原生；用 YaRN 可扩展到 1,000,000，但不是原生 1M
许可证Apache 2.0，无访问门槛，权重在 Hugging Face Qwen/Qwen3.8-27B
体积BF16 约 55.6 GB；Ollama 4-bit 构建约 18 GB；FP8 官方版本另提供
热度近一个月 Hugging Face 下载 801 万、1.9 万 likes（2026-11 初）

为什么特别

它不是跑分最高的开源模型，却是生态最厚的一个。2026 年 11 月的量化实验（Unsloth Dynamic、Nace、Hessian-Refined）、去审查衍生、GGUF 供应链、MCP 与浏览器 agent 实验，几乎都以 27B 这一档为基准。选它意味着你能直接复用别人已经踩过的坑：现成的 chat template、现成的 KV cache 预算、现成的评测脚本。

另一个被低估的点是许可。Apache 2.0 没有月活或营收阈值，而同期若干旗舰开源模型带自定义条款；对要放进产品里的团队，这一条比榜单上几个点更硬。

上手

ollama run qwen3.8:27b-q4_K_M
mlx_lm.generate --model mlx-community/Qwen3.8-27B-4bit --prompt "..."

模型标签名随运行时版本变化，执行前回查 Ollama library 或 mlx-community 仓库。官方模型卡建议用 SGLang、vLLM 或 TokenSpeed 服务，并提醒常见框架静态启用 YaRN 会损害短输入精度。

支持证据官方规格与许可可查；801 万月下载是最强的可部署性信号；社区报告 Q6 量化在 oMLX + MCP 下约 75 tok/s 并能驱动浏览器完成网页任务；Docker 早期 3,570 场景评测中同族 Qwen3 14B Q4_K_M 工具调用 F1 达 0.971。
反对证据与风险模型卡上每一项 benchmark 都由阿里自测：SWE-bench Pro 61.7 建立在阿里自行修正题目并重跑基线的版本上，与公开榜单不可比；QwenSWEBench、CoWorkBench 两项自研测试未公开题集与样本量；对比对象是较旧的 Opus 4.6 Max；无第三方独立复现。另有 892 楼的社区长帖称同款模型在 3090 + 128K 上下文下做编程「完全不可用」。
证据强度：规格 / 许可 / 上下文 = 一手官方模型卡；下载量 = 平台可查；跑分 = 厂商自测（弱）；tok/s 与可用性争议 = 社区自报（弱，且方向相反）。建议动作：拿自己的代码或检索任务做 A/B，不要引用模型卡上的 SWE-bench 数字做验收。

Qwen3.6-35B-A3B

Alibaba Qwen · 消费级速度甜点
速度优先35B 总 / 3B 激活官方 GGUF

当 27B 稠密模型的交互速度不够、但你还不想碰统一内存设备时，MoE 只激活 3B 参数是更划算的路线。

架构MoE，约 35B 总参数 / 3B 激活，每 token 读取量远小于同规模稠密模型
体积Unsloth 4-bit 约 23 GB（128 GB 档指南口径）
官方 GGUFggml-org/Qwen3.6-35B-A3B-GGUF，2026-11-12 记录 220,506 次下载
社区测速3090 上 Q4 报告 130+ tok/s；4090 上 IQ4_XS + KV q8_0、65K 上下文占 24.2 GB，报告约 180 tok/s

为什么特别

它把「27B 级质量」和「接近小模型的响应速度」放在同一张卡上。对需要常驻的智能体、自动补全、多轮工具调用这类延迟敏感任务，激活参数量比总参数量更能预测体验——这正是图 1 里把 MoE 与稠密模型分开看的理由。

上手

ollama run qwen3.6:35b-a3b
llama-server -hf ggml-org/Qwen3.6-35B-A3B-GGUF -ngl 999 -c 32768 --jinja
支持证据官方 ggml GGUF 仓库可查且下载量高（22 万）；MoE 低激活量的物理优势在低带宽设备上尤其明显；多个独立来源都把它列为「最快全能型」候选。
反对证据与风险130 / 180 tok/s 来自不同硬件、不同量化档、不同上下文长度与不同运行时，属二手汇总，不能直接横向比较；MoE 对内存容量仍按总参数计，KV cache 预算不因激活小而减少。
证据强度：仓库与下载量 = 一手；架构优势 = 可推导的物理事实；速度 = 社区自报汇总（弱）。建议动作：固定量化档与上下文长度后自测首 token 延迟与稳态 tok/s 两个指标。

Gemma 4 系列（E2B / 12B / 31B）

Google · 多尺寸阶梯 · 企业友好
Apache 2.0多模态工具调用稳定尺寸阶梯完整

如果你要在同一套 harness 下覆盖从手机到 24 GB 显卡的多种设备，Gemma 4 的尺寸阶梯和干净许可让迁移成本最低。

尺寸E2B、12B、26B-A4B、31B 等多个档位，覆盖端侧到单卡
许可证Apache 2.0
官方 GGUF 下载2026-11-12：E2B 247,860；12B 105,209；31B 54,854
社区表现26B A3B 在 3090 + LM Studio 上被报告工具调用稳定，80–110 tok/s、260K 上下文；8 GB 显存用户仍靠 26B QAT 约 26 tok/s

为什么特别

它是「同一家族跨档位」做得最完整的一支。对做产品而非做实验的团队，这比单点性能更值钱：prompt 模板、工具调用 schema、量化档位可以在不同设备上复用，升级硬件时不必重调整个 harness。

社区多份报告把 LM Studio 上的 Gemma 4 列为结构化输出与工具调用较稳的选择，而同期 Open WebUI / Ollama 上多个模型出现「把原始 JSON 打印到聊天窗口而不执行工具」的问题。这再次说明运行时层常比权重更致命。

上手

ollama run gemma4:12b
mlx_lm.generate --model mlx-community/gemma-4-12b-it-4bit --prompt "..."
支持证据三个尺寸的官方 GGUF 下载量均可查且位居前列；Apache 2.0 无附加商业条款；社区报告的低显存可用性与工具调用稳定性来自多个独立帖子。
反对证据与风险2026 年关于 FP4 推理引擎刷分的社区反弹指出，1–10B 小模型在 3–4 bit 下的精度损失远大于 70B 级，而 Gemma 4 的主战场恰好在小尺寸；「把量化精度写进标题，别放脚注」是这一档最需要注意的读法。
证据强度：许可与下载量 = 一手；工具调用稳定性 = 社区自报（弱）；量化损伤方向 = 多篇量化研究一致（中）。建议动作：小尺寸优先 Q6/Q8 起步，别默认 Q4。

Qwen3-Coder-30B-A3B / Coder-Next

Alibaba Qwen · 本地代码助手专用
代码专用Aider + Ollama 组合量化要保守

源码不能出内网的场景里，它是「本地版 Cursor」最常被验证的一条路线；代价是对量化档位比通用聊天敏感得多。

定位面向长程软件工程与 agentic coding 的后训练模型
官方 GGUFggml-org/Qwen3-Coder-30B-A3B-Instruct-GGUF，2026-11-12 记录 61,790 次下载
体积30B-A3B Q4 约 18–20 GB；Coder-Next 在 128 GB 指南里 4-bit 约 46 GB
典型组合Aider + Ollama（终端编码、Git 感知、自动提交），或指向本地端点的 IDE 插件

为什么特别

通用模型做代码补全尚可，做「读仓库 → 改多文件 → 跑测试 → 修回归」这类长链条任务时，专用后训练的差异会放大。Coder 系列也是少数在官方 GGUF 仓库里有独立条目的代码模型，说明它被真实下载使用，而不只是榜单上的名字。

上手

ollama run qwen3-coder:30b
aider --model ollama/qwen3-coder:30b
支持证据官方 GGUF 仓库可查；Aider + Ollama 被多份第三方指南列为成熟的本地编码栈；专用后训练在 agentic coding 上的优势有厂商与社区两条独立线索。
反对证据与风险社区同模型对比显示 HumanEval 从 BF16 56.10% 降到 Q4_K_M 50.61%、Q8_0 52.44%（164 题小样本）；vLLM 研究里 4-bit 选项把 HumanEval 拉到 45.7–51.8%。Q4 对代码任务可能不是省显存，而是买返工。此外 3090 + 128K 上下文下「本地 27B 编程不可用」的长帖也是真实反例。
证据强度：仓库 = 一手；量化对代码的影响 = 小样本社区评测 + 量化研究（中，方向一致）；「可用 / 不可用」两极体验 = 社区自报（弱）。建议动作：从 Q5/Q6 起步，用自己的仓库跑固定任务集，别用通用 HumanEval 代理。

Nemotron 3.5 Lightning 30B-A3B

NVIDIA · 12 GB 档的速度候选
低显存最优候选MoE官方 GGUF

当显存只有 12 GB 又想要接近 30B 级能力时，第三方按 VRAM 分档的榜单把它列在该档最强位置。

架构MoE 30B 级 / 约 3B 激活，Lightning 变体面向低延迟
官方 GGUFggml-org/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-GGUF，2026-11-12 记录 218,656 次下载

为什么特别

它代表了另一条思路：不是把大模型压小，而是让厂商直接针对推理成本设计 MoE 结构。对 12 GB 卡用户，这比「把 27B 硬塞进 8 GB」的 2-bit 极限量化更可靠，因为不需要牺牲到表达冗余崩塌的程度。

上手

ollama run nemotron3.5-lightning:30b
llama-server -hf ggml-org/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-GGUF -ngl 999

反对证据与风险「12 GB 档最强」来自单一聚合榜单的评分口径，未见独立复现；厂商优化明显偏向 CUDA，Mac MLX 与 AMD ROCm 上的表现需另测；Lightning 与 Super 是不同规模，别把两者数据混用。
证据强度：仓库与下载量 = 一手；档位排名 = 第三方榜单（中）；跨平台表现 = 未验证。建议动作：先确认你的运行时有没有该架构的 kernel 支持，再谈速度。

B 组 · 轻量与端侧（≤16 GB）

这一组不该拿来做主聊天模型。它们的价值是在多智能体里承担低延迟的专门角色——语音前端、解析、校验、判定——这也正是情感陪伴硬件与端侧交互最需要的形态。

LFM3-Omni-2B / LFM3-1.7B

Liquid AI · 端侧 any-to-any

另有一条容易被忽略的顺序问题：GSQ / RCO 这类混合比特量化在 llama.cpp 分支上跑得通，在 vLLM 上支持却不完整，社区还在自行打补丁。所以「换了量化包」往往同时意味着「换了运行时」，这两个变量必须分开测，否则你无法判断提升来自权重还是引擎。

05运行时与工具栈

同一份权重，在 LM Studio 里工具调用稳定、在 Ollama 里可能打印原始 JSON；榜单第一的 xLAM-2 8B 因 chat template 不兼容，在另一套评测里只有 15% 通过率。决定体验的常常是 serving 层，不是权重。

推理引擎llama.cpp要完全控制、CPU 或异构硬件MIT；GGUF 生态底座；2026-05-16 主线合入 MTP 投机解码；2026-05 曾披露 6 个 GGUF parser 漏洞，影响所有下游封装

前端Open WebUI、AnythingLLM聊天界面、私有知识库与 Ollama 组成最常见的十分钟起步栈；但工具调用失败案例也多来自这一层

给 Mac 用户的路径

优先 MLX-LM 或 LM Studio 的 MLX 引擎；GGUF 走 Ollama 时会自动切到 llama.cpp Metal。统一内存决定容量上限，但带宽决定体感，别只看「能装下」。

给国产卡与多智能体的路径

SGLang 已把 Ascend 列入硬件支持，agent 循环里共享长 system prompt 时 RadixAttention 比 vLLM 更对路；但 GGUF 生态仍围绕 llama.cpp / CUDA / Metal，国产软件栈要单独做 POC 实测。

把 harness 纳入版本管理

固定运行时 commit、chat template、采样参数、上下文长度和工具 schema，把它们和模型权重一起存档。社区里「同一个 Qwen3.8-27B 有人说替代了 Cursor、有人说完全不可用」的两极体验，绝大多数能归因到这一层。

08结论与判断

三句话版本：先在 约束章节 算出你的容量、带宽与上下文预算；在 24–32 GB 档装一个 Qwen3.8-27B 级别的宽松许可主力，再配一个 2B 级小模型做解析与校验；然后用 检查清单 在自己的任务上做 A/B，而不是相信任何榜单。

如果只有 8–16 GB

Gemma 4 12B 或 Granite 4.2 8B 起步，小模型优先 Q6/Q8；别被 2-bit「7.89 GB 跑 27B」的宣传带偏，KV cache 会先击穿显存。

如果有 24–32 GB

这一档是本文档的主推荐：Qwen3.8-27B 求均衡、Qwen3.6-35B-A3B 求速度、Coder 系列求代码。先固定 harness，再比量化档。

如果有 128 GB 统一内存

优先 MoE（gpt-oss-120b、GLM-5.3-Flash、Qwen3.8-Flash-Next），并在 BIOS 里调高 GPU 显存分配；稠密 70B 在这类设备上通常慢到失去交互性。

这是观点，不是社区共识

「27B 是当前主力」「量化损伤优先表现为方差」「榜单与下载量应当分开看」这三条是本文档基于 2026-11 证据给出的判断，社区里存在明确相反的声音——既有 27B 驱动浏览器替代商业订阅的案例，也有 892 楼声称同款模型完全不可用的长帖。分歧本身说明：harness 与任务分布比模型名更决定结果。

时效性提醒：模型约半年一代，推理引擎逐月升级；Qwen4 系列（qwen4-max / coder-plus / omni-120b）已从 Qwen Code 仓库 PR 泄露，近期可能发布。若在大额采购设备，建议先复核当月榜单再决策。
