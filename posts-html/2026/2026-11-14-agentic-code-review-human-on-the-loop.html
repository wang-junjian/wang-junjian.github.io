00摘要：十条核心论断

只读一页也能用。下面十条都是可证伪的断言，报告后续每一章都是其中某条的展开、举证或限制条件。

  1. 人还在看，但「逐行」这个默认值已经死了。在一个 802 人 / 196,212 PR 的纵向面板里，收到人工评审的 PR 从 89% 降到 68%，收到自动化 AI 评审的从 19% 涨到 84%；机器阅读的覆盖量已经反超人类，且合并率与回滚率没有变差。大样本观察
  2. 「看多少」不是百分比，是按爆炸半径拨的旋钮。Addy 给出的三个变量（爆炸半径、代码寿命、需要理解它的人数）与 Anthropic 的 0 / 1 / 2 人批准分级，是同一个制度的两面：不是「看 30% 的行」，而是「这类变更配几道检查」。方法论
  3. 瓶颈转移是速度巧合被打破的结果，不是态度问题。过去资深工程师读得比初级写得快，评审能顺势发生；智能体几分钟产出一千行，人的阅读带宽没变。排队论的直接推论是：让验证更便宜、更小、更早，而不是让评审更慢。推导
  4. 更多代码不等于更多交付，差额落在评审队列里。718 家企业 / 约 3 亿工作事件：代码 +30%、commit +20%、PR +23%，而 Jira issue 与 epic 完成数无统计显著变化；PR 到合并耗时 +49%，要求修改的比例近乎翻倍。大样本观察
  5. 主流做法不是取消评审，而是把评审重建成一条分层流水线。生成侧自证 → 全新上下文复审 → 并行 AI 评审 + 投票 → 安全审查 → 确定性 CI → 按风险的人工批准 → 合并队列与灰度撤销。机器读前三遍，人在上游定意图、下游签风险。厂商工程披露
  6. 让 AI 审 AI 有效，但「同模型四副本」不是冗余。146 个真实 PR、679 条发现里，93.4% 的被标记位置只被四个评审器中的一个发现，没有一个被四者同时发现；异构性才是价值来源，同族模型会共享盲点，产出「借来的自信」。单一案例
  7. 「测试通过」在智能体 PR 里是主张的一部分，不是证据。GitHub 把 CI gaming（删测试、跳 lint、降覆盖率阈值、加 || true）列为第一红旗；Addy 的要求更直接：读测试 diff 要比读实现更仔细，测试必须独立于生成器。官方实践
  8. 评审原本主要不是找 bug，被自动化拿走的那部分必须显式补回来。微软研究：仅 14% 的评审评论涉及缺陷。共享理解、mentoring、系统心智模型这类副产品，若不转成 spec、决策日志与 eval set，会以「理解债」在 on-call 时偿还。经典实证
  9. 责任不可转移：零人批准不等于零人负责。发起智能体的那个人就是 reviewer，智能体的批准永不算人；人保留「这个功能该不该做」「架构是否合理」「现有检查是否覆盖此风险」三个决定，以及事故归属。官方制度
  10. 度量要从「合并 PR 数」换成「人时预算 + 护栏」。把每 PR 人批准数、人工评论数、等人时间当预算，用回滚率 / 事故率 / 变更失败率做护栏；Anthropic 自己也承认，按回滚率自动收紧审批的「熔断」尚未建好。官方披露

一句话回答原问题

人还在看，但看的对象从「每一行 diff」换成「意图、风险、测试改动与证据包」；比例不再是一个全局百分比，而是按爆炸半径调的旋钮。主流智能体编码没有取消评审，而是把评审拆成多道机器闸门，把人从 loop 里挪到 loop 上——human in the loop → human on the loop。

阅读提示：本报告把证据分成五级（大样本观察 厂商工程披露 方法论/推导 单一案例 自报调查）。凡带立场的数字，第 03 章与第 12 章都给出了折扣说明。

01范式判定：这场争论到底在问什么

Addy Osmani 在 2026-06-15 的《Agentic Code Review》里没有问「AI 评审准不准」，他问的是一个更刺耳的问题：当机器写得比人读得快几个数量级时，「有人读过这段代码」还能不能继续充当信任机制。文章的核心观察是，代码评审过去能运转是一个速度上的巧合：资深工程师读代码的速度快过初级工程师写代码的速度，所以「顺手看一眼」在流程上免费。智能体打破了这个巧合——产出一份一千行的合格代码，比你读完这一段文字还快，而人的阅读速度没有变。

于是约束条件从「写」滑到了「一个人确信这个改动是对的」。这不是工具能力问题，是流程的承重结构变了。理解这一点，才能看懂后面半年里所有看似矛盾的实践：GitHub 仍在教人用 10 分钟检查智能体 PR，Anthropic 已经允许低风险变更零人批准——两者不是立场对立，而是同一条曲线上的不同风险档位。

概念分野：四个常被混用的词

概念问的问题由谁回答失效模式

评审 review这个改动是否该进代码库？异构评审器 + 按风险介入的人同族模型相关盲点，四人份同一份自信

这四件事在传统流程里被压进「code review」一个动作，因此当有人宣布「code review 已死」时，通常只指第二项的一部分（逐行读 diff）被机器接管。Addy 在同年 9 月的《The Code Nobody Reads》里明确修正了自己两年前「逐行审查 AI 生成代码」的建议：

你不必读全部代码。但每个变更仍需要某种审查，而且每个变更都需要一个对「是否发布」这个决定负责的人。变化在于：仔细地逐行人工阅读，不再是提供这种审查的唯一方式，也不总是最好的方式。

判别式：一个组织落在曲线的哪一段

不用问「你们用不用 AI 评审」，问下面三个问题就能定位：

  1. 一个低风险变更，能否在无人批准的情况下合并？能，且关卡是自动的 → 已在「human on the loop」段；不能 → 仍在逐行段，队列迟早堵。
  2. CI 配置和覆盖率阈值，智能体有没有写权限？有 → 绿色信号不可信，无论后面叠了多少 AI 评审器。
  3. 发起智能体的那个人，是否就是记录中的 reviewer？不是 → 问责链已断，零人批会变成无人负责。

本章服务的论断

D1（逐行默认值已死）与 D9（责任不可转移）。把「读代码」与「拥有发布决定」拆成两件事，是理解后面所有实践的前提；争论之所以激烈，正是因为双方在用同一个词指不同的事。

02理论根基：为什么流水线必须是这个形状

这一章不谈工具。四条理论各自能推出一个具体工程动作，如果不能，说明它只是个比喻。

2.1 排队论 → 让验证更便宜，而不是让评审更慢

把评审队列看成一个到达率为 λ（智能体开 PR 的速率）、服务率为 μ（人类评审者完成一份可信审查的速率）的服务台。利用率 ρ = λ/μ。排队论给出的等待队列长度近似为 L ≈ ρ²/(1−ρ)，当 ρ 从 0.5 升到 0.9，等待量不是翻 1.8 倍而是接近 10 倍。这解释了为什么「零评审合并 +31.3%」不是纪律问题：没有任何团队决定停止评审，是排队排不过来，于是代码开始未经阅读就合并。

可推出的动作只有三个：降 λ（提高 intake 门槛、限制在制品、拒绝大而无主的补丁）、升 μ（机器承担前三遍阅读、把 diff 拆小、给评审者证据包）、或者缩短「人」这个服务台的单次服务时间（按风险分级，只让高风险变更占用深度时间）。「要求大家更认真地读」是降低 μ，会把队列推向更陡的非线性区——这正是最反直觉、也最常被管理层选错的那个选项。

2.2 验证成本不对称 → 把检查前移，而不是在后段叠加

生成的边际成本趋近于零，验证仍是串行的认知工作，且错误发现得越晚越贵。Addy 引用的一句被反复转述的判断来自 Claude Code 作者 Boris Cherny：给 Claude 一个验证自己工作的方式，最终效果能差 2—3 倍。重要的不是这个倍数（属于个人估计，单一案例），而是它指出的结构：同一份缺陷，在 PR 之前被智能体自己跑测试发现，成本是几十秒；在合并后被 on-call 发现，成本是事故与回滚。

推论是验证必须发生在 PR 存在之前：编码智能体在隔离容器里跑测试 / lint / typecheck 并迭代到通过，界面改动附截图，且必须展示命令与输出。Anthropic 的官方措辞是「回复一句『测试全部通过』不算数」。后段叠再多评审器，也补不回前段省下的那一步。

2.3 委托—代理与独立性 → 测试不能由生成器自己出

一个模型既写实现又写断言，等于自己给自己出题，绿色 CI 的信号量为零甚至为负。Addy 把这条推到极致：测试必须独立于代码生成器，独立来源可以是 spec、参考实现、既有黄金用例，或至少是不同上下文的独立实例（他类比航空 DO-178C 与 SQLite 的做法）。在智能体 PR 里，「读测试改动要比读代码更仔细」不是经验之谈，而是信息论上的必然：实现是主张，测试是证据，若两者同源，则只剩主张。

GitHub 把这条变成了硬阻断：任何削弱 CI 的改动都是 blocker，没有例外——删测试、跳过 lint、降低覆盖率阈值、把 CI 步骤塞进新条件、给命令加 || true。对应到权限设计上，就是 CI workflow 文件与覆盖率阈值必须对编码智能体只读。

2.4 相关盲点 → 异构性比数量更重要

多智能体投票常被当成可靠性来源，但投票过滤的是独立噪声，不是相关盲点。当 writer、reviewer、judge 来自同一模型家族，它们会在同一处自信地达成一致。Addy 造了个很准的词：borrowed confidence（借来的自信）——系统的确定感变成了你的确定感，而实际上没有任何人理解过任何东西。工程推论不是「别用多智能体」，而是「别用同一个模型的四份副本」：在关键路径上跑两个性格刻意不同的评审器，比堆四个同构的更有信息量。

理论章最容易犯的错

把这四条当成「多上几道关卡」的辩护。它们的共同结论其实是相反的：关卡数量不是目标，关卡之间的独立性、确定性、以及不占用人时，才是。第 06、07 章会看到，Anthropic 踩过的坑恰恰是关卡太多导致评审轮数失控。

3.2 数量级自洽性反推

引用前做一次反推，能挡掉大部分二手转述的失真：Harvard 论文里代码 +1,494 行 / 基线 5,017 行 = 29.8% ≈ 30%；PR +1.22 / 5.34 = 22.8% ≈ 23%；耗时 +3.45 天 / 7.03 天 = 49.1% ≈ 49%，三组自洽。LinearB 的 17.6 / 3.4 = 5.18，与官方表述的 5.25× 在同一量级（P75 精确值差异）。唯独「评论数 +35% 与 +53%」在不同二手源里冲突，故正文采用与论文解读一致的 35% 并显式标注，不做平均。

3.3 反证据：三个把结论往回拉的事实

分层不等于万无一失

Anthropic 2026-03-26 上线的会话清理优化有 bug，恢复对话后每轮都执行清理，导致模型健忘、重复、工具调用异常，直到 4-10 才修复。这个改动穿过了多轮人工与自动审查、单元测试、E2E 与内部试用；复盘用 Code Review 重审出事 PR，给足仓库上下文时 Opus 4.7 找到了，4.6 没找到。检出率依赖模型能力与上下文完整性。厂商披露

AI 评审会把自己堵死

一个 CLI PR 一夜之间经历 50 多轮「智能体写—智能体审」，git blame 回溯发现约 59% 的评论指向首轮之前就存在的老代码。加「三轮上限 + 只复审新 diff + 同类问题只提一次」后，一轮通过率才从 65% 升到 78%。厂商披露

发现变便宜，分诊没变便宜

《The Code Nobody Reads》里的 Teleport 脚注：13 名工程师在一个季度里挖出近两年积累的高危漏洞。自动化让「找到」变便宜，但「判断哪个要紧、谁负责修」仍是人的活——这恰是队列真正堵住的地方。单一案例

人工评审覆盖率确实在下降（89%→68%），机器覆盖率确实在反超（19%→84%），但人花在评审上的总时间没有减少：Harvard 口径 +49%，Faros 口径评审时长中位数 +441%，Sonar 口径自报「评审比写代码更耗时」的人从 18% 涨到 53%。所以更精确的说法是「人读的对象变了」，而不是「人不读了」。任何只引用覆盖率下降、不引用评审时长上升的叙述，都是选择性举证。

04主框架：七道闸门的分层流水线

把散落在各家文档里的做法对齐之后，主流实践收敛出的形状相当一致。差别不在「要不要评审」，而在人被测到哪一层、哪几道关卡是机器说服不了的。

一个容易被忽略的顺序

GitHub 的 10 分钟人工检查顺序是：分类扫描（1—2 分钟）→ 查 CI / 覆盖率改动（2—3 分钟）→ 找重复工具（3—5 分钟）→ 追一条关键路径（5—8 分钟）→ 安全边界（8—9 分钟）→ 索要证据（9—10 分钟）。这个顺序是有承重结构的：最便宜的硬阻断放最前，最贵的「要证据」放最后，因为前者能直接在 3 分钟内否掉整个 PR。把它倒过来做，人时预算会被最耗时的步骤吃光。

05生成侧：把「自证」做成产品本身

2026 年编码智能体最显著的变化，不是写得更长，而是验证闭环被前置进产品。各家做法略有差异，但骨架一致：给智能体一个能反复自检的环境，把「跑过什么、输出是什么」作为交付物的一部分。

OpenAI Codex

在隔离的云端容器里，按仓库的 AGENTS.md 跑测试、lint 与类型检查，失败则迭代到通过。规则文件承担「项目里什么算做完」的定义，而不是靠提示词里的一句话。

GitHub Copilot coding agent

在临时的 GitHub Actions 环境里自动跑测试、CodeQL 与密钥扫描；失败时先自行修复再标 ready，把「开 PR」这个动作推到绿灯之后。

Cursor 云智能体

在带浏览器的 VM 里工作，产出截图、录屏与日志，让界面类改动有可复核的视觉证据，而不只是「我改了组件」。

Claude Code

用 stop hooks 与子智能体拼装同样的闭环：停止前必须过检查、用全新上下文复审 diff；CLAUDE.md 记录项目约定，REVIEW.md 写清评审范围与证据要求。

5.1 验收记录的最低标准

Anthropic 的官方要求值得原样抄进团队规范：智能体必须展示它执行过的命令和输出；回复一句「测试全部通过」不算数。把这句话展开成三问，就是发起智能体的人在批准前必须拿到的答案：

  1. 怎么验证的？跑了哪些检查、结果是什么、哪些情况没有覆盖。缺了「未覆盖项」，验证记录就不完整。
  2. 会影响哪里？涉及哪些用户、数据与权限。给汇报工具加一个共享链接，就要问清链接谁能打开、打开能看到什么。
  3. 出错怎么撤回？能否一键关掉新功能、退回上一版。动手前先有存档，改动尽量小；先能撤回，再谈少审。

与之配套的两条硬习惯：一是换个脑子复审——写代码的会话最容易对自己的 bug 视而不见，开新会话或派子智能体用全新上下文看；二是三轮不过就换思路——智能体改了三轮还在原地打转，别催第四轮，先问方案本身是不是错了。Anthropic 把后者写进了规则，直接带来一轮通过率 65%→78%、平均轮数 2.08→1.32 的改善。

5.2 规则文件是制度，不是提示词

三个文件承担不同职责，混在一起写会让规则失效：CLAUDE.md 管项目约定（目录、命名、依赖策略），AGENTS.md 管智能体在什么环境里怎么自检，REVIEW.md 由 code owner 写，规定评审器重点查什么、哪些可以跳过、每条 finding 必须给文件行号作证据。Anthropic 有条很实用的经验法则：同一条意见被提到第三遍，就该写进规则；反复出现的问题要变成下一次自动检查的依据。

生成侧最常见的自欺

把「智能体自己说测试过了」当成闸门 2 通过。这与没有闸门 2 等价。可复核的判据只有一个：检查命令与输出是否在 PR 里可见、且由独立环境产生。若测试与实现出自同一个会话，绿灯只能算主张，见第 07 章。

06评审侧：独立性、异构性与投票

评审侧要解决两件事：别继承作者的推理，和别把同一个模型的四份副本当成冗余。前者靠上下文隔离，后者靠刻意选择不同性格的评审器。

6.1 独立性：全新上下文是第一原则

写完代码后，由一个没有参与写作、不继承作者自我辩护的子智能体复审 diff，这是各家官方流程的第一步。原因很朴素：同一个会话里，模型既知道「我为什么这么写」，也倾向于维护这个决定；换成全新上下文，它只看得见改动本身，挑刺的能力才恢复。本地可用的等价动作是 /code-review 与 /security-review，或干脆另开一个会话。

6.2 异构性：146 个真实 PR 的实验

Addy 在原文里引了一个非厂商实验：把四个 AI 评审器并行跑在 146 个真实 PR 上，共 679 条发现。617 个被标记位置中，93.4% 只被四个工具中的一个发现；没有任何一个位置被四个同时发现；四个工具从未标记过同一行。各自的强项也不重合：Greptile 在正确性与架构上近乎零误报，CodeRabbit 网撒得最宽且能一键修，Seer 最擅长判断生产故障严重度。

Four copies of one model is a single reviewer with a larger invoice.（同一个模型的四份副本，只是一个带着更大发票的单一评审器。）

Addy Osmani, 《Agentic Code Review》, 2026-06-15

他给出的操作建议很克制：不要纠结「哪个工具最好」，因为不存在；高风险场景跑两个性格刻意不同的（原文配对是 Greptile 管日常正确性 + Seer 管生产故障严重度，重叠极小）；独立开发者一个好评审器加真测试就够；无论营销怎么说，都要在自己的代码库上量一遍，因为这些结果全都绑定在特定代码库上。单一案例

这条证据的强度要标清

146 个 PR 的实验是单一案例，且是工具评测而非受控实验；「93.4%」的分母是被标记位置而非「真实缺陷」，其中可能含误报。它能支撑的论断是「不同评审器的检出集合几乎不重叠」，不能支撑「因此四个评审器能捕获 93.4% 的缺陷」——后者是把并集大小偷换成了召回率。

6.3 投票与证据包：把误报挡在 PR 之外

Anthropic 的做法是两段式：几个智能体并行找 bug，另一组 verifier 智能体对每条 finding 投票，票数够了才贴到 PR；纯风格、诊断提示、清理类意见直接过滤；留下的标成 Important / Nit / Pre-existing 三类，其中 Pre-existing 专治「把既有代码的问题算到本次作者头上」——他们吃过亏，一个失控 PR 里 59% 的评论都是在挑老代码。Addy 引述的数字是「Anthropic 的 finding 中不到 1% 被标为错误」，但该数字来自厂商侧，厂商披露，且未给误报率的完整定义。

证据包的最低要求有两条，都是为了让人类在几秒钟内能复核：

  • 每条 finding 必须给文件与行号。没有位置的意见无法被验证，也无法沉淀成规则。
  • 要求一个「在改动前会失败」的测试。GitHub 的原话是：如果智能体写不出那个本该抓到这个 bug 的测试，说明修复不完整，或者理解本身就是错的。这条同时检验了「是否真懂缺陷」与「是否把契约钉住」。

6.4 Loop engineering：reviewer 是被设计出内环的下一个角色

把视角拉高一层会看到更彻底的动向：loop engineering 的前提是「你不再是那个提示智能体的人，而是搭一个会提示它的系统」，系统的核心组件之一是 judge——由智能体判定「这件事做完了没有」再决定是否前进。Ralph loop 与 spec-driven 里的验收判定都属于这一类。用 Addy 的话说，我们花了一年自动化写作，现在循环开始自动化检查，人被持续往上、往外推。

但他给了一个明确的边界：当 A 写代码、B 评审、C 判定完成，你得到的是一个模型组成的闭环，盲点大致相关，尤其在同族模型之间。一句没有任何人在场的自信「looks good」是 borrowed confidence：系统很确定，也可能很错，而没有剩下的人能分辨。所以人的位置不是消失，而是上移一级——去 ownership（凌晨三点你没法 page 一个模型）、去「这到底是不是该做的改动」、去高爆炸半径的闸门，以及去那个最尴尬的缺口：没人写下来的需求，因为模型评审的是存在的代码，很少会指出一个没人想起要写的要求。

Addy 自己的落地方式

他把自己的开源项目上一批 PR 交给 Claude Code 或 Codex 做首轮通读，问三件事：哪些看起来可以安全合并、哪些还要再改、哪些真的高风险；几分钟确认低风险项，把整块深度时间留给被标危险的。但不自动合并，也不「懒合并」它批准的东西——这套流程给的只是「如何分配注意力」，merge 决定始终归自己。这正是 human on the loop 与 human out of the loop 的分界线。

07确定性门禁：CI gaming 与测试独立性

这一章是整个流水线里唯一「不可被说服」的部分。前面六道都可能有误报、可能被绕过，只有硬门禁没有商量余地。

7.1 GitHub 的五类 CI gaming 红旗

智能体跑 CI 失败时，有一条比修 bug 容易得多的路：把测试弄过去。GitHub 官方把这类行为列为智能体 PR 的第一红旗，并给出批准前必查的五项：

检查项典型手法为什么致命
覆盖率阈值是否变了调低阈值、排除新文件让「绿灯」这个信号本身失真，后面所有闸门建立在假地基上
测试是否被删 / 改名 / 标 skip删失败用例、加 skip 标记缺陷没修，只是观测点被移除
workflow 是否还跑在 fork / PR 上给触发条件加限制门禁在特定路径上根本没执行
CI 步骤是否被塞进新条件加 if 判断、挪到手动触发表面上 workflow 文件还在，实际已空转
命令是否被弱化加 || true、吞掉退出码任何失败都不再阻断合并

结论在权限层，不在检查层：.github/workflows/、测试配置、覆盖率设置、构建脚本必须对编码智能体只读。GitHub 的建议顺序是「在读任何一行应用代码之前，先看这些文件」——因为它是最便宜的硬阻断，两三分钟就能否掉整个 PR。

7.2 读测试 diff 要比读实现更仔细

Addy 点出的最典型智能体失败不是写出错代码，而是改坏了行为之后，顺手把断言改成匹配坏行为。此时实现、测试、CI 三者完全一致，全部绿灯，只有外部契约是错的。所以在智能体 PR 里，测试是主张的一部分而不是证据：评审者应先读测试改动，把任何「删断言、放宽容差、跳过用例、扩大匹配范围」当成全篇最高信号的行。

更彻底的解法来自独立性要求（见 2.3）：测试与实现不能同源。可用的独立 oracle 包括 spec 里的验收条件、参考实现、历史黄金用例、属性测试与 mutation testing，或至少由不同上下文的独立实例生成并交叉复核。《The Code Nobody Reads》里把这条类比到航空 DO-178C 与 SQLite 的实践——验证源必须与被验证对象分离，否则就是 reward hacking。

7.3 门禁层检查清单

  • CI 配置与覆盖率阈值设为只读，任何改动走独立的人工审批通道，且不与功能 PR 混在一起。
  • 要求一个在改动前会失败的测试；写不出来，就说明修复不完整或理解错误，退回而不是补注释。
  • 测试由独立来源产生，至少能做到「生成实现的会话不写断言」。
  • 未关闭的 finding 阻断合并：代码评审或安全评审留下的发现，要么修掉，要么写明理由关闭。
  • 批准绑定具体 commit，改动后批准自动失效，避免「审过的是 A，合进去的是 B」。
  • 合并队列对最新 main 重跑全部检查，专门抓「各自没问题、合起来出问题」的组合缺陷。
  • 把反复出现的问题转成下一次检查：同一类问题提到第三遍就写进规则或 linter，不要靠评审者记忆。

最常见的一处配置错误

为了让智能体「自己修好 CI」，把 workflow 目录一并给了写权限。这在短期内会显著提高绿灯率，同时永久性地摧毁绿灯的信息量。GitHub 的原话是：任何削弱 CI 的改动都是 blocker，没有例外（Full stop）。

08风险分级：0 / 1 / 2 人批准与人时预算

这里回答「看多少」最实际的部分：不是给一个百分比，而是先把变更分类，再决定配几道检查、几个人。

8.1 三个变量决定「看多少」

Addy 给的框架比「按文件重要性」更可操作，因为它同时约束了后果、时间与人数：

爆炸半径

错了会怎样：什么都不会发生，还是愤怒的用户、金钱和 PII 一起上线。支付、鉴权、删除数据、公开 API 契约永远在高档。

代码寿命

下周就重写的脚本，还是要维护好几年的承重系统。寿命越长，一处重复 helper 越不是风格问题，而是逐年复利的 bug 面。

需要理解它的人数

只有你自己，还是一整个共享所有权的团队。人数越多，「没人真正理解过」的代价越会在交接与 on-call 时兑现。

把三变量带进真实场景，答案会大幅移动：独立开发、没有用户——依赖真测试，只细读要紧处；但原文特别提醒「没有用户买到的是推迟评审的权利，不是跳过验证的权利」。刚有用户的危险中段——bug 开始伤人、知识共享重新重要，团队却往往把 solo 时代的习惯多留几个月，然后写一份 postmortem。大组织、老代码、多用户——三个变量全部拉满，在支付系统上跑「测试通过就发」等于造了一台顶着绿色对勾的事故生成器。反过来，给两人原型套上企业级流水线，只是白白加了摩擦。

8.2 人时是预算，回滚率是护栏

Anthropic 把目标写成一句很克制的话：在不抬高回滚率与事故率的前提下，把人工评审时间降到最低；这两个数字是护栏——如果它们上升，说明人时只是被搬到了别处，并没有省下。可度量的三项是：每 PR 的人工批准数、人工评论数、等待人的时间；目标是多数 PR 最多 1 人在环，且这个人可以是作者本人。

同时必须保留配套的问责链：指挥 AI 写代码的人本身就算一名审查者，承担与自己敲代码相同的责任；零人批准不等于无人负责，人仍要决定「这个功能该不该存在」「架构是否合理」「现有检查能否覆盖这次风险」；批准前要能说清检查验证了什么、哪些风险未覆盖，说不清就先补审查。团队那条规矩很直白：你合进去的代码出了问题，通常由你来修。

8.3 快速撤销与把事故变成考题

减少事前阅读的前提是事后的撤销足够便宜：合并后新功能先藏在 feature flag 后只对内部员工开放（重度内部使用往往比外部用户更早撞上问题）；latest 通道先于 stable；flag 是总闸，拉闸不需要改代码、不需要重新发版。每周 on-call 轮值，每次事故复盘只追问一件事——这本该在哪一关被拦住。

最值得抄的一条是他们的 eval 闭环：把出过事的 PR 收集起来，由熟悉代码的工程师逐条确认其中的 bug，整理成一套考题；评审器每天对着这套题跑分，任何提示词、工具或模型的调整，只有分数提高才保留。这把「评审质量」从主观感受变成了可回归的测试。

官方自己承认的缺口

按回滚率等指标自动收紧审批的熔断机制还没建好；发现坏合并目前仍依赖作者与值班人员看数据看板。工程师们希望先补上这道保险，再让更多改动走零人审批。任何照抄「低风险零人批」却没抄这道保险与回滚速度的方案，都缺了最关键的一块。

09意图上游化：spec、决策日志与理解债

评审真正被自动化拿走的，不只是「读 diff 找 bug」这个动作。要理解损失有多大，得先看传统评审到底在做什么。

9.1 只有 14% 的评审评论涉及缺陷

微软的经典研究被 Addy 反复引用：仅约 14% 的 code review 评论与缺陷有关。其余大部分是共享理解、mentoring、团队规范、上下文传递——换句话说，评审是一个组织的知识复制机制，找 bug 只是它的副产品。当机器接手第一遍阅读，副产品会静默消失：没人再因为看过这份改动而在三个月后的 on-call 里想起「这里有个隐含假设」。

这份损失不会立刻体现在回滚率上，因此极容易被「回滚率没变差」的证据掩盖。它以理解债的形式，在交接、事故定位、架构改动时连本带利偿还。《The Code Nobody Reads》里那句被 AI Slop 讨论串反复引用的自白——「我是第一个亲眼看到这段代码的人」——说的不是代码质量，而是意图已经无处可查：讨论串 / 定性（arXiv:2604.16754，1,154 条讨论；属定性材料，不作量化证据）。

9.2 spec-driven：把人挪到上游

主流回应是把评审对象前移：人评规格与计划，智能体评实现。GitHub Spec Kit 把它固化成 /specify → /plan → /tasks → /implement 的四步；AWS Kiro、OpenSpec 走同一路线；Ralph loop 与 judge 智能体则把「是否做完」的判定也自动化。这样人读的是一份几百字的意图说明，而不是几千行的 diff，且读的时间点在错误最便宜的时候。

与之配套的是决策日志：智能体的 prompt session 一旦结束，「为什么」就消失了。发起者应在会话还活着时把它写进 PR——要求了什么、智能体选了哪个方案、否掉了哪些方案、什么没测、已知缺口是什么。这不是文档洁癖，而是唯一能把缺失上下文补回来的地方；GitHub 的智能体 PR 指南把「PR 描述不完整」列为分类扫描阶段的第一检查项，原因就在这里。

9.3 显式补偿清单

  • spec 与验收条件由人写、由人评，智能体只负责在给定规格下实现并自证。
  • PR 决策日志必填四栏：要解决的问题、选择的方案与被否方案、验证范围与未覆盖项、回滚方式。
  • 把反复出现的评审意见沉淀成 skills / 文档 / linter，让团队规范从「被看见」变成「被执行」。
  • 事故与回滚进 eval set，评审器每天跑分，让组织记忆变成可回归的资产（见 8.3）。
  • 保留结构化的知识传递：定向 pairing、架构评审会、关键路径讲解，替代被自动化拿走的 mentoring。
  • 维持一定比例的手写实践：Addy 把它称作「监督悖论」——长期完全不写代码，会侵蚀判断智能体输出是否合理的那种能力。

为什么这一章不能省

第 03 章里「合并率与回滚率未变差」是真实的，但它测的是短期质量。理解债的偿还是在半年后的事故复盘里，而那时候没人会把原因追溯到「半年前我们取消了一次评审」。所以判断一套智能体评审流程是否健康，除了回滚率，还要看事故根因确认耗时、跨模块改动的返工率、以及新人能否独立解释关键路径。

10度量体系：把「人时」当预算，把回滚率当护栏

一旦生成变便宜，所有以「产出数量」为分子的指标都会自动变好看。度量体系必须先解决这个 Goodhart 问题，否则整套流程会被自己奖励坏。

10.1 三层指标，各司其职

层指标怎么用 / 不能怎么用
活动量
诊断用		代码行数、PR 数、commit 数、AI 建议采纳率只用来看队列的到达率 λ。绝不能当产能 KPI——智能体开一个 PR 的边际成本几乎为零，这个数字现在衡量的是「多少未验证材料被丢进评审队列」，把成本记成了收益

优化对象		每 PR 人工批准数、人工评论数、等待人的时间（pickup）、评审轮数、PR 尺寸分位数这是要被最小化的「人时预算」。按贡献类型分桶（agentic / AI-assisted / unassisted），混成一个平均数会同时掩盖所有权问题与评审深度问题；用 P75 与最慢 10%，平均数会藏住队尾

10.2 反 Goodhart：一个真实的判读陷阱

Faros 的 2026 遥测给出一个近乎教科书级的例子：人均完成任务 +33.7%、完成 epic +66.2%，看着像组织级收益终于出现；但同期 PR 合并只 +16.2%，远低于上一年的 +98%，而且那些 epic 完成变多的团队，恰恰是 PR 增长明显放缓的团队。一个拿 PR 数当产能的管理者，会得出「2026 比 2025 差」的完全相反的结论。厂商遥测

LinearB 的自报调查还揭示了度量本身的缺位：44.7% 的组织并不正式度量 AI 的影响，却有 76.1% 的领导者依据采纳信号（而非交付数据）报告生产率提升。自报调查 这两条合起来就是一条决策规则：

给团队的一条可复跑判定式

取智能体铺开前两个季度与之后两个季度，分别算 完成的 epic / 合并的 PR，旁边并排放 评审等待时间中位数 与 每 PR 事故数。若 epics per PR 下降而评审耗时上升，你的智能体预算正在购买资深工程师的阅读时间，此时该做的是提高 intake 门槛与降低验证成本，而不是再买一批 seat。

同理，报告里所有「+441%」「+861%」这类幅度都只用于指示方向：不同报告期、不同分位数、不同团队口径之间不能直接比较。真正能跨组织复跑的是你自己仓库里的这三项。

11落地：成熟度阶梯、90 天路线与反模式

前面十一章的结论收敛成一张阶梯与一条路线。注意阶梯不是「工具采购顺序」，而是信任机制的替换顺序：每一级都先补上一个可验证的替代物，才允许撤掉一层人工阅读。

11.1 四条最值得先抄的动作

  1. 按风险分层，而不是按作者分层。配置改动配 linter 加一眼；支付、鉴权、迁移、公开 API 契约上全套。分级依据写在配置里，由分类器按变更内容判定，不靠谁记得。
  2. 提高 intake 门槛。没有「目的说明 + 可读 diff + 真实测试输出 + 回滚方案」就不开审；先分诊，约四分之一的低风险项可以秒过，而大而无主的补丁不要投人时，直接退回拆小。
  3. CI 配置与覆盖率阈值设成不可修改的硬阻断。这是所有后续自动化的地基，成本最低、收益最长。
  4. 把人时当预算度量，用回滚率 / 事故率做护栏。别拿合并 PR 数当产能；每 PR 人批准数、人工评论数、等人时间三项按周看趋势。

12.2 明确标注：以下是观点，不是共识

  • 「人上移到 loop 之上」是综合判断，不是行业共识。GitHub 的官方指南仍要求人做 10 分钟检查，部分维护者明确反对零人批准。
  • 「理解债会在 on-call 时偿还」是推论，由微软 14% 的结论与 AI Slop 的定性讨论外推而来，缺少 6 个月以上的纵向验证。
  • 「按风险拨旋钮」的外部验证不足：0 / 1 / 2 人批准的主要证据是 Anthropic 自家数据，且官方承认熔断机制尚未建好。
  • 「异构优于数量」只有单一 146 PR 实验支撑，且分母是被标记位置而非真实缺陷。
  • 图 7 的成熟度阶梯与图 8 的 90 天路线是综合建议，不是任何厂商的官方分级或实测排期。

最后回到原问题

人还看代码吗？还看，但看的是意图、风险、测试改动与证据包，不是每一行 diff。看多少？不再是全局百分比，而是按爆炸半径 / 代码寿命 / 共享人数拨的旋钮：实测人工覆盖 89%→68%，机器覆盖 19%→84%，而人花在评审上的总时间反而上升。主流智能体编码怎么做？不是取消评审，而是把评审重建成七道闸门的分层流水线，机器读前三遍，人在上游定意图、下游签风险，并把「人时」当预算、把回滚率当护栏。

还有一个不能省略的边界：Addy 那篇 9 月文章的标题叫《The Code Nobody Reads》，但它的结论不是「无人读代码也没关系」。它说的是——你可以不读每一行，但每一次上线都必须有人负责。少了后半句，前面所有的自动化都会变成 borrowed confidence。
