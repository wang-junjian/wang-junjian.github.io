01定位判定：它为什么不是反编译器

先把最容易误判的一点钉死，后面所有机制都建立在它之上。

第一次看到 REA 的能力清单，最自然的理解是"一个 AI 版的反编译器"。但这个理解会立刻导致一连串错误的预期：为什么装完它还是"什么都反不了"？为什么 doctor 退出码是 1？为什么 170 个工具里绝大多数在零引擎环境下用不了？

正确答案是：REA 是分析编排层（analysis orchestration layer），不是分析引擎。它把"产生分析知识"这件事整体外包给 provider，自己只做三件事——把请求路由到合适的 provider、把能力边界与限制声明清楚、把观测结果封成可复现的证据。

证据一：依赖审计——36 个运行时依赖，零引擎

这是最直接的判据。一个真正的反编译器必须依赖反编译算法；如果依赖树里一个都没有，它在结构上就不可能是反编译器。

证据二：官方架构图把"引擎"和"调度"分到不同层

仓库的 docs/architecture.mermaid 用 11 个 subgraph 描述了自己的构成。其中 src/server/ 的标注是 「MCP request translation」（MCP 请求转译），而所有引擎——Ghidra、Hopper、IDA、JEB、pwntools、EVM、Binwalk——都落在独立的 Provider Layers 里，并且各自的标注都在强调适配而非实现：

Provider Layers
├─ src/ghidra/   Ghidra discovery, profile & function analysis
│                snapshot, Unix/Windows transport, bounded lifecycle
├─ src/hopper/   Hopper launch & Unix-socket protocol
│                BridgeLauncher, HopperClient, protocol
├─ src/ida/      Upstream MCP contract adaptation

注意几个措辞：「adaptation」（适配）、「BYO」（bring your own）、「unchanged upstream」（上游未改动）。REA 在架构文档里明确承认这些能力不是它实现的：src/ida/ 是"上游 MCP 契约的适配"，pwntools/pwndbg 是"BYO 离线适配器，上游解析器/ABI 结构/映射 API 均未改动"。

判据

如果一个项目自认它的核心分析组件是"适配"和"未改动的上游"，那么它的原创性必然在别处。REA 的原创性在三处：provider 路由、能力边界声明、证据模型。后面 03—07 章就是逐个拆这三样。

证据三：实测报错自证了边界

最干脆的证据来自一次真实调用。用 REA 的"正规入口"分析一个 macOS 应用：

$ rea inspect /System/Applications/Stickies.app
error: provider_unavailable
  operation = current_document
  ghidra : not_configured
  ghidra : architecture_unsupported   ← v1 无法强制 universal Mach-O 的架构
  hopper : executable_missing
  ida    : not_configured

它没有尝试"降级用别的方式凑一个结果"，没有返回半个分析，也没有含糊地报"分析失败"。它做的是：列出所有候选 provider，逐个说明为什么用不了。这正是"编排层"的自证——当没有可用的执行者时，编排者唯一诚实的动作就是报告"没有执行者"。

反过来：它也不是"空壳"

把 REA 简化成"只是个包装层"同样是误判。零引擎环境下它依然能完成实质工作——18 项 target-free 操作中有 decode_interface_builder（解 nib）、inspect_keyed_archive（解 keyed archive）、inspect_plist、inspect_macho、list_architectures、demangle_swift、trace_dylib_resolution 等。这些不是"包装"，是它自己实现的静态解析能力（src/domain/apple/interfaceBuilderGraph.ts、src/domain/artifactGraph.ts 等）。

所以准确的定位是：REA = 自研的静态产物分析内核 + 对第三方引擎的统一编排 + 一套证据契约。三者权重随你安装了什么而变。

它不是

  • 不是反编译器——依赖树里零引擎，核心能力靠外部 provider
  • 不是分析算法库——不实现反汇编/反编译/符号恢复算法
  • 不是规则引擎 / 特征库——没有静态规则集，判定来自证据而非模式匹配
  • 不是一次性脚本集合——有会话、身份、账本、缓存等状态设施

它是

  • 是调度层——把请求按 target 与 operation 路由到唯一合适的 provider
  • 是约束层——每项能力都声明自己的可见限制（exact visible limits）
  • 是存档层——把观测封成带稳定 ID 与 authority 的可复现证据
  • 是编排层——把多个 provider 的产出组织成可评估的完整调查

02分层架构：依赖为什么必须向内流动

官方架构图给出 11 个层次。理解层间依赖方向，才能理解为什么"换个引擎"不会牵动其他部分。

仓库的 docs/architecture.mermaid 是理解 REA 结构最好的入口。它把系统切成 11 个 subgraph，并且给出了层间连线。把连线关系提炼出来，依赖方向非常干净：

DISPATCH (scripts/rea.mjs)  →  CLI (src/cli.ts)  |  MAIN (src/main.ts)
MAIN  →  CONFIG  |  SERVER  |  APP
CLI   →  APP
MAIN  →  COMPOSITION     CLI → COMPOSITION     SERVER → COMPOSITION

关键点在于 Composition 层被三个入口同时依赖，而 Composition 自己不依赖任何入口。这是典型的依赖倒置：入口层薄，装配层重，能力层（provider）只被装配层引用。

三件关键装置

官方架构图在应用层单独点名了三个装置。它们是理解 REA 运行时行为的钥匙：

SessionProviderRouter
+ BinarySession
每个目标一个不可变深绑定。一旦选定 provider 处理某个二进制目标，整条会话链路都绑定在它上面，中途不切换。标注还提到「disjoint auxiliary routing」——辅助能力（如符号 demangle）走独立的、不相交的路由，不污染主绑定。
AnalysisProviderRegistry
排序的深候选 + 确定性选择、无回退。候选按序排列，选中即定，不因失败而模糊降级。这就是 provider_unavailable 里那份"逐条列出为什么用不了"的候选清单的来源。
EvidenceLedger
+ Unknown ownership
证据账本 + 未知归属。仓库里有 EvidenceLedger.residualUnknown.test.ts——"残留未知"是被单独测试的一等概念，而不是遗漏。这与第 07 章的失败哲学直接相关。

第 05 段为什么值得单独说

把 run_id 的分配放在 provider 启动之前，是一个很小的实现决策，但它决定了三件事：① 失败的归因粒度——是"这次 run 没成"而不是"进程挂了"；② 重放能力——有了稳定 run 标识，同一次调查才可以被确定性重放；③ 所有权审计——process_lineage 的每条观测挂在 run 上，进程泄漏才有归属可查。

配套的是第 07 段的 verified / unavailable 二态：它不把"没能验证所有权"当成"没有所有权"，而是标成 unavailable 并说明原因。这与第 09 章的 fail-closed 是同一种价值观。

一个反向证据：目录是不变的

契约文档里有一条容易被读漏、但很能说明问题：

tools/list returns the complete canonical tool inventory,
including tools that are currently unavailable.

Opening or closing a target or observing a provider health
transition leaves that catalog unchanged and does not emit
notifications/tools/list_changed.

也就是说：打开一个引擎、或引擎从故障中恢复，都不会让工具目录发生变化。目录是"规范全量"，不是"当前可用集"。这与很多工具"动态注册能力"的做法正好相反。

这个选择的代价是：调用方必须在每次调用前用 binary_session 查当前可调用集，不能靠目录推断。收益是：宿主（以及模型上下文）里的工具定义永远稳定——不会因为某个引擎的启动或崩溃而让上下文里的一大块 schema 失效重算。

这就是为什么"170 个工具"和"18 项可用"可以同时成立

实测 tools/list 返回 170 个工具（170/170 带完整 inputSchema），而 rea capabilities --json 在零引擎环境下只承认 18 项可用。这两个数字并不矛盾——前者是规范目录（不随环境变），后者是当前路由的可用集（随 host、target、provider、客户端能力变）。契约文档把这两者的关系写得很直白：判断工具是否真的可用，应当以 binary_session 的 tool_availability 为准，tools/list 只负责提供完整定义。

04Provider 模型：确定性与不可替换性

"确定性选择、无回退"听着像一句广告语，但它有精确的字段级语义。这一章把它拆开。

REA 的 provider 不是插件式的"多路尝试"。它是一套带类型的选择协议——候选、绑定、选择来源、歧义，各自是不同字段，语义不可互换。契约文档对此有明文规定。

三类 provider

13 个 provider 按"能力从哪来"可以归为三类。这个分类决定了它们在零引擎环境下的命运：

自研静态解析

src/artifacts/ src/dotnet/ src/javascript/ src/android/ src/inspector/ src/domain/apple/

零外部依赖。nib 图解析、keyed archive、plist、Mach-O 头部、.NET 元数据、APK 资源、sourceMap 解码，都是 REA 自己实现的解析器。这是它在零引擎环境下仍能做实质工作的原因。

外部引擎适配

src/ghidra/ src/hopper/ src/ida/ src/jeb/ src/native/ src/firmware/

BYO（自带）。REA 提供启动、协议、快照、生命周期管理，引擎本体由用户自备。Ghidra 走打包的 HeadlessScript（ReaGhidraBridge.java），Hopper 走进程 + Unix socket 协议（hopper_bridge.py）。

运行时观测

src/browser/ src/inspector/ src/process/

需要真实运行时。CDP/Playwright 驱动浏览器；V8 Inspector 被动捕获脚本与目标位置；进程捕获记录真实执行。这类 provider 产出的是"动态证据"，与静态证据在 authority 上不等价。

选择协议的精确语义

契约文档对 binary_session 的几个字段做了明确的区分，这几条合起来就是"确定性"的完整定义：

analysis_provider_candidates
深度引擎发现的权威来源。每个候选的能力集描述"这个可能的 provider 能做什么"——它们不构成选择。这是一个纯粹的发现结果，不产生副作用（不创建 analysis client）。
capabilities
（顶层）
描述当前路由。即"现在这条会话走的是谁"。
analysis_provider_binding
标识具体选定的路由——一个不可变的 provider、具体版本、选择来源、完整分析画像。契约原文特别强调这几个字段不可互换（not interchangeable）。
open_binary.provider_id
接受具体 provider ID 或 auto；使用与 CLI --provider 和 REA_ANALYSIS_PROVIDER 同一套解析与选择策略。这是 CLI/MCP 能力等价的一个具体证据。
歧义与失败
歧义、未知、不可用、不支持的选择各自返回带类型的 selection details——不兜底、不猜。
不可替换性
"A selected provider is never replaced automatically after a runtime failure." 选定之后，即使运行时失败，也不会自动换一个 provider 顶上。

实测：失败出口长什么样

对 Stickies.app 调 rea inspect，命中的是中间那条出口。它的输出结构值得逐行读：

error: provider_unavailable
  operation = current_document      ← 失败的是哪个"操作"，不是哪个"工具"
  ghidra : not_configured           ← 候选 1：装了没配
  ghidra : architecture_unsupported ← 候选 1 的第二个卡点
  hopper : executable_missing       ← 候选 2：可执行文件不在
  ida    : not_configured           ← 候选 3：未配置
  (jeb 甚至没进入候选)

三点值得注意：

  • 按"操作"失败，不按"工具"失败。报的是 operation = current_document。这与架构图里"operation"是路由的一等公民一致——工具只是 operation 的对外投影。
  • 同一候选可以有多个卡点。ghidra 出现了两次：既未配置，又架构不支持。architecture_unsupported 这一条特别有信息量——它说明这类检查带有目标侧约束，不只是"环境里有没有"。
  • 没有进入候选的引擎不会出现。jeb 不在清单里，说明候选集本身也是过滤后的结果，而不是"所有已知引擎都列一遍"。

这条实测推翻了我先前的一个判断

我在复刻规划里写过"接 Ghidra 只需设 GHIDRA_INSTALL_DIR"。实测不成立。Stickies.app 是 x86_64 + arm64e 的 universal Mach-O，而这里明确报 architecture_unsupported——装了 Ghidra 之后还得先把二进制 thin 成单架构，才能进入分析。我把这条列进第 11 章的更正清单。

第二套可用性：目标准入

上表里有一项 inspect_asset_catalog。它在能力目录里是绿的。但真拿一个 Assets.car 去调用时：

$ rea inspect-asset-catalog .../Stickies.app/Contents/Resources/Assets.car
error: target_unavailable
  reason: unsupported binary format

这不是 bug，也不是配置问题。它是两套独立机制在各自如实表态：

第一套：操作级可用性

回答"这个操作在这个 host 上能不能被调用"。取决于：是否装了所需引擎、客户端是否提供所需能力、操作是否处于默认启用的 mode。

查询方式：binary_session.tool_availability 或 rea capabilities。

第二套：目标准入

回答"这个具体输入能不能被这个操作读"。取决于：文件格式、架构、版本、是否加密、是否被截断。

失败形态：target_unavailable + 具体原因（如 unsupported binary format）。

这条区分为什么值得单独讲

多数工具把这两种失败混成一个"运行出错"。混同的代价是无法区分"我缺个东西"和"这个文件我读不了"——前者你可以去装，后者你只能换方法。REA 把它们分开之后，第 09 章的义务台账才可能做到"给不出结果时明确告诉你缺什么、下一步该采什么证据"（required_next_evidence 字段）。

顺带纠正我自己先前的判断：我在复刻规划的自我批评里写过"Assets.car 是完全跳过的遗漏"。实测证明这是工具边界，不是我的疏漏——REA 自己也打不开这个文件。我已把这条列进第 11 章的更正清单。

三个状态，而不是两个

从 binary_session 与 rea doctor 的字段设计可以看出，REA 的可用性是三态的：

状态含义典型触发调用方该做什么
available可以调用所需条件全部满足直接调用
unavailable不可用，且原因已知not_configured / executable_missing / architecture_unsupported按 remediation 字段处置，或换操作
unknown不可用，且原因未知未建立活动连接时 doctor 对实时服务器状态的判定先建连接再判断，不要假定为可用或不可用

第三态最容易被忽略，也最能说明这套设计的性格。契约文档里对 rea doctor 的原文是：它"keeps live-server state unknown unless the active connection supplies identity"——在没有活动连接提供身份之前，它宁可说"我不知道"，也不猜。

同样地，target-free 发现阶段会返回 unknown target support，而不是把"没试过"标成"不支持"。这是一个很克制、也很少见的默认值选择。

06产物图：一张图管住所有目标类型

nib、JavaScript 应用、.NET 程序集、Mach-O、APK——它们的分析结果落在同一个数据结构里。这是 REA 能"一套工具面覆盖多种目标"的结构前提。

nib 解码的 limitations 里明确写着：不含像素几何。我实测确认了这一点——遍历全部 780 个节点的 attributes，frame / bounds / width / height / autoresizing 等几何键命中为零。

07证据模型：五元口径与稳定标识

这是 REA 最可移植的一层，也是它和"跑个脚本输出一段文字"之间最本质的区别。

实测 rea inspect-artifact 的输出是一份 426 KB 的 JSON，其顶层结构给出了 REA 对"一次调查"的定义：

实测的标识长什么样

evidence_id    = ev_68273f72…

三个细节：

  • ID 带类型前缀。ev_ 是证据、ai_ 是 inspection。前缀让 ID 在日志和引用中自带语义，不需要额外查表。
  • inspection_id 是 64 位十六进制——长度暗示它是内容摘要而非自增序号。配合目录摘要 catalog_digest，一次调查可以被完整锚定。
  • next_probes 带 authority。它不只是说"建议下一步做什么"，还说"这一步的证据权威性属于哪一级"。

authority 是什么，为什么它重要

从契约文档能确认 authority 至少有三个取值：process、packaged-process、ast-static-analysis。它的作用在第 09 章的复刻台账里说得最清楚：

一个必需义务只有在"验证者的权威性与原始观测相当"（a passing verifier whose authority is comparable to the original observation）时才能闭合。

换句话说：你不能用一个静态分析的结论，去证明一个只有真实运行时才能确立的事实。这条规则把"证据强度"从一句定性描述，变成了机器可校验的字段约束。

这一层为什么是可移植资产

换掉引擎、换掉目标类型、换掉客户端——这套口径都不用改。观测/假设/矛盾/未探索/下一步这五个桶，对 nib 成立，对 JavaScript 应用成立，对 .NET 程序集也成立。所以 REA 的真正沉淀不是"支持了 13 种目标"，而是"把这 13 种目标的分析输出，约束到同一套可评估、可比较、可复现的形态上"。

这也是它和"一堆分析脚本"的分水岭：脚本产出结论，REA 产出可被第三方复核的记录。

一条很讲成本意识的工程约束

契约文档里有这么一条，值得单独摘出来：

Hosts forward input schemas to the model with every request,
so advertised examples never copy complete producer Evidence.
An embedded Evidence record is shown as its exact
{"kind":"retained-evidence","evidence_id":"ev_..."} reference.

因为宿主（IDE、CLI 客户端）会把工具定义连同示例随每一次请求发给模型，所以工具广告里的示例绝不复制完整的证据正文——只给一个引用指针。这是对 token 成本的正向设计：工具面的大小不能随证据体量膨胀。

配套的还有 REA_MCP_INPUT_SCHEMA_PROFILE=compact：某些函数调用型客户端对单个工具的 parameters schema 有字面序列化大小上限（文档记录了 Moonshot 系客户端如 kimi-cli 在默认目录下每个请求都会失败，社区实测 13.7 KB 被接受、约 15 KB 被拒绝）。compact profile 把每个输入 schema 压进 13,312 字节预算，而服务端仍按完整 schema 校验——所以按精简广告调用的调用方会收到类型化错误，而不是被静默接受。

这个取舍很有意思：宁可让不按规范调用的客户端收到明确报错，也不放宽真实校验。又是一次 fail-closed。

08双接口：同一内核的两个薄适配器

"你没激活 MCP 就等于没用上 REA"是一个自然但错误的推断。这一章用结构证据说明为什么。

本次实践里，mcp__rea__* 工具始终未出现（需要用户在连接器页手动信任）。但整个工作流照常跑通了——这说明 CLI 与 MCP 不是"主从"关系。官方架构图给出了结构上的解释：

DISPATCH  scripts/rea.mjs
  ├─→  CLI   src/cli.ts + src/cli/
  │         One-shot CLI adapter
  │         setup, diagnostics, analysis, decompilation
  └─→  MAIN  src/main.ts + src/main/
            MCP stdio server adapter
            config, session, process lifetime

CLI  →  APP          MAIN  →  APP
CLI  →  COMPOSITION  MAIN  →  COMPOSITION
SERVER (MCP 转译) →  COMPOSITION

两条路径汇合在同一个 src/application/ 与 src/composition/。scripts/rea.mjs 只是一个 dispatcher（文档原话：Executable dispatcher，routes mcp / one-shot）。所以适配层是薄的，内核是共享的。

能力等价的三个结构证据

共享组合层
CLI 与 MCP server 同时依赖 src/composition/——provider 与 session 工厂是共享的，不存在"某条路径少一个 provider"的可能。
共享选择策略
open_binary.provider_id、CLI --provider、环境变量 REA_ANALYSIS_PROVIDER 使用同一套解析与选择策略（契约原文：it uses the same parser and selection policy as CLI）。
共享目录身份
CLI 的 capabilities 与 providers 返回与 MCP server_identity.catalog 相同的目录身份摘要。两边的"自我描述"是同一份。

实测：MCP 通道确实在工作

虽然会话里没有 mcp__rea__* 工具，但 MCP 服务器本身是通的。用事件驱动的 stdio 探针实测：

→ initialize (protocolVersion 2024-11-05)
← serverInfo {"name":"rea","version":"6.4.0"}
→ notifications/initialized
→ tools/list
← 170 个工具，170/170 带完整 inputSchema

同时实测出一个对使用者有实际影响的特性：冷启动成本高。首次 tools/list 需要加载全部 170 个工具的 schema，用固定延时等待的探针连续三次超时（最长等到 260 秒）。换成事件驱动——一收到 initialize 响应就立刻发 tools/list，而不是靠定时——才稳定取回结果。

实践提示

如果你要写程序直接和 REA 的 MCP 通道对话，不要用固定 sleep 等待就绪。JSON-RPC 是应答式的，按响应推进即可。另外：若用 Node 脚本收尾，process.exit() 会截断尚未刷盘的异步 stdout——本次实践中两次"结果为空"都是这个原因，改用同步写（fs.writeSync）才拿到完整输出。

数量不对称不等于能力不对称

实测中，CLI 侧用正则从 rea --help 提取到 129 个子命令，MCP 侧 tools/list 返回 170 个工具。两者数量不等，原因在于暴露粒度不同——同一个底层 operation 可能按 surface（CLI / MCP）、按 mode、或按客户端能力差异，投影成不同数量的对外条目。

契约文档对这种粒度有一套明确的展开规则（tool_availability.groups[].names 逐条展开，携带 surface、availability、reason、remediation、default-mode 状态、modes 与 client 需求），并给了一条校验建议：把各组的名字取并集，与 tools/list 比对，即可验证客户端是否收到了完整目录。它还补了一句关键的：某操作若不出现在任何组里，就意味着它从完整清单中缺失——而不是"隐式地不可用"。

义务台账：闭合条件

义务台账（obligation ledger）的核心机制可以概括成一句话：把"应该复刻什么"变成带闭合条件的条目，然后逐条判定它闭没闭合。

一条必需的复刻义务只有在同时满足以下全部条件时才能闭合：

  1. 一个 manifest binding 提供了唯一的实现方（unique owner）；
  2. 提供了所有必需的 parser / schema / domain 类型；
  3. 提供了每一个必需的用例 fixture；
  4. 有一个通过的验证器，且该验证器的 authority 与原始观测相当；
  5. 该验证器枚举了这条义务的 ID；
  6. 验证结果存在于输入证据包中。

而下列任何一条都会让闭合保持 open 或转为 failed：矛盾、重复的定义或实现方、残留未知、缺失依赖、权威不可用。

义务条目的字段设计本身就是一份方法论：

obligation_id
obligation_version
稳定 ID + 版本号。文档原文："稳定 ID 与版本让改动可复核"。
application_layer
family
义务落在哪一层（如 cli）、属于哪个族（如 argument-parsing）。
target
四选一定位：artifact_sha256 / application_node_id / semantic_node_id / location。既能锚到字节，也能锚到语义节点。
required_case_kinds
必需用例类型。文档示例里是 ["positive","negative","malformed"]——正常路径、拒绝路径、畸形输入三者都要有。
required_original_authority
required_fixture_authority
required_verifier_authority
三级权威要求。示例值：process / packaged-process / packaged-process。这是"不能拿静态结论证明运行时事实"的落地形态。
residual_unknown_ids
unavailable_authority
残留未知与不可用权威必须显式列在义务上，不能省略。
required_next_evidence
明确的下一步取证动作。示例："Capture the installed CLI for all three cases."
review_evidence_ids
支持这条义务的评审记录（ev_…）。义务本身也必须有证据支撑。

最关键的一条：空输入不声称闭合

文档里给了一个刻意留空的请求示例，并解释了它的用途：可以拿它来检查客户端集成。它返回一个 unknown 且零义务的账本。文档原文强调："源证据缺失永不声称闭合"（absence of source Evidence never claims closure）。

这条把"没做"和"做完了"严格分开——一个退回空结果的工具，永远不会被误读成"复刻已验证完成"。同一条价值观还体现在：静态应用图事实只能产生候选义务，不能证明运行时或进程行为。

fail-closed：12 条拒绝就绪的情形

契约还列了一张"什么时候判定为不就绪"的清单。它比"通过条件"更能说明设计取向——因为这里每一条都是主动拒绝给出结论：

  • 一个有界能力没有给出有效的数值限制；
  • 一个 fixture 缺少恰好一个兼容的选中工作流；
  • 调用了不兼容或不可用的 provider；
  • 类型化的 CLI 失败却以 0 退出，或 MCP 失败却报告成功；
  • 并发行为使用了全域序比较；
  • 把截断、不稳定、权威不可用或矛盾标记为等价；
  • 一处刻意的主分歧没有被本地化；
  • 矛盾证据或受影响的比较缺失；
  • 复刻义务台账不是 ready、没有必需义务，或保留了未归属/未验证的必需义务；
  • 进程超出其声明的 target / lifecycle、取消丢失诊断信息，或自有资源未释放；

最后一条尤其能说明"可复现"是被当作硬要求写进契约的：连"上次的源摘要和这次不一样"都必须被检测出来并拒绝。

三条更正

更正一：路径隐患不存在

本次改用独立前缀安装后，我担心 rea setup 会基于 npm root -g 拼出错误的启动器路径。--dry-run 实测显示它解析到的是真实安装位置。原因是它用自身路径自省。这条更正的含义是：不要用"通用生态常识"去推测一个具体工具的实现——REA 在这件事上做得比通用做法更可靠。

更正二：Assets.car 不是我的疏漏

我在复刻规划的自我批评里，把"完全跳过了 Assets.car"列为自己的遗漏。实际补跑后 inspect-asset-catalog 返回 target_unavailable / unsupported binary format。REA 自己也读不了这个文件。这条更正的含义是：先验证工具是否具备某能力，再检讨自己是否遗漏——否则会把工具边界误记成自己的失误，进而去做无效的补救。

更正三：接引擎不只是一个环境变量

我把"设 GHIDRA_INSTALL_DIR 即可"写进了规划。实测报错里出现了 ghidra: architecture_unsupported，并附有说明：v1 无法对 universal Mach-O 强制架构，须先 thin。这意味着接入 Ghidra 的前提条件里，包含一步针对目标文件的前置处理。这条更正的含义是："装上就能用"通常在编排层工具上不成立——编排层的接入成本不只在你装了什么，还在目标本身的形态。

12正确用法清单

如果只带走一页，带这一页。每条都对应前面某一章的机制。

判断可用性

  • 用 rea capabilities --json 判断"零引擎下能做什么"，不要靠工具名猜
  • 用 binary_session.tool_availability 判断"当前这次调用能不能成"，因为 tools/list 是全量目录、不反映当前可用性
  • 分清两种失败：provider_unavailable（缺东西，可补救）vs target_unavailable（这个输入读不了，只能换方法）
  • 把 unknown 当独立状态对待——它既不是可用也不是不可用

组织调查

  • 每个结论挂 evidence_id；没有 ID 的结论是"我看到的"，不是"可复核的"
  • 区分观测与推断——REA 自己就是这么分桶的（observations vs hypotheses）
  • 把"没查清"写进输出，而不是留给读者猜。unexplored_branches 和 residual_unknown 都是正式字段
  • 复刻类任务用义务台账的形态组织：稳定 ID + 版本 + 必需用例 + authority 要求

控制成本

  • 大输出用 --token-limit 截断（本次单次 inspect-artifact 输出 426 KB）
  • 直接写程序对话 MCP 时，用事件驱动而非固定等待；冷启动要加载 170 个工具的 schema
  • Node 脚本收尾别用 process.exit()，异步 stdout 会被截断——用同步写
  • 单工具 schema 超客户端上限时开 compact profile（需重启服务器生效）

避免踩坑

  • 不要假定"装了引擎就能分析一切"——架构与格式是可独立否决的条件
  • 不要因为工具清单里有某个工具，就认为它在当前环境可用
  • 不要用低权威证据去支撑高权威结论（静态图 ≠ 运行时行为）
  • 不要指望失败后自动换条路——REA 明确不这么做

一句话总结用法

把 REA 当成一个需要先问清楚"现在能做什么"、再接受"做不到就明说"的执行器。它的用法不舒服的地方，恰好也是它可信的地方——你在它那里拿到的每一个结论，都带着"凭什么"的凭据。

13结论

以下判断是观点，不是共识。它们建立在前十二章的证据上，但推论部分由我负责。

它解决的问题不是"分析能力"，是"分析的可复核性"

如果把 REA 的价值理解成"让 AI 能反编译"，那它的天花板就是它所编排的引擎——你装了 Ghidra，它就有 Ghidra 的水平。这不是一个有护城河的位置。

但如果把它的价值理解成"让分析结论变得可复核、可比较、可复现"，那它做的事情就没有替代品：五元口径把观测与推断分开、authority 分级阻止证据越级、稳定 ID 让结论可追溯、fail-closed 让"没做成"无法伪装成"做成了"。这套东西在引擎换成什么之后都依然成立。

本次实践最有说服力的一个细节：126 KB 的证据包里，contradictions 与 unexplored_branches 是正式字段。一个把"我有哪些没查清"写进输出结构的工具，和一个只输出结论的工具，可信度不在一个层级上。

它的定位代价是真实的

编排层必然要付的代价是：能力上限受制于被编排者。零引擎环境下，REA 能做的是 18 项静态产物分析；要触及反汇编与伪代码，必须自带引擎。doctor 退出码 1、170 个工具里大量不可用、provider_unavailable——这些都是同一个代价的不同表现。

但这个代价换来的是可裁剪性：不装引擎不会让任何一项已有能力失效（第 05 章的两栏没有交集）。对使用者来说，这意味着一件事：你可以从零成本开始用，然后按需加装，而不是必须先配齐一整条工具链。

对"AI 原生工具"的一点观察

REA 是少数把失败路径设计得和成功路径一样完整的工具。它有三套显式的失败分级（provider / target / authority）、一个诚实的三态可用性（含 unknown）、一份 12 条的就绪拒绝清单，以及"缺少源证据永不声称闭合"的明文规定。

这与"AI Agent 需要什么"这个问题直接相关：Agent 最容易犯的错不是"不会做"，而是"不知道自己做没做成"。一个把"我做到了什么程度、还差什么、下一步该采什么证据"结构化输出的工具，比一个"能力强但只说结论"的工具更适合被编排进 Agent 流程——因为后者会让 Agent 在不确定的地方自信地继续往前走。

最后一个判断

本次实践的起点是"用 REA 复刻一个 macOS 应用"。走到最后，REA 给的最大收获不是它解出了多少 nib 对象（780 个节点确实有用，但那只占整件事的一小部分），而是它示范了一种把"逆向"从手工技艺变成工程记录的做法：先声明要证明什么，再为每条主张配置证据要求与权威等级，最后用机器判定闭合。

这套做法与工具无关。就算不用 REA，产出物也应该长成那个样子。
