判断 01

oMLX 解决的不是「Mac 上能不能跑」，而是 Agent 工作负载的 prefill 税：把重复前缀的计算成本，用存储换掉。

判断 02

分层 KV 缓存的价值集中在冷路径的恢复，不在热路径的提速。与 mlx-lm 相比，热态几乎打平；差异只在重启之后才出现（7.2s vs 17s）。

判断 03

它的架构是 vLLM 的调度思想在 MLX 统一内存上的再实现（block / CoW / 前缀共享 / 内容寻址），而非 vllm-mlx 的封装。vllm-mlx 只是起点。

判断 04

连续批处理是 macOS 生态上真正稀缺的能力，但 3.36–4.14× 的 8 路加速比说明 decode 阶段被内存带宽锁死——并发是给多用户/多智能体的，不是给单用户提速的。

判断 05

在 oMLX 上，缓存命中率就是 SLA。命中率不由服务调优决定，而由客户端如何组装 prompt 决定：前缀顺序、tools 是否稳定、动态内容放在哪。

判断 06

在 Mac 推理栈里它不替代 Ollama。Ollama 卖易用性与模型库，oMLX 卖「智能体后端」这一格的工程属性，两者目标函数不同。

判断 07

能力上限由物理决定：它只把 KV 溢出到 SSD，不溢出权重。64GB 的机器买到的是「巨大上下文复用」，不是「更大的模型」。

判断 08

成熟度存在结构性矛盾：3465 次提交、近每日发版，修得快也破得快。生产使用必须锁版本 + 固定内核构建。

判断 09

正确的验收方式是 「看第 2 次请求，不看第 1 次」。任何用首轮 TTFT 做的评测，测到的都是冷启动税而不是缓存收益。

一句话结论

如果你的负载是「同一段大前缀被反复重发」——编码智能体、长系统提示、固定工具集、多轮会话——oMLX 是目前 macOS 上唯一把这件事当第一性问题来解的服务；如果你的负载是「单轮问答」或「一次性脚本」，它给你的只有冷启动的账单。

01定位判定：它是什么，以及它刻意不是什么

同名分支在 GitHub 上至少有四个，营销站点也在抢注相似域名。先把项目边界钉死，后面的所有性能讨论才有对象。

oMLX 是 jundot 维护的、Apache 2.0 授权的 Apple Silicon 本地推理服务。官方仓库的自我定位只有一句话：「带连续批处理与 SSD 缓存的 Apple Silicon LLM 推理服务器，可从 macOS 菜单栏管理」。支撑这一定位的是三层东西：一个 FastAPI 服务（暴露 OpenAI 与 Anthropic 兼容端点）、一套迁移自 vLLM 的分页缓存调度层、一个原生 SwiftUI 菜单栏应用。

它不是模型、不是微调框架、不是聊天客户端。它更接近于「把 vLLM 的工程模型搬到一个没有独立显存、没有 CUDA、没有多卡 NVLink 的硬件平台上」这一次移植尝试的产物。

1.1 起点与演化速度

项目于 2026 年 3 月在 Apple MLX 仓库的 GitHub Discussions 首次公开，起点是 vllm-mlx v0.1.0——一个把 vLLM 的 API 形状套在 MLX 后端上的薄封装。此后它长出了原创新实现：SSD 分层缓存、连续批处理、VLM 全分页缓存、Anthropic 兼容端点、原生 macOS 界面。仓库累计提交数已达 3,465，这个数字本身就是一条关于成熟度的重要证据（见 §09）。

1.2 与相邻项目的概念分野

02理论根基：prefill 税，以及它为什么可以被存储掉

如果不理解 prefill 与 decode 的物理分野，就会把 oMLX 当成一个「更快的推理器」。它不是。它是一个「把已经算过的东西记住」的服务。

2.1 两个阶段的物理性质不同

Transformer 解码分两段，两段的瓶颈在硬件上是相反的：

  • Prefill（预填充）：把整段 prompt 一次性前向，产出每个位置的 KV。所有 token 可以并行，矩阵乘占主导——这是算力受限（compute-bound）。在 M4 Max 上，Qwen3.8-27B dense 的 prefill 速率稳定在约 250 tok/s，这个数字几乎不随工程优化变化，它是 GPU 算力的下限。
  • Decode（解码）：逐 token 生成，每步都要把全部权重从内存搬到计算单元——这是带宽受限（memory-bandwidth-bound）。所以 decode 速度基本由「内存带宽 ÷ 权重字节数」决定，与提示长度无关（只受 attention 的 O(n²) 轻微拖累）。

这个分野直接决定了一件事：你能优化的只有 prefill，decode 你优化不动。这也解释了后文所有数字的形状——为什么 oMLX 的 TTFT 能从 68.6s 降到 2.5s，而 tok/s 始终在 40–60 徘徊。

2.2 智能体请求的真实形状

一次普通聊天请求的 prompt 可能是几百 token。而一次编码智能体请求是这样的：

[system prompt]        约 2k–8k tok   ← 几乎不变
[tool definitions]     约 3k–12k tok  ← 几乎不变，但顺序敏感
[项目上下文/RAG]       约 2k–20k tok  ← 会话内不变
[对话历史]             逐轮增长
[当前用户输入]         几百 tok       ← 唯一真正新增的部分

第三方实测给了一个具体样本：把 GitHub Copilot CLI 指向本地 26B 模型，每次请求都发送 26,627 个 token 的 system + tool 定义。第一轮 0 命中，耗时 1 分 28 秒；第二轮命中 14,330（54%），耗时降到 33 秒。同一个「2+2」，同样的模型，差 2.7 倍。

这就是 prefill 税：用户为了一段从未改变的文本，每一轮都重新付一次全量计算的账。

2.3 成本模型

把首 token 延迟（TTFT）拆开，可以得到一个能指导调优的式子：

T_ttft  =  T_load        # 模型权重进入统一内存（懒加载时发生）
         +  T_warmup      # Metal kernel JIT / MLX 图优化，首次推理独有
         +  N_uncached / R_prefill   # 未命中 token 数 ÷ prefill 速率
         +  T_book   # 块哈希查找、元数据、调度开销

四项里，只有第三项与缓存直接相关，而它的分子 N_uncached 完全由客户端的 prompt 组装策略决定。这是本报告最重要的一条推论：在 oMLX 上，性能调优的主战场不在服务端配置，而在调用方的 prompt 结构。

理论落地 · 四条可执行动作

① 静态在前，动态在后。system → tools → 稳定上下文 → 历史 → 当前轮。任何把时间戳、随机 ID、变量内容塞进 system prompt 的做法，都会让缓存永久失配。

② tools 顺序必须冻结。实测中仅交换两个 tool 的定义顺序，命中率从 16,384 块直接掉到 0，TTFT 从 2.5s 回到 81.4s。

③ 一次性调用主动放弃写缓存。摘要器、标题生成、分类器这类不重复的调用，用请求头 X-oMLX-Cache-Store: off 跳过存储，避免挤掉多轮会话真正要复用的前缀。

④ 客户端超时必须大于冷 prefill。如果客户端 30s 就断开，而冷 prefill 需要 68s，则缓存永远建不起来——每一轮都是冷启动，这是最隐蔽的死循环。

2.4 为什么 KV 可以持久化：一个结构性红利

因果注意力有一个性质：位置 i 的 KV 只依赖位置 0..i 的 token，与后面的内容无关。这意味着 KV 是「前缀的函数」——只要前缀相同，产出的 KV 就完全相同。

于是 KV 可以被当作内容寻址的数据来处理：给定前缀，算出它的哈希，去查有没有存过；存过就直接取回，没存过就算一遍再存。这一步跨过去，KV 就从「一次会话的临时产物」变成了「可索引、可去重、可落盘、可跨进程共享的模型状态数据库」。oMLX 的全部设计都是这句话的技术展开。

反过来说，这个红利有严格前提：前缀必须逐 token 完全一致。不是语义一致，不是「差不多」，是二进制一致。这个苛刻条件，就是后面所有工程细节（块大小 4096、链式哈希、tools 敏感）的来源。

3.2 被刻意保留的窄通道：自定义 Metal 内核

在对 Qwen3.5、GLM-5.2、MiniMax M3 这几族模型上，oMLX 提供可选的原生自定义内核（如 GLM-5.2 的融合 DSA prefill）。这不是通用优化，而是一条按模型手工开的窄通道，代价与收益都极端：

收益端

GLM-5.2 在 M3 Ultra 上，融合 DSA prefill 实测 845 tok/s，通用回退路径约 29 tok/s——将近 30 倍。这不是调参能补的差距。

代价端

需要完整 Xcode 与 Metal toolchain（xcodebuild -downloadComponent MetalToolchain）。只有 Command Line Tools 会报 xcrun: unable to find utility "metal"。缺失时不会报错，而是静默回退到慢路径，同时占用更多内存。

最容易被忽略的部署陷阱

「静默回退」意味着你无法从服务日志判断自己跑在快路径还是慢路径上。部署后必须显式验证：python -c "from omlx.custom_kernels import native_kernel_status; print(native_kernel_status())"。DMG 安装包已预编译内核，源码安装则需 make kernels；pip install -e . 会跳过内核构建。

04三层 KV 缓存：一个内容寻址的状态数据库

这是整份白皮书的技术核心。如果只能记住一句话：oMLX 把 KV 当作「前缀的哈希映射」来管理，而不是当作「这次请求的临时张量」。

4.1 三级存储与各自的职责

常见的误解是「三层缓存是三级速度」。实际上三层的分工并不对称——L1 管的是元数据与活跃性，L2 管的是避免重复读盘，L3 管的是跨重启的持久性：

4.2 链式哈希：为什么不能只用 token 前缀的简单哈希

compute_block_hash(model_name, parent_hash, token_ids, extra_keys) 返回 SHA-256，关键在于 parent_hash 这一项：每个块的哈希都把它前面所有块的哈希卷进去，形成一条加密链。

这不是为了安全，是为了正确性。若只对块内 token 求哈希，那么「块 A 后面接块 B」和「块 C 后面接块 B」会因为块 B 内容相同而共享同一份 KV——但它们的注意力上下文完全不同，KV 也不同，复用直接产出错误输出。链式结构从机制上排除了这种可能：前缀不同，哈希必然不同。

代价是级联失效：只要有一个块变了，它之后所有块的哈希全变，全部失效。这解释了实测中最刺眼的那个数字——仅仅交换两个 tool 定义的顺序，命中块数从 16,384 归零。改动发生在很前面，后面 12 个块跟着一起死。

4.3 异构层：不是所有 KV 都能切块

MLX 的缓存类型并不统一。标准注意力层产出可切的 KVCache，滑动窗口模型产出 RotatingKVCache，而 Mamba / Jamba 这类状态空间层用的是 ArraysCache——它没有序列维度的分块语义，无法按块切片存储。oMLX 用一套类型注册表分流：

类别典型类名存储策略
可切片KVCache、QuantizedKVCache按块存为 4D slice，标准分页路径
旋转窗口RotatingKVCache、PrefillReadyRotatingKVCache专用 handler 处理窗口回绕，单独计算有效范围
不可切片ArraysCache（Mamba / Jamba）走 BoundarySnapshotSSDStore：在块边界处做整状态快照，序列化为原始字节由后台线程 flush；快照完成后立即释放 GPU 内存
 表 4 · 缓存类型注册表。混合架构模型（注意力 + 状态空间）是这里最麻烦的一类，实测中 4096 的块粒度限制就来自这一类模型的架构约束。

BoundarySnapshotSSDStore 这个设计值得单独说一句：不可切片层的状态在长 prefill 期间会持续累积占用 GPU 内存，如果不做快照，128K 上下文的 prefill 会直接把统一内存吃穿。它选择「到边界就落盘、落完立刻释放」，本质是把内存压力换成了磁盘 I/O——又一次「用存储买空间」。

4.4 工程细节：那些决定它能不能长期跑下去的东西

异步写入

磁盘序列化在后台线程完成，队列有界（_MAX_PENDING_WRITES）。队列满时丢弃写入而不是阻塞推理——这是正确的取舍：宁可少缓存一块，不能卡住生成。

原子落盘

自定义的 _write_safetensors_no_mx 走原子 rename，避免半写文件被后续请求当作有效缓存读入。分桶子目录防止单目录文件数爆炸。

配额策略

默认 auto = （空闲磁盘 + 已有缓存文件）的 50%，且预算只增不减，不会因缓存增长而反复收缩。也可用 --paged-ssd-cache-max-size 20GB 硬限。

损坏恢复

校验和验证 + Metal command buffer 检查，失败自动重试并降级到重算路径。缓存坏掉不会让服务挂，只会让它变慢。

可观测性

stats.py 记录命中/未命中比、写丢弃数、恢复事件数。调优时这几个计数比 tok/s 更有诊断价值。

选择性写入

X-oMLX-Cache-Store: off 只跳过存储，不跳过查找。一次性调用仍能复用已有前缀，只是不再污染缓存。

为什么这套设计值得认真对待

它把「进程重启」这个在本地推理里几乎每十分钟发生一次的事件，从语义上的灾难降级成了性能上的小挫折。对云端服务这是理所当然的，对个人机器上的推理服务，此前没人做过。这才是 oMLX 真正的原创点——不是更快的 kernel，而是让缓存活过进程生命周期。

05调度与批处理：3.36× 背后的物理上限

连续批处理常被讲成「并发让一切变快」。在 Apple Silicon 上这个说法只对一半——它对，但只在多请求场景对；而它之所以不更快，原因在内存带宽，不在调度器。

5.1 连续批处理到底批了什么

传统静态批处理（static batching）要求一批请求全部生成完才能释放批次。一个请求生成 20 token、另一个生成 2000 token，整批就被后者拖住，短请求的槽位在空转。

连续批处理（continuous batching）改为按迭代步调度：每生成一步，完成的请求立刻退出、新请求立刻补位。oMLX 通过 Scheduler（FCFS 队列，并发数可配，默认 8）驱动 mlx-lm 的 BatchGenerator 实现这一点。

这在云 GPU 上是标配，在 Mac 本地推理市场上不是。Ollama 的请求是串行的；mlx-lm 本身没有服务层调度器。oMLX 在 macOS 上是第一个提供真实并发的选项——这个「第一」有实际价值，但价值的上限由下面的数字决定。

5.2 为什么加速比是 3.4× 而不是 8×

decode 阶段每生成一个 token，都要把全部模型权重从统一内存搬到 GPU 计算单元。8 个并发请求共享同一份权重搬运——这是批处理收益的来源。但共享之后，瓶颈就变成了带宽本身：每步的时间被「权重字节数 ÷ 带宽」锁死，与批里有几个请求无关。

所以在理想情况下，8 路并发的吞吐上限是单路的 8 倍（一次搬运服务 8 个 token），但实际上：注意力计算量随批增大而增加、KV 读取量线性增长、调度与同步开销上升。最终落在 3.4–4.1×，意味着带宽利用率从单路的约 12% 提到了约 45%——已经是很有价值的改善，但距离线性很远。

工程推论

并发数是多租户指标，不是单用户指标。把 --max-concurrent-requests 从 8 调到 32，对单个用户自己的请求延迟没有帮助，只会让 32 个请求一起变慢、并抬高内存占用到可能触发模型驱逐。正确的用法是：一个人跑一个智能体 → 保持默认；一台机器服务一个团队 → 才调高。

5.3 FCFS 的代价：缺少优先级是设计选择，也是缺陷

Scheduler 用先来先服务，没有优先级、没有公平份额、没有抢占。这个选择的后果是典型的队头阻塞：

  • 一个 128K 上下文的慢请求排在前面，会把它后面所有请求的首 token 延迟一起拖长；
  • 交互式请求（人打字等回复）与批处理请求（离线跑评测）竞争同一队列时，前者会被后者拖累；
  • 没有 per-tenant 配额，一个失控的智能体外循环可以吃掉全部并发槽位。

缓解手段只有工程侧的：把批处理任务指向独立的第二个实例、或通过模型别名 + Profile 把它们在引擎层面分开。这不是优雅方案，但对单机场景够用——真正需要优先级的场景，通常也已经在考虑多机了。

如果 oMLX 的价值主张是「更快的 prefill」，它在热路径上就输了——因为 mlx-lm 早就做到了。它真正独有的是让缓存活过进程死亡。所以正确的价值陈述不是「oMLX 更快」，而是「oMLX 在重启后依然快」。这两个说法指向完全不同的使用场景：前者是性能优化，后者是可用性工程。

6.4 冷启动税：必须预付款的 20 秒

oMLX 采用懒加载模型。这意味着服务启动后第一次请求要一次性付清三笔账：

三笔账的构成是：模型加载（9.7–11.9s，权重进统一内存）、首次推理预热（9–10s，Metal 内核 JIT + MLX 图优化）、全量 prefill（取决于 prompt 长度）。前两笔与 prompt 无关，是纯固定成本；第三笔才是缓存能优化掉的部分。

CI 与自动化场景的隐性事故

如果你的自动化流程在服务启动后立刻发请求并设置 30s 超时，会稳定撞上「30 秒无响应」，然后被误判为「服务挂了」。正确做法：启动后先发一个 1 token 的探针请求（或从管理面板 pin 模型），把加载与预热成本前置支付，再进入真实负载。

7.2 应该劝退的四类用户

「我就想在本机聊天」

单轮问答、单模型、每轮 prompt 都不同——缓存命中率结构性地接近 0。你会付 20 秒冷启动、装一个 Python 环境、还要管一个后台服务，换回来的是零收益。用 Ollama 或 LM Studio。

「我要跑 70B 以上」

SSD 缓存只存 KV，不存权重。64GB 机器上 70B 4bit 大约需要 40GB+ 权重，能装但没有余量给长上下文。这类需求不是换软件能解决的，是换机器或租云。

「我需要 Linux 服务器 / 团队共享集群」

macOS 15+ 与 Apple Silicon 是硬约束（MLX 依赖 Metal，菜单栏用 PyObjC）。团队共享的正确形态是一台 Mac Studio 加反向代理，而不是「部署到 K8s」。

「我需要稳定不变的 API 契约」

近每日发版意味着端点行为、默认参数、模型兼容性都可能在两次 patch 之间变化。如果你的下游有 SLA，锁版本比追新版更重要（见 §09）。

8.3 安全模型：一条不许绕过的规则

oMLX 的安全设计有一条硬边界和若干软开关，理解这个分层很重要：

  • 硬边界：未设置主 API key 时，服务拒绝在任何非 loopback 地址上启动。想监听 0.0.0.0，必须先有 key，或 key 与 host 一起保存。
  • 软开关 1：skip_api_key_verification 会同时关闭推理与管理鉴权，因此被强制限制在 loopback 绑定下。
  • 软开关 2：auth.allow_unauthenticated_inference（默认 false）允许网络绑定下的无密钥推理，但管理端点仍需主 key 或 admin 登录。这是为「局域网内多客户端调用、但管理面要锁」的场景准备的。
反向代理场景的注意事项

如果你用 Pinggy、Cloudflare Tunnel 之类的隧道把 localhost:8000 暴露出去，oMLX 会认为自己在 loopback 上，安全底线因此不生效。此时必须自行在 --api-key 或隧道层加认证——不要把「服务端有保护」当成「隧道后也安全」。

8.4 客户端接入

管理面板会为选定模型生成现成的配置命令，覆盖 Claude Code、OpenClaw、OpenCode、Codex、Copilot CLI、Hermes Agent、Pi、Mistral Vibe、DeepSeek Harness 等。CLI 侧可用 omlx launch list 查看本机已安装的集成。

SSD 缓存放外置盘命中却有 1–3s 甚至更高的额外延迟；「持久化好像没用」外置 USB/网络盘的随机读延迟远高于内置 NVMe。所有公开数据均来自内置盘缓存目录固定在内置 NVMe；外置盘只放模型权重（顺序读为主）
关掉 memory guard 跑大模型整机卡死、风扇狂转、需要强制重启统一内存被 GPU 与系统共用，超限不是优雅失败而是 swap 风暴保留 --memory-guard；用 --memory-guard-gb 设定明确上限

11落地路径：五级成熟度与验收清单

从「装上试试」到「团队共享生产」，中间隔的不是配置项，而是四个具体的验证动作。

11.1 四个必须自己跑的验证

以下四条不依赖任何第三方基准，二十分钟内可完成，但它们能决定方案是否成立：

验证 1 · 缓存真的生效了吗

同一个请求连发三次，记录第 1、2、3 次的 TTFT。期望形态：第 1 次显著高，第 2、3 次接近且大幅下降。如果第 2 次没降，说明前缀里混进了动态内容。

验证 2 · 重启还活吗

跑一轮让缓存建立，重启服务，再发同样的请求。这是 oMLX 与 mlx-lm 唯一的分水岭。若重启后退回到冷启动水平，说明 SSD 层没生效（目录配置错误或配额为 0）。

验证 3 · 顺序敏感度

把 tools 数组顺序交换一次，再发同一请求。预期命中归零。这一步不是找 bug，是确认自己理解了机制——也顺便证明缓存判定确实在按内容工作。

验证 4 · 内核在不在

跑 native_kernel_status()。如果你用的是 GLM-5.2 / MiniMax M3 / Qwen3.5，这一项决定你是 845 还是 29 tok/s 的 prefill。静默回退不会给你任何提示。

12结论：一次成功的「错位移植」

oMLX 做的事情，用一句话概括是：把一个为数据中心设计的服务模型，硬塞进了一台个人电脑，而且塞对了。

vLLM 的 PagedAttention 诞生于「显存稀缺、请求高并发、GPU 昂贵」的云环境，目的是让同一块 GPU 服务尽可能多的用户。把它搬到 Apple Silicon 上，前提全变了：没有独立显存（统一内存），没有多用户（通常一个人），GPU 不贵（已经买断了）。按常理，这套工程应该水土不服。

但它找到了一个在新环境里成立的对应物：云上稀缺的是显存，Mac 上稀缺的是「不被打断的连续计算时间」。智能体的存在制造了这个稀缺——每一轮都要求机器把两万个 token 重新算一遍，而这台机器同时还要跑 IDE、浏览器和 Docker。

于是那些在云上用来省显存的机制，在这里被用来省时间：分页是为了碎片化复用，这里是为了让不同会话共享同一段前缀；写时复制是为了并发安全，这里是为了让多个客户端读同一份缓存而不互相污染；LRU 驱逐是为了容量管理，这里是为了在 64GB 里同时放下模型、KV 和 IDE。连 SSD 落盘这个在云端几乎不存在的设计（云盘太慢），在 Mac 上反而成立——因为本地 NVMe 的随机读延迟，比重新跑一次 16K prefill 快了两个数量级。

判断（这是观点，不是共识）

oMLX 的技术价值不在于它比谁快，而在于它证明了「本地推理服务的缓存可以是持久的」这件事值得做。一旦这个前提被接受，后续所有优化（KV 量化、跨进程共享、多机分片）都有了新的落点。目前它更接近「一个方向正确的早期实现」，而不是「一个可以无脑上生产的组件」——但这个方向本身，比它当下的完成度更重要。

12.1 三句话行动建议

  1. 如果你的日常是 Claude Code / Cursor / Codex 指向本地模型，现在就换，收益立刻可见，而且改造成本只有一次配置。做完 §11.1 的四个验证再决定是否长期使用。
  2. 如果你只是在本机聊天或跑脚本，不要换。你付出的部署复杂度与冷启动税是确定的，换回的收益是零。
  3. 无论哪种情况，先花半天把自己的 prompt 组装顺序规范化。这一步的收益不依赖 oMLX——它对任何带前缀缓存的推理服务都成立，而它恰好是绝大多数团队从未做过的事。

12.2 尚待观察的三个问题

  • 单维护者风险。项目由一位独立开发者维护，没有公司背书。3,465 次提交的活跃度是优点，也是单点依赖的放大器。团队采用前应评估「如果明天停更」的迁移成本——好消息是 MLX 生态本身在扩张，坏消息是这套 SSD 缓存没有等价替代。
  • 跨进程 / 跨模型共享尚未出现。当前缓存绑定在单个服务实例上。如果未来能做到多个本地进程共用一个缓存池（比如 IDE 插件与 CLI 共享），收益会再上一个量级。这是最值得期待的方向。
  • 基准数据的独立性。目前几乎所有性能数字都来自维护者自测或单篇第三方评测，缺少多环境、多负载的交叉验证。SSD 恢复路径在慢速盘、低内存机器上的表现尤其缺乏数据。
