MacBook 远程控制 Mac mini 完全指南

一台没有显示器的 Mac mini 放在家里，一台 MacBook 白天在公司用手机热点、晚上带回家。本文把这条链路上所有会卡住你的环节拆开，逐个给方案、给命令、给判断标准。

01场景与问题拆解

先把一团乱麻拆成三根独立的线

大多数人在配置远程 Mac 时会陷入同一个误区：把它当成一个问题。于是装个 Tailscale、连上屏幕共享，发现卡得没法用，又去换网络、换软件，一路试下来依然说不清哪里不对。

实际上这是三个完全独立的问题叠在一起。它们各自有独立的解法，任何一层短板都会主导整体体验。

1.1 你的实际配置

设备位置网络角色
MacBook Pro随身（白天公司 / 晚上家）公司侧用手机热点；家中同一局域网操作端
Mac mini固定在家家庭宽带被控端（无显示器）
为什么这个组合比"两台都在家里"难得多

手机热点意味着双重 NAT（手机自己一层，运营商 CGNAT 再一层），而且是移动网络里最不利的对称型。它同时带来三个约束：打洞成功率下降、中继延迟变高、流量按 GB 计费。这三条在后文会反复出现。

1.2 需求强度决定方案

同样叫"远程控制"，每天用 20 分钟和每天用 5 小时是两套完全不同的架构。先对号入座：

强度每天图形化时长体验门槛可行方案
轻度< 30 分钟能看清、能操作，卡一点可忍自带屏幕共享 + 任意通路（含中继）
中度1–3 小时接近本地手感，输入不能丢HEVC 类协议 + 必须直连
重度> 3 小时／当主力机与坐在机器前无差别高性能模式 + 局域网千兆 + 大流量卡
一个容易被忽略的前提

本文默认两台机器都是 Apple Silicon（M 系列）且系统在 macOS 14 Sonoma 以上。如果是 Intel Mac，第 4 章里最重要的「高性能模式」直接不适用，方案会退回到第三方客户端。

02显示层

让一台没有屏幕的机器以为自己在正常工作

2.1 为什么无头 Mac 会出问题

macOS 启动时，系统通过 HDMI/DisplayPort 的 EDID（显示器身份数据）获知对方支持的分辨率、刷新率、色域。如果这条线上什么都没有，WindowServer 会创建一个兜底的帧缓冲——通常固定在 1024×768 @ 60Hz，并且 GPU 的显示输出管线不会完整初始化。

后果不止是"画面小"：

  • 窗口布局全部错位——所有应用按 1024×768 排布，接上正常分辨率后要重排一遍
  • 依赖 Metal 的应用可能拒绝启动或降级——Final Cut Pro、Blender、部分 Electron 应用会检测不到可用 GPU 特性
  • 色彩管理失效——没有 EDID 就没有色域信息，屏幕共享传出去的画面颜色不准
  • 无法全屏或分屏——部分应用在极低分辨率下禁用这些布局
关键认知

这个问题和网络、软件都无关，它发生在 GPU 出画面之前。所以无论用什么远程软件，都必须先解决它。好消息是：macOS 14 之后系统自己就能解决，不用买任何硬件。

2.2 三种方案对比

方案实现层成本分辨率能力适用条件
高性能模式虚拟屏macOS 内置免费最高 4K，或 1920×1080 HiDPI双端 Apple Silicon + macOS 14+
BetterDisplay第三方软件免费基础 / $21.99 Pro任意，可 HiDPI、可脚本化任何 Mac
HDMI 假负载硬件（EDID 模拟器）¥20–40出厂固定，常见 1080p / 4K30任何 Mac，最稳

方案 A：macOS 内置虚拟显示器（首选）

macOS Sonoma 重新设计了屏幕共享功能，其中「高性能」连接类型可以自行创建 1–2 块虚拟显示器，完全不需要物理屏幕。这是目前最干净的做法：零成本、系统级、不需要装任何东西。

限制也很明确：只能是 1 块或 2 块、单块上限 4K、且必须双端 Apple Silicon。第 4 章会详细展开。

方案 B：BetterDisplay（灵活度最高）

它能在软件层创建任意分辨率的虚拟屏，支持 HiDPI，还提供命令行工具 betterdisplaycli，可以把"创建虚拟屏 → 设置分辨率"写成脚本、开机自动执行。免费版包含基础虚拟屏，Pro 版解锁自定义分辨率、自动化等能力。

它的价值在于：当你用 Parsec、VNC 等不自带虚拟屏的方案时，它是必需的。

方案 C：HDMI 假负载（最稳的兜底）

一个几十块钱的小 U 盘状设备，插进 HDMI 口后向系统谎报"我是一台 1920×1080 显示器"。系统因此正常初始化显示管线，效果和真接显示器一样。

缺点是便宜货通常把分辨率和刷新率写死，改不了；而且占用一个接口。但它的可靠性是三者中最高的——不依赖任何软件运行，重启、系统更新都不受影响。

我的建议：两个都做

先用高性能模式的虚拟屏（零成本、够用）。如果你后来发现需要更高分辨率，或者改用 Parsec 这类不自带虚拟屏的客户端，再补一个假负载做兜底——它只有 20 块钱，插上就不用管了。

2.3 分辨率对齐：一个影响长期舒适度的细节

远程桌面最容易被忽视的体验杀手，是分辨率不匹配导致的二次缩放。如果 Mac mini 的虚拟屏是 1920×1080，而你的 MacBook 屏幕逻辑分辨率是 1512×982，远程窗口要么留黑边，要么被缩放——文字立刻变模糊，看久了眼睛很累。

解决办法是把虚拟屏设成与 MacBook 一致的逻辑分辨率，并开启 HiDPI：

MacBook 型号逻辑分辨率建议虚拟屏设置
13 英寸（M1/M2）1440 × 9001440×900 @2x
14 英寸（M3/M4）1512 × 9821512×982 @2x
16 英寸1728 × 11171728×1117 @2x

查看本机逻辑分辨率：系统设置 → 显示器，或执行 system_profiler SPDisplaysDataType | grep Resolution

用 BetterDisplay 的 CLI 一次性建好：

# 创建一块 16:10 的 HiDPI 虚拟屏，预置几个常用分辨率
betterdisplaycli create --type=VirtualScreen \
  --virtualScreenName="Remote" \
  --aspectWidth=16 --aspectHeight=10 \
  --virtualScreenHiDPI=on \
  --resolutionList="1512x982,1728x1117,1920x1200,2560x1600"

# 连接（启用）它
betterdisplaycli set --name="Remote" --connected=on

# 设成与 MacBook 一致的分辨率
betterdisplaycli set --name="Remote" --resolution=1512x982

把它存成 shell 脚本，挂到登录项里，Mac mini 每次重启后自动恢复——否则重启一次就要重新配。

虚拟屏的代价

创建 4K 虚拟屏会增加约 200MB 显存占用，CPU 空闲时几乎无影响。如果发现风扇转得凶，先降低虚拟屏分辨率。Mac mini 常年开机，这个成本基本可以忽略。

03网络层

从"能连上"到"能直连"，中间隔着一整套 NAT 穿透机制

3.1 Tailscale 是怎么工作的

理解 Tailscale 的关键，是把它拆成两个完全分离的平面。很多人误以为它是"又一个 VPN 服务器"，其实它的服务器几乎不碰你的数据。

控制平面（协调服务器）只做三件事：给你的设备分配一个 100.64.0.0/10 网段的虚拟 IP、登记每台设备的 WireGuard 公钥、在设备之间交换"对方的公网端点是什么"。它全程看不到任何明文——因为私钥永远不离开本机，服务器连解密的能力都没有。这也是它和传统 VPN 网关的本质区别：传统网关是所有流量的必经之路，Tailscale 的服务器只是电话簿。

数据平面才是真正的传输通道：一条点对点的 WireGuard UDP 隧道，端到端加密。理想情况下两台设备直接对打，数据一个字节都不经过 Tailscale 的服务器。

除了这两条，还有两个能力值得知道：

  • MagicDNS：给每台设备一个固定主机名，直接用 ssh mac-mini 而不是记 IP。切换网络后地址变了也不受影响。
  • ACL：在控制台用声明式策略控制"谁能访问谁"。个人使用一般用默认的全互通即可。

3.2 NAT 穿透的四个步骤

两台设备都在 NAT 后面，谁都无法被主动连接。打洞的核心思路是：让双方几乎同时向对方发包，用各自"刚发出去的包"在 NAT 上凿出一个临时洞口，对方的回包就能顺着这个洞进来。

3.3 NAT 类型与成功率

NAT 不是只有一种。按对入站包的限制严格程度，从宽到严分四类：

类型行为打洞友好度
Full Cone内部地址映射到固定公网端口，任何外部地址都能发进来最好
Restricted Cone只放行"曾经收到过我包"的那些 IP好
Port RestrictedIP 和端口都要匹配过中等
Symmetric每个不同的目标地址分配不同的公网端口，外部无法预测最差

两端组合后的实际成功率（业界长期观察的粗略经验值，非精确测量）：

本端 ＼ 对端Full ConeRestrictedPort RestrictedSymmetric
Full Cone极高极高高中
Restricted极高高中高中低
Port Restricted高中高中低
Symmetric中中低低极低
一个重要但反直觉的结论

"一锥一对称"（比如家宽 + 手机热点）通常能打通，不是必然失败。因为家宽这一侧是锥形，它主动发出的包会给对方的地址开一个口，对方的回包就能进来。只有双对称才近乎必然失败。

3.4 手机热点到底行不行

你的链路实际是双层 NAT：

MacBook → iPhone 热点 NAT (172.20.10.0/28) → 运营商 CGNAT (100.64.0.0/10) → 公网

外层是运营商级 NAT，通常表现为对称型；内层是 iPhone 自己做的锥形 NAT。对端看到的有效类型由外层决定，也就是对称型。所以你的组合是"对称 × 家宽锥形"，落在上表中"中"到"中低"这一档。

实际情况比表格更复杂，因为移动网络还有三个额外变量：

  • 运营商 CGNAT 的严格程度不同——有的放行匹配包，有的做更严的过滤
  • 部分移动网络对 UDP 做端口随机化，让外部无法预测映射
  • 少数网络直接限速或屏蔽非标准 UDP 端口

所以结论是：值得先试，但不能假设一定成功。实测分布大约是一半左右的场景能直连，其余回落中继。这必须用命令测，不能靠猜。

怎么测：tailscale netcheck

tailscale netcheck

输出里重点看这四个字段：

字段含义关键取值
UDPUDP 能否出站true 是打洞的前提；false 直接放弃穿透
MappingVariesByDestIP是否对称 NATtrue 表示端口随目标变化，打洞难
PortMapping路由器自动端口映射出现 UPnP 或 NAT-PMP 是加分项
Nearest DERP最近的中继节点及延迟大陆用户常见 150–300ms

再看实际连接方式：

tailscale status          # 对端显示 direct 还是 relay "xxx"
tailscale ping mac-mini   # 第一行直接告诉你是直连还是走中继
不要只看一次结果

打洞结果和当前网络状态强相关。手机热点在 4G/5G 之间切换、信号波动、运营商出口变化都可能导致重新判定。建议在不同时间、不同位置各测两三次再下结论。

3.5 六种通路方案对比

把所有可选路径放在一起，按"数据是否经过第三方服务器"分成三类。这个分界同时也是延迟分界。

3.6 该选哪条：一条命令决定

不用猜，也不用全试一遍。跑一次 tailscale ping，按结果分流：

3.7 自建 DERP：把中继延迟从 250ms 压到 30ms

如果测试结果显示始终走中继，且 UDP: true，自建 DERP 是性价比最高的一步。官方 DERP 全部部署在海外，大陆用户实测延迟 150–300ms，跨境链路晚高峰抖动明显；换成国内轻量 VPS 后，实测稳定在 20–40ms，波动大幅收敛。

准备

  • 一台国内轻量 VPS（2 核 2G 足够，年付通常 100–300 元）
  • 一个域名（推荐），或直接用 IP（需自签证书 + 非标准端口）
  • 安全组放行：443/TCP、3478/UDP、80/TCP

编译并启动 derper

export GO111MODULE=on
export GOPROXY=https://goproxy.cn

git clone https://github.com/tailscale/tailscale.git
cd tailscale/cmd/derper
go build -o derper
cp ./derper /usr/local/bin/ && chmod +x /usr/local/bin/derper

# VPS 本身要先加入你的 tailnet（-verify-clients 需要）
curl -fsSL https://tailscale.com/install.sh | sh
tailscale up
tailscale status

配置 systemd

[Unit]
Description=Tailscale DERP Server
After=network.target tailscaled.service
Requires=tailscaled.service

[Service]
User=root
ExecStart=/usr/local/bin/derper \
  -hostname=relay.yourdomain.com \
  -certmode=manual \
  -certdir=/var/lib/derper \
  -a=:443 \
  -stun \
  -stun-port=3478 \
  -verify-clients \
  -socket=/var/run/tailscale/tailscaled.sock
Restart=on-failure
RestartSec=3
LimitNOFILE=500000

[Install]
WantedBy=multi-user.target

注册到 Tailnet

登录 Tailscale 控制台 → Access Controls，在 JSON 中加入 derpMap：

    "OmitDefaultRegions": false,
    "Regions": {
      "900": {
        "RegionID": 900,
        "RegionCode": "cn-custom",

保存后验证：

tailscale netcheck

netcheck 里应该能看到你的自建节点，延迟在 30ms 左右。status 里对端若显示 relay "cn-custom" 即表示已生效。

两个已知的坑

未备案域名 + 443 端口：国内 VPS 上，运营商可能对未备案域名的 443 连接注入 RST，症状是"节点在线但连不上"。解决办法是改用非标准端口（如 9810）+ 自签证书，并在 derpMap 里加 "CertName" 与 "InsecureForTests": true。

不要只看最低延迟：自建中继初期可能有一组高延迟样本（实测有 28–539ms 的波动区间），稳定后才落到 26–32ms。判断要连续测几十次，看中位数而不是最好值。

3.8 frp / rathole：彻底放弃打洞

如果 UDP 被封，或者你希望"永远不依赖打洞结果"，反向代理是最确定的方案：在 VPS 上跑 frps，Mac mini 上跑 frpc，把 22（SSH）和 5900（VNC / 屏幕共享）端口映射出去。

优点代价
不依赖打洞，任何网络下都能连所有流量都过 VPS，受 VPS 带宽上限约束
延迟稳定，无抖动端口暴露在公网，需额外做访问控制
可配合自有域名与 TLS比 Tailscale 多一套维护成本
安全提醒

把 5900 直接暴露到公网是很危险的。至少要做到：只监听 127.0.0.1 + frp 的 sk 鉴权、开启 TLS、加 fail2ban。更稳妥的做法是只映射 SSH，VNC 通过 SSH 隧道转发。

04协议层

同一块屏幕，编码方式不同，带宽能差三倍

很多人把"卡"全部归咎于网络。但在同一个网络条件下，换一个客户端就能从"没法用"变成"接近本地"——这中间的差距来自编码方式。

4.1 三种编码范式

远程桌面协议史上有三种完全不同的思路，理解它们的差异就理解了为什么体验差这么多：

指令流

RDP 式：传"画什么"

不传像素，传绘制命令——"在 (120, 88) 用 14px 黑体画这行字"。带宽极省、文字锐利、鼠标无延迟。代价是需要协议层深度集成，macOS 至今没有原生 RDP 服务端。

像素块

VNC 式：传"长什么样"

持续截屏，把变化的矩形区域压缩后发过去。通用性强、任何系统都能实现，但对 4K/5K Retina 屏幕来说像素量巨大，滚动和动画场景下带宽飙升。macOS 自带屏幕共享的标准模式走这条路。

视频流

HEVC 式：把整屏当视频编码

用硬件编解码器把整屏画面压成视频流。压缩率最高、动态画面表现最好，是现代远程桌面的主流方向。缺点是需要双端硬件支持，且低码率下文字会有轻微振铃效应。

macOS 的历史包袱

Apple 二十年前就标准化了 VNC，所以系统自带的"屏幕共享"长期是 RFB/VNC 实现，监听 5900 端口。这也是为什么传统上大家都说"Mac 的远程桌面很卡"——直到 macOS Sonoma 加入高性能模式。

4.2 macOS 高性能屏幕共享：被低估的最优解

这是本文最重要的一个修正。如果你两年前查资料，得到的结论一定是"用 Jump Desktop 或 Parsec"；但 macOS 14 之后，系统自带方案在局域网内已经是最好的——而且它自带虚拟显示器，正好解决第 2 章的问题。

解锁条件

条件要求不满足的后果
芯片双端均为 Apple Silicon（M1–M4）退回标准 VNC 模式
系统双端 macOS 14 Sonoma 或更新退回标准 VNC 模式
端口UDP 5900 / 5901 / 5902 双向可达协商失败，无法启用
带宽单台 4K 显示需 75 Mbps降帧、降分辨率、自动回落

它能给你什么

  • 60fps，4:4:4 色度抽样（文字边缘无彩边，长时间看代码不累）
  • 1–2 块虚拟显示器，单块最高 4K 或 1920×1080 HiDPI——无头 Mac 直接可用
  • 立体声音频转发、HDR / 参考模式、动态分辨率自适应
  • 完全免费，无需装任何第三方软件

它的局限（必须知道）

  • 会话期间主机物理屏幕会黑屏——这是隐私设计，也意味着如果有人在家用这台机器，你们不能同时用
  • 每台 Mac 同一时间只允许一个高性能会话
  • 单虚拟屏上限 4K，不能更高
  • 75 Mbps 的带宽门槛，手机热点几乎无法满足
这就是核心矛盾

高性能模式在局域网内是完美方案：免费、60fps、4:4:4、自带虚拟屏。但它对带宽的要求决定了它不可能跑在手机热点上——5G 峰值虽高，实际持续 75 Mbps 且低抖动是不现实的，何况流量成本会让这一步直接崩掉。

所以正确的用法是：回家用高性能模式，在外面用第三方客户端。两套并存，各管一段。

怎么连

macOS 自带的「屏幕共享」App（/System/Applications/Utilities/Screen Sharing.app）里，连接时选择连接类型：

  1. 打开「屏幕共享」，输入 vnc://mac-mini 或对方的 tailnet IP
  2. 认证后，在窗口中点工具栏的显示设置
  3. 把「连接类型」从标准改成高性能
  4. 「显示类型」选 1 块或 2 块虚拟显示器

主机端需要开启：系统设置 → 通用 → 共享 → 屏幕共享（或远程管理）打开，并在「允许访问」里加上你的账户。

Jump Desktop：跨网场景的首选

它的 Fluid 协议是自研的，2.0 版本改用 HEVC，官方称同画质下比 H.264 省约一半带宽。几个关键特性正好对上你的场景：

  • 自带高性能虚拟显示器，支持 120/144/240Hz，可保存预设——不依赖假负载，也不需要 BetterDisplay
  • 支持 4:4:4 色彩与 60fps，文字质量接近高性能模式
  • 弱网自适应做得好：带宽下降时优先保输入响应，而不是硬撑画质
  • 服务端 Jump Desktop Connect 免费，只有 Mac / iOS 客户端需要付费（Mac 版有 14 天试用）
  • 支持 Wacom 数位板、Stream Deck、YubiKey 等外设透传
服务端结构容易被搞混

Jump Desktop 的模型是：Mac mini 装免费的 Connect（服务端），MacBook 装付费的客户端。别在 Mac mini 上买错。相比 Parsec 双端都免费但功能分层，Jump 的一次性买断更适合长期自用。

Parsec：延迟最低，但有前提

Parsec 起家于游戏串流，物理延迟通常在 20–40ms，是这个列表里最低的。但要注意三点：

  • 它捕获的是真实显示输出，无头 Mac 上经常抓不到画面——必须先有假负载
  • 个人免费版是基础能力，虚拟显示器、4:4:4、多屏、隐私模式都需要 Warp 订阅（年付约 $8.33/月）
  • 更偏"流畅优先"，文字锐利度略逊于 Jump

4.5 五个省带宽的系统设置

在 Mac mini 上执行。这些设置能砍掉大量"无意义的动态画面"，对编码器来说是直接的减负，实测能降低 30–50% 的码率消耗：

# 1. 减弱动态效果——最有效的一条，直接砍掉大部分动画帧
defaults write com.apple.universalaccess reduceMotion -bool true

# 2. 减少透明度——半透明模糊每帧都要重算
defaults write com.apple.universalaccess reduceTransparency -bool true

# 3. 关闭 Dock 放大
defaults write com.apple.dock magnification -bool false

# 4. 最小化改用"缩放"而非"精灵"效果
defaults write com.apple.dock mineffect -string "scale"

# 5. 关闭自动隐藏/显示 Dock 的动画
defaults write com.apple.dock autohide-time-modifier -float 0

killall Dock

另外两项需要手动设置：

  • 换静态壁纸——动态壁纸是持续编码的，白白吃掉码率
  • 分辨率不要贪高——1440p 足够日常；4K 的像素量是它的四倍，手机热点扛不住

5.1 换算公式

码率（Mbps）换算成每小时流量：

每小时 GB = 码率(Mbps) × 3600 ÷ 8 ÷ 1024

简化记忆：1 Mbps ≈ 0.44 GB/小时。下面这张表可以直接对号入座。

5.2 手机热点的三个隐性成本

除了流量本身，还有三件事会持续消耗你的耐心：

断连

热点会自动关闭

iPhone 在一段时间无流量后会自动关掉个人热点。长时间远程中途掉线是常事，重连又需要手动操作——而你此时正在远程，无法操作手机。随身 Wi-Fi / CPE 没有这个问题。

限速

"不限量"通常有阈值

大部分"不限量"套餐在 30–40 GB 后降速到 1 Mbps 以下。降到这个程度，连 SSH 都开始有感知，图形化完全不可用。

来电

接电话会断网

部分运营商在 VoLTE 未启用时，来电会中断数据连接。远程正在跑任务时断一下，可能意味着一次构建白做。

上行

上行才是瓶颈

远程桌面主要消耗 MacBook 的下行（接收画面），但家宽侧的上行决定了画面能多快送出来。很多家宽下行 500M、上行只有 30M——高性能模式要 75 Mbps 上行，直接不够。

06配置清单

从零开始的完整步骤，按顺序执行

6.1 Mac mini 端（8 步）

  1. 首次开机必须接显示器
    macOS 初始化向导（选择语言、登录 Apple ID、建账户）无法远程完成。临时接电视或借一次显示器，配完就再也不需要。
  2. 开启共享服务
    系统设置 → 通用 → 共享，打开「屏幕共享」「远程登录」「文件共享」。SSH 也可以用命令开：
    sudo systemsetup -setremotelogin on
  3. 设置电源策略，避免睡眠后永久失联：
    sudo pmset -a sleep 0　永不休眠
    sudo pmset -a autorestart 1　断电恢复后自动开机
    sudo pmset -a womp 1　网络唤醒（仅以太网有效）
    sudo pmset -a displaysleep 10　屏幕 10 分钟关闭，不影响服务
  4. 接上网线
    比 Wi-Fi 三个好处：唤醒可靠、打洞成功率高、上行稳定。顺手在路由器上做个 DHCP 地址保留，避免 IP 变化。
  5. 决定自动登录策略
    要实现"重启后无需人工介入"，需开启自动登录（系统设置 → 用户与群组）。代价是物理安全降低。如果放家里且无他人接触，可以接受。
  6. 处理 FileVault
    若开启 FileVault，重启后会停在解锁界面，所有共享服务都不启动。远程重启必须用：
    sudo fdesetup authrestart
    它会临时携带凭据重启，重启后磁盘已解锁、服务正常拉起。
  7. 关闭系统自动更新
    自动更新会在半夜自行重启，醒来就联系不上了。改为手动在方便时更新： 
    sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticCheckEnabled -bool false
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate AutomaticDownload -bool false
sudo defaults write /Library/Preferences/com.apple.SoftwareUpdate CriticalUpdateInstall -bool false
  8. 安装 Tailscale 并登录
    App Store 或官网下载，登录同一账号，记下主机名（默认就是机器名）。

6.2 显示输出（三选一）

你的客户端推荐的显示方案原因
macOS 高性能模式不需要额外配置会话内自带虚拟显示器
Jump Desktop不需要额外配置自带高性能虚拟显示器
Parsec / 标准 VNCHDMI 假负载 或 BetterDisplay它们捕获物理输出，无屏时拿不到正常画面

6.3 MacBook 端（4 步）

  1. 安装 Tailscale 并登录同一账号，确认 tailscale status 能看到 Mac mini。
  2. 测通路
    tailscale netcheck 看 UDP 与 NAT 类型
    tailscale ping mac-mini 看是 direct 还是 relay
  3. 装客户端
    跨网主力：Jump Desktop（Mac 版可先试用 14 天）
    局域网主力：系统自带「屏幕共享」App，连接时切到高性能模式
  4. 验证 SSH
    ssh <用户名>@mac-mini，能登录说明基础通路没问题。建议配好 SSH 公钥，免密登录。

6.4 上线前验收清单

检查项命令 / 操作期望结果

通路质量tailscale ping mac-minidirect 优先；relay 则<100ms 可接受

最后一项最重要

"重启后自愈"是无人值守方案的分水岭。很多人配好当天一切正常，第二天机器重启后彻底失联，而人不在家——这一项务必在上线前实测一次。

07故障排查

按症状定位，而不是靠猜

症状最可能的原因排查方法解决
局域网也连不上 共享服务未开，或防火墙拦截 sudo lsof -i :5900 看端口是否监听 系统设置里重新开关一次「屏幕共享」
Tailscale 里看不到对方 未登录同一账号，或设备离线 两端各跑 tailscale status 重新登录；确认 Mac mini 未睡眠
能连但分辨率锁 1024×768 没有虚拟显示器或假负载 主机端看「显示器」设置里有没有第二块屏 启用高性能模式虚拟屏，或装假负载 / BetterDisplay
画面糊、文字有彩边 用的是 VNC 标准模式（4:2:0 色度） 看客户端连接类型 切高性能模式，或换 Jump Desktop
鼠标有明显拖影 走中继，或编码器跟不上 tailscale ping 看是否 relay 先解决直连；再考虑换 HEVC 客户端
打字丢字、快捷键失效 弱网下客户端仍在硬撑画质 观察码率是否打满带宽 手动把码率限到 2 Mbps，优先保输入
重启后完全失联 FileVault 停在解锁界面 回想是否开过 FileVault 下次用 sudo fdesetup authrestart 重启
「高性能」选项是灰的 芯片不是 Apple Silicon，或系统低于 Sonoma 两端各看「关于本机」 无法满足则只能用第三方客户端
远程时家里屏幕黑着 高性能模式的隐私设计，非故障 — 正常现象；需要本地同时用就换标准模式
用一段时间突然断开 手机热点自动关闭 检查手机屏幕是否已熄 改用随身 Wi-Fi；或保持热点常开
时快时慢，晚高峰特别差 走的是跨境 DERP 中继 tailscale status 看 relay 名称 申请家宽公网 IP，或自建国内 DERP

一条通用排查顺序

遇到问题不要乱试，按这个顺序逐层排除，每层都有明确判据：

  1. 物理与电源——机器是否开机、是否睡眠（找一台在家的设备 ping 一下）
  2. 组网——tailscale status 是否 online，虚拟 IP 是否存在
  3. 通路——tailscale ping 是 direct 还是 relay，延迟多少
  4. 服务——5900/22 端口是否监听，SSH 能否登录
  5. 显示——是否有虚拟屏，分辨率是否正常
  6. 编码——连接类型、码率、客户端选择

前面五层都通了，第 6 层才有意义。跳过任何一层直接调后面的参数，都是浪费时间。

8.2 术语表

术语含义
EDID显示器向主机自报身份的协议数据，包含分辨率、刷新率、色域。假负载就是模拟这个。

  • Apple 官方支持文档《Mac 上的屏幕共享类型选项》——高性能模式的硬件、系统、带宽与端口要求
