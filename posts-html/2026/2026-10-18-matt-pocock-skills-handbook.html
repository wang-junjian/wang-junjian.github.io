CHAPTER 01

先想清楚：AI 原生开发到底改变了什么

为什么"会写 prompt"远远不够——这套技能集解决的真问题。

大多数人对 AI 编程的第一印象是：快。第二印象是：它怎么又自作主张了？

把"帮我实现这个登录功能"丢给一个全新的 agent，常见结局是它边写边重新设计你的方案——因为它手里只有一句话，没有被你否决过的三个备选、没有"我们必须兼容旧 token"这条约束、没有你项目里管"取消"叫 void 而不是 cancel 的惯例。它只能猜，而猜错了你也往往在三天后才发现。

Matt Pocock 的这套技能集（以下简称"这套技能"）给出的答案可以概括为一句话：

人负责决策，agent 负责执行，文件负责记忆。聊天框里什么都不会留下，文件才会。

具体拆开来是三个心智模型，后面所有技能都是它们的推论：

① 上下文窗口是会耗尽的资源

你在一场长对话里敲定的每个决定，都活在那个即将被清空的窗口里。所以要有 spec（规格）——一份"已做决策的记录"，让全新会话不用你重新解释就能接手。

② Agent 默认会发明流程

指着一份纯词汇参考说"开始吧"，agent 会自己编一个流程——重探你已探明的代码、跑很久才问你。所以"参考"和"司机"必须分清：有些 skill 只给词，有些 skill 负责开车。

③ 工件（artifact）优先于对话

问"这次改动安全吗"该得到的不是一段回答，而是一份带引用的文件；分工作该得到的不是聊天里的编号步骤，而是追踪器上一张带阻塞边的票。能留存的，才是交付物。

④ 模型不可全信，纪律兜底

模型会忘记 session 中段的挣扎、会凭摘要描述别的 skill、会过度触发正式流程。每个 skill 的"验收清单"就是为此准备的：别信它说"完成了"，对照清单验。

这套技能里几乎每个 skill 都带一份「It's working if / 怎样算正常工作」清单。老手和新手的差距不在会不会背流程，而在跑完会不会逐项验。把这份指南第 13 章的清单贴在手边，比记住所有命令更有用。

CHAPTER 03

动手之前：setup 与三件地基文件

每个仓库跑一次。它是其余一切技能默认你做过的事。

setup-matt-pocock-skills 回答三个问题：issue 住在哪、triage 标签叫什么、域文档放哪，答案写成 docs/agents/ 下的 markdown。核心设计思想值得单独强调：

这套技能的 skill 文件在任何仓库都一模一样，仓库之间唯一的差异是 docs/agents/ 里的几个 markdown。skill 运行时才读这些文件——所以换 tracker 永远改文件、永远不要改 skill 本身。这就是它不绑死 GitHub 的原因。

它写什么

  • docs/agents/issue-tracker.md — tracker 选择 + 工作流描述（含 wayfinder 的 "Wayfinding operations" 一节）
  • docs/agents/domain.md — 域文档布局
  • docs/agents/triage-labels.md — 仅当装了 triage
  • CLAUDE.md 或 AGENTS.md 里的 ## Agent skills 块 — 指向上面每个文件

tracker 四选一

选项需求备注
GitHub / GitLabgh / glab CLI出厂模板，开箱即用
Local markdown什么都不需要，连 remote 都不要完整选项而非退路；与 GitHub 是替代品，别同时用
Other你写一段工作流描述Jira / Linear / Azure DevOps / Beads 全走这条路；已有 Jira-over-MCP 等实例

CHAPTER 04

决策与词汇：一切的地基

grilling 家族、GLOSSARY.md 与 ADR——以及那两道最容易搞混的"写杠"。

所有 skill 的源头是一个共同原语：grilling——一轮问题、等你回答、再下一轮。套在它外面的三个 skill 各管一段：

grill-with-docs有仓库 · 单 session 规划
grill-me无仓库 · 纯访谈
wayfinder跨 session · 先绘图
to-questionnaire决策卡在别人的脑子里

grill-with-docs 与其他 grilling skill 的全部差别在于：它是 stateful 的——术语敲定那一刻就写进 GLOSSARY.md，决策过三道杠就落成一条 ADR。别的 grilling 把 session 留在你脑子里，它把文件留在磁盘上。

两个工件，两道杠

GLOSSARY.mddocs/adr/
装什么术语：一物是什么，一两句；弃用同义词列在 _Avoid_ 下一个决策：背景、选择、理由，一到三句
写杠一个含糊词被敲定三道全过：难逆转 + 无背景会意外 + 真实取舍
时机内联，敲定那一刻被提议，不是默认
永不装实现细节、spec、草稿、通用编程概念本场每个选择的日记
GLOSSARY.md 是词汇表，别的什么都不是。模型最常犯的错就是把它当"把你说的每句话都存下来"的许可——文件退化成一份运行中的 spec。你的词汇表膨胀到几百上千行时，病因几乎都是这个。解法是一句直接指令：「/grill-with-docs make my GLOSSARY.md more concise and remove any implementation details from it」。

词汇层：codebase-design 的七个词

这套体系给模块设计强制了一套语言：module（任何"接口+实现"的东西，与规模无关）、interface（签名 + 不变量 + 顺序约束 + 错误模式 + 配置 + 性能特征）、depth（每学一个单位接口能行使多少行为）、seam（不改此处就能改变行为的地方——Feathers 的术语）、adapter（接缝处满足接口的具体角色）、leverage（调用方得到什么）、locality（维护者得到什么）。

同时禁掉四个松散词：component、service、API、boundary。这条纪律看着形式主义，实际效果立竿见影——当讨论里有人说"这里该拆个组件"，你可以追问"拆出来的接口是什么、深度够吗、过没过删除测试"，争论就从口味变成可判定的题。

codebase-design 是参考，不是流程。指着它说"开始吧"，agent 会自己发明流程——有用户因此烧了 10 万 token 重设计了一堆没要求的东西。正确姿势：跑一个司机 skill（grill-with-docs、tdd、improve-codebase-architecture），让 codebase-design 当它们的词汇。同理 domain-modeling：grill-with-docs 说加载它时，模型经常只加载 grilling 把它跳过——判断法：一场 grilling 跑完 GLOSSARY.md 纹丝未变 = 它被跳过了，按名字把它和别的 skill 并列调用。
CHAPTER 05

规划阶段：从想法到可执行的票

to-spec 与 to-tickets——以及那个被违反最多的规则：竖切。

规划阶段只有两个 skill，但分工极清：

to-spec：只记录，不访谈

到你调用它时，决策已经做完。它综合对话、代码库、GLOSSARY.md 和 ADR，用你自己的词汇写下"已决定的事"。如果 spec 里出现了你没说过的东西，那是缺陷。它存在的理由：上下文窗口会结束。

to-tickets：切成竖切票

每张票是一发 tracer bullet：窄而完整、穿过 schema→API→UI→tests 每一层，落地即可独立演示，并声明阻塞边（哪些票必须先完成）。

竖切 vs 横切：一套技能里最重要的图

按层切（先全部 schema、再全部 API）是最直觉的分法，也是这套体系明确反对的分法：

  • 横切：全部落地前没有任何可演示的东西；每张票的验收标准要伸手到别的票的工作里。真实案例：一个 26 张横切票的团队，每张票关闭平均需要 ~20 次 agent 运行，其中约 75% 是返工——复盘把每一类失败都归因于切法而非实现。
  • 竖切（tracer bullet）：每张票落地即可演示、拥有它考核的一切；验证过的形状反过来锁定测试结构。
to-tickets 发布前会把编号清单交回给你审（粒度对吗？阻塞边是真的吗？要不要合并或拆分？）——你批准之前什么都不会进追踪器。这里是被报告最多的问题的修理厂：三行改动切出十二张票（过度分解，要求合并即可）；票按层出来了（逐票问"做完我能演示什么"，答不上来的就是横切片）。

两条容易忘的实操纪律

/to-spec 和 /to-tickets 之间不要 clear 或 compact。超大 spec 超出 issue 能干净回传的上限，又没有本地副本，agent 反复取块永远到不了头。同一个上下文窗口里跑完两者。

另外，装得进一个上下文窗口的改动根本不该走 spec+tickets——grilling 之后直接 /implement。spec 只在跨 session 的工作上才值回成本。

CHAPTER 06

构建阶段：一个人工位与一座工厂

implement 的"清空→一票→提交→再清空"，与 implement-spec 的并行编排。

implement：信任上游的工匠

implement 的立身之本：绝不重新打开计划。没有访谈、没有澄清轮、没有"换个方案怎么样"——上游敲定什么是输入，它的全部工作是把输入变成一个 commit。这正是它和对全新 agent 说"build this"的区别：后者常边做边重新设计。

一次运行五步：① 读票/spec、定接缝 → ② 在预先敲定的接缝上驱动 tdd（一个 red-green 切片接一个）→ ③ 频繁 typecheck、随跑单测 → ④ 收尾完整测试套件跑一遍 → ⑤ 跑 code-review，提交到当前分支。

节奏

清空上下文 → 实现一张 → 提交 → 再清空。每张 tracer-bullet 票按单窗口裁好，前一张的上下文直接丢弃。

动手前唯一要检查的事

它提交到你所在的分支——不建分支、不问。确认 HEAD 在你想要的分支上再开始。

它没有的步骤（都要你自己来）

没有完成步骤：跑完停在 commit，不关 ticket、不勾验收框、不处理 review 发现。依赖链上这最要命——frontier 只看"阻塞者全关闭"，你不关票就没有任何票 visibly 解锁。

token 预算的直觉

一张非平凡票烧过 10 万 token 是常态（探索 + 每接缝一轮 red-green + 全量测试 + review）。反复超限的票，解法在上游：拆票，不是调高档位。

implement-spec：一座工厂

整张 spec 一次落地时，调度者从"你"换成一个编排 agent：frontier 上的票全部同时开工，每个 implementer 在自己的 git worktree 里构建，汇入一条集成分支（fast-forward 合并），最后统一 code-review 并 resolve 票。

worktree 隔离了代码，隔离不了协调。三个最常踩的坑：① 两个并行 implementer 撞同一文件或给同一事物起不同名（解法：给两张 frontier 票之间补一条阻塞边，或在探索笔记里写死确切名称）；② GitHub 的 blocked-by 计数在 blocker 关闭前不下降，而票通常到 PR 合并才关闭——让编排者跟踪已并入集成分支的票来算 frontier；③ worktree 只有 git 跟踪的文件，读 gitignored fixtures / 本地库的测试会静默 skip 却报绿——这类票放主 checkout 跑。另外 review-fix 循环只该跑一次：code-review 对照整份 spec，只在全部落地后有意义；看到第二次宽泛 review 启动，告诉它"对已修发现跑 focused checks 然后停"。

tdd：方法论而非司机

tdd 是 reference：装着"什么是好测试"的规则，跑 session 的是 implement（或你）。要点三则：接缝在任何代码存在之前商定（未确认的接缝上它拒绝写测试——没人商定，运行就静默退化成"直接写码"）；三个让套件一文不值的反模式要会认——实现耦合（重命名内部函数测试就红）、重言式（期望值用代码同款算法算出）、横切（一批测试先于任何实现落地）；mocks 只用于系统边界，绝不 mock 自己的模块。

触发短语 "red-green-refactor" 仍有效，但 refactor 阶段已在 2026 年 6 月移除——重构归 code-review。诚实的边界：没有指令能让 agent 100% 依从循环，有模型坦白"我读了规则，只是默认回了老习惯"。某个切片必须严格依从时，盯着运行，别指望 skill 自己 enforcement。
CHAPTER 07

质量阶段：双轴评审与那句"门"的判定

code-review 拒绝混合裁决，pr 把直觉变成可反驳的明示。

code-review：两个互不见面的评审员

它评审 <fixed-point>...HEAD 的 diff，分两条轴、各由一个独立 sub-agent 跑：Standards（构建得对不对——仓库自己的规范 + Fowler 十二 smell 基线）与 Spec（构建的是不是对的东西——来源 issue/spec 逐条对照）。报告分两个块，每轴各给一个最差项，拒绝评总冠军。

混合裁决会让通过的一轴遮住失败的一轴：代码遵守每条规范但实现了错误的东西 → Standards 过、Spec 挂；照单全收但破坏仓库约定 → 反之。任何"总体打分"都丢了这条信息。另：它在 无 spec 时明说 "no spec available"，绝不从代码反推需求。
sub-agent 产出是假设不是证据——skill 不逐条回文件复核，发现可能引错位置或夸大影响。每条发现必须带引用（规则 / smell+代码段 / spec 行），动手前先读引用。另两条：它审的是三点式 diff，不含未提交改动——先 commit 再审；在写代码的同一 session 里跑它等于"带斜杠命令的确认偏误"，独立做法是自己从干净 session 调用。

pr：三段的正文，一段是主导想法

pr 只塑形正文、不开 PR：① Summary——是图不是段落，从六种视图（伪代码、调用树、组件树、文件树、Mermaid、shaped diff）里挑最小的讲清形状；② Evidence——前后对照（截图，或"曾失败现通过"的确切测试），"tests are green" 是主张不是证据；③ Merge Danger——一扇门（one-way：破坏性迁移、对外发出、公开 API 移除）还是两扇门，加爆炸半径。

door call 的意义是让它可反驳。写改动的人就是打分的人，所以 agent 说"两扇门、小爆炸半径"时要最警惕——"回滚 commit 不会撤回已发出的那批邮件"。两个动作：让 agent 手里有 ticket/spec 而不只是 diff；把你们仓库"永远视为单行道"的清单写进 agent 文档。
CHAPTER 08

收尾与保养：PR、复盘、代码库健康

retro 修环境不修代码；improve-codebase-architecture 修代码不修环境。

retro：把"这次教会的东西"固化下来

在"比本该更难"的 session 末尾跑 retro。它一行代码都不修——被 ship 的 bug、找了一万年的文件、reviewer 漏掉的规则，它一个都不直接修；它问"仓库里什么允许了它发生"，然后提议检查、指针或标准。只提议，你选中之前什么都不变（human-in-the-loop 是刻意的：判断什么值得变成永久检查需要人）。

核心路由规则

机械性错误 → 会失败的 check（lint/类型/测试/CI）；真正的判断题 → CODING_STANDARDS.md 里给 reviewer 的规则。标准属于 reviewer 不属于 implementer——实现 agent 上下文压力最大，reviewer 只拿 diff、有余地应用新规则。

它反驳最多的事

"agent 反复犯错就往 CLAUDE.md 加一行"——通常不要。CLAUDE.md 每行都加载进每个 session、稀释其他内容、随代码过期。AGENTS.md / CLAUDE.md 只留导航指针。

最弱点

它不审计自己上月提议的规则——只能删 prose，看不见某条 lint 是否已 fire 太频。在好代码上频繁 fire 的规则 = 该删的信号，修剪归你。

健康指标

AGENTS.md 随时间变短而不是变长；重复的错误变成会失败的 check；每个候选能指回 session 里的一个具体时刻（指不回去的 = 编的，丢弃）。

improve-codebase-architecture：周期保养的调查

每隔几天跑一次，扫描"浅模块可变深"的地方。两道过滤器挡掉泛泛建议：删除测试（删掉这个模块，复杂度退到更小接口后 = 配得一张卡；摊回调用方 = 不配）+ 聚焦常变路径（没人碰的代码里的加深永远不回本）。产出是一份 HTML 报告 + 你选中一张后的 grilling——产出决策，不是 diff，重构走正常构建流。

调用时想被问"怎么 prompt"：指着下一步要构建的东西问「how can we make this change easy?」——这是对它最有效的一句。报告几乎从不说"没问题"（它存在就是为了产出发现）：若一场全是 Speculative 徽章，那就是它"没找到"的表达方式。
CHAPTER 09

外来工作：triage 匝道

与自己规划的工作是两条平行车道，终点相同。

triage 只处理你没创建过的 issue：原始 bug 报文、外来功能请求、不请自来的外部 PR。它给类别（bug / enhancement）和五个状态（needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix）的建议，附带理由并停下来等你。

brief 之前先验证

bug 按 reporter 步骤复现；PR checkout 跑测试。三结果：Confirmed / 复现失败 / 细节不够（最强的 needs-info 信号）。同趟车跑冗余查 + 前次拒绝查，命中即 wontfix。

agent brief 是合同

写类型、签名、行为契约，永不写文件路径和行号（票可能躺几周，代码一直在变）。brief 贴上后，原报文只是上下文。

.out-of-scope/ 知识库

每概念一文件（非每 issue 一文件），按概念匹配——"night theme" 命中 dark-mode.md。被拒请求回来时，它引用旧理由问你还要不要坚持，而不是从头再吵。

最常撞的坑

to-tickets 的票已自动贴 ready-for-agent，别再 triage；bulk 跑 backlog 时它只读正文不读评论——明说"每个 issue 必须读评论"。

CHAPTER 10

大工程：wayfinder 与战争迷雾

装不进一个 session 的工程，先绘图，再逐个清空。

wayfinder 的触发条件极窄：工程大于一个 session，且路线看不清。分界是 session 数而非项目大小——一场对话装得下就 grilling，装不下才 wayfinder。greenfield 不是前提：legacy 的雾常是"这里已经什么是真的"。

地图的四节

  • Destination——地图尽头的样子，在任一 ticket 存在之前命名（指整个地图的尽头，不是本场 session 的）。
  • Decisions so far——每个已关闭 ticket 一行 + 链接。地图是索引不是仓库：决策只活在它的 ticket 里。
  • Not yet specified（战争迷雾）——看得出要来、还说不清的问题。雾 vs ticket 的测试：你现在能否精确陈述这个问句（不是能否回答）。resolve 一张票，它前方的雾散开，能说清的毕业成新 ticket；Out of scope 永不毕业。
  • Frontier（前线）——开放的、无阻塞的、未被认领的票；认领 = assign 给自己。

四种决策 ticket

类型模式何时用由谁 resolve
grillingHITL默认；能聊透的问题grilling + domain-modeling，新 session
prototypeHITL"该长什么样/该怎么表现"，聊不决prototype，ticket 链接工件
researchAFK外部事实挡着决策research subagent 并行跑（唯一可并行的类型）
taskEither无决策可定但手工劳动挡路agent 能独立做就独立做
「plan, don't do」的默认可以在地图 Notes 里被覆盖——但 Notes 是被约束的 agent 自己写的。有用户看着 agent 把 "this map carries execution" 写进自己的 Notes，后续 session 读成许可在 live server 上开建。修复前：读一切非你绘图的地图的 Notes；任何看着像构建切片的 wayfinder:task 当作类型标错。
27 张票走到第 13 张时其余全作废的瀑布陷阱，两味药：地图绑有界的 destination（一个定义好的 epic，而非"实现 V1"）；激进 prototype ——廉价具体工件在实现依赖不确定性之前暴露它。wayfinder 是 "prototypemaxxing"，不是 "planmaxxing"。清空后的地图必须过 /to-spec #<map_issue> 收拢——直接灌进 implement 会丢掉链接细节。
CHAPTER 11

独立工具箱：原型、调研、向导、交接

四个"随时取用"的 standalone，各自守着一条清晰的边界。

prototype · 回答一个问题的用完即弃代码

"用完即弃"约束的是写法（无测试/无错误处理/无抽象），不是销毁承诺。两个幸存者：答案进 main，原型进 prototype/<name> 分支永不合并、issue 留指针——下一个接手的人要的是能重跑的证据，不是 prose 摘要。逻辑分支产出单个可双击分享的 HTML；视觉分支产出结构互不同意的多变体。开始加固它 = 停止原型。

research · 读一手来源的委托

答案不落进对话，落进一份每条声明带链接的文件。分界线是保质期：事实（短寿）→ research；决策（耐久）→ grilling / grill-with-docs。你唯一的质检是引用——随机跟两三条，落在"关于它的转述"而非"它本身" = 这场失败。委托后盯后台任务列表：恰好一个新任务，多出来的分身停掉（已知嵌套 bug，单任务烧过 45 万 token）。

wizard · 自动化的尽头

agent 撞上只有你能点的 dashboard 时，它写脚本、你本机跑——key 盲输直写 .env/gh secret，不过模型上下文。先确认有序 stage 清单再生成；没有后退键，答错 Ctrl-C 重跑（已存的值回显为默认值）。比写进 README 强：某一步失效时它显眼地失败，而不是安静地错。

handoff · 标准交接

session 太大、换 harness、同事接手、mid-phase 分支线——该搬的不是聊天记录而是"决策 + 指针"。它是把上下文当一等公民搬运的纪律，进图出图两侧都靠它。

CHAPTER 12

出问题时：六相诊断法

diagnosing-bugs 的铁律：没有红的循环，就没有理论。

给定 bug report，coding agent 的默认动作是读代码然后猜。diagnosing-bugs 把这条路堵死：在一条"紧的反馈环"存在之前，不允许形成任何理论。紧 = 秒级、确定性、断言的是你那个确切症状、agent 无需你就能跑。

① 造环十种下环方式，最难的一相
→
② 最小化每个元素都说得出必要性
→
③ 假设排序3–5 个，带可证伪预测，先给你看
→
④ 插桩一变量一探针，[DEBUG-xxxx] 标签
→
⑤ 修复+回归测试接缝太浅就明说
→
⑥ 收尾环绿、插桩清零、commit 点名对的假设
间歇性 bug 的目标不是干净复现，是更高的复现率——循环触发、并行、加压、注入 sleep。造不出环时它必须停下来向你要环境权限，绝不"先提假设再说"。最快的健康检查：理论先于红色输出出现 = skill 没在跑。
两个现实提醒：它现在没有专门 skill 时 agent 也能解 merge 冲突，但"先回溯两边意图（commit/PR/issue）、兼容处都保留、提交前跑检查"仍是好纪律，值得在 prompt 里手动要求；复现输出可能含凭证——脱敏是你自己的活，尤其在外发之前。

CHAPTER 14

上手路线：第一周该怎么跑

从 setup 到第一个 retro 的最短路径。

  1. 第 0 天 · 打地基：在一个真实仓库跑 /setup-matt-pocock-skills。确认 docs/agents/ 三个文件和 CLAUDE.md/AGENTS.md 的指针块都在——以及它们在你的 harness 实际读的那个文件里。
  2. 第 1 天 · 小改动热身：挑一个装得进单窗口的小特性。/grill-with-docs 敲定 → 直接 /implement。故意跳过 spec 和 tickets，体会「什么尺寸才值得拆」的那条分界线。
  3. 第 2–3 天 · 完整主链：一个稍大的特性走全链：grill-with-docs → to-spec → to-tickets → implement（逐票、票间清空）→ code-review → pr。重点体验两件事：to-spec/to-tickets 之间不清上下文；implement 跑完自己关票。
  4. 第 4 天 · 复盘与保养：对昨天那场跑 /retro，挑一条候选落地（比如一个会失败的 check）。顺手跑一次 /improve-codebase-architecture，感受"调查不改码"的节奏。
  5. 第 5 天 · 独立工具：各抽十分钟试 prototype（一个聊不决的小问题）、research（一个等事实的决策）、wizard（一个要配的服务）。
  6. 持续 · 形成反射：困惑时 /ask-matt；外来报文进 triage；硬 bug 进 diagnosing-bugs；每隔几天 wayfinder/improve-codebase-architecture 做保养。每周把第 13 章清单过一遍。

最后一条经验：这套技能集最强的部分不是任何单个 skill，而是它背后的态度——把"AI 写代码"当成一门需要流程、词汇和纪律的工程学科。工具会过时（resolving-merge-conflicts 已因模型进步归档），纪律不会。

本指南基于 mattpocock/skills 技能集文档整理编写，供学习参考。文中命令、issue 编号与版本信息以官方仓库为准。

结构：定位 → 选型 → 核心判断 → 陷阱与验收 · 与技能集本身同一套骨架。
