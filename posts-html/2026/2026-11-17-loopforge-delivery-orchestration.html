LoopForge：把编码智能体
收进可冻结的交付流程

腾讯轻量云团队开源的自托管平台，把 CodeBuddy、Codex、Claude Code 等十余种编码 CLI 变成可替换的执行器， 用 SOP 图、确定性脚本和人工关口把「一次运行看运气」变成「每次运行同一套检查」。 这份报告不复述它的功能清单，而是回答三个问题：它究竟在什么坐标系里、它的「自进化」到底能改什么、 以及一个团队在什么条件下不该用它。

判断 01

它不是 Agent 框架，是交付编排层。整个 Go 后端不依赖任何 LLM SDK——go.mod 里只有 gin、gorm、websocket、pty 这类基础库，模型能力全部来自被当作子进程调起的 CLI。所以它的技术护城河不在「怎么调用模型」，而在「谁在什么沙箱里按什么顺序做、由谁签字」。

判断 02

核心抽象不是工作流图，是「冻结」。SOP 版本不可变、运行快照冻结沙箱定义、检查点写进 run JSON 而不是模板库、沙箱 profile 随运行冻结。改一次 SOP 不会影响在跑的交付，重试能重建当时的确定环境——这是「可复现交付」真正的地基，也是绝大多数 Agent 产品缺的那一层。

判断 03

「自进化」被刻意关进了笼子。复盘引擎让模型对 6 个维度打分、开「处方」，但可应用的动作只有四种：改节点的 4 个标量字段、增门禁、删门禁、往角色提示词末尾追加文本。提示词里明令禁止「整份重写 SOP 或角色、不要改边或删节点」，总分还由服务端按权重重算、不采信模型自报。这是「受限自我修改」，不是自主重写。

判断 04

它最硬的设计是「不信任 Agent 的自述」。三种门禁正交：command（退出码说了算）、manual（人说了算）、mr（平台去代码托管方查 PR 是否真的指向推送的那个 commit）。0.4.0 新增的 MR 门禁会拒绝「声称已提 PR 但没提」「提到错分支」「只留了一个早先合过的旧 MR」三种情况。

判断 05

护城河是「多宿主投影」，代价也是它。同一套契约投影到平台 5 类节点与 Local 版 7 个宿主适配器；10 种 CLI 的凭据按责任人隔离、每个运行有私有 HOME、MCP 配置互不污染。代价是永无止境的适配长尾——公开 changelog 里大量条目是单个 CLI 的截断、装不上、能力被 drop 后 tar 改不了属主这类具体坑。

判断 06

安全模型是「内网可信团队」，不是多租户 SaaS。平台通过宿主机 Docker socket 起沙箱，官方文档自己写明这等于 host root；默认监听 0.0.0.0:8090 且开放自助注册；绑定的仓库里如果有 agent 配置或 hook，那段代码会被执行。第三方评测把这三条列为首要风险，这与官方「可信团队、不构成不可信多租户隔离边界」的表述一致。

判断 07

这是一次「主干分叉出口」，不是从零起步的社区项目。它保留了上游 Go 模块名 agentflow、包边界和 AGENTFLOW_ 环境变量前缀，公开说明是为了「减少持续的合并冲突」；1,718 个源文件里 1,466 原样、178 适配、74 排除、58 新增。维护者的同步记录留在私有侧——这意味着长期供给节奏取决于内部主干，而非社区 PR。

判断 08

它的可持续性风险不在技术，在治理与运维。16 位贡献者、175 个未关闭议题、11 天发 9 个版本的节奏，加上「升级必须手工执行 SQL 迁移」「对话工作台仅中文」「需求澄清/评测/通知汇总锁死 CodeBuddy 模型」这几条，共同决定了它当前适合「有平台工程能力、能接受粗糙边缘的内部团队」，而不是「装上就用的产品」。

一句话判断

LoopForge 值得研究的地方不是它支持十个 CLI，而是它把「Agent 说自己做完了」这件事拆成了三道可外部验证的证据：退出码、人去签字、托管方的 PR 状态。这三道证据串起来，才是「团队级 Agent 交付」和「个人 Vibe Coding」的真实分界线。

01范式定位：它在哪个坐标系里

「AI 工作流平台」是一个被用滥的标签。要判断 LoopForge 是什么，先得给出这一类系统的判别条件，再看谁真的满足。

四条判别式：什么才算「团队级 Agent 交付系统」

把「能让 Agent 写代码」当成一个品类，会把 Copilot 补全、Claude Code 终端、Devin 云端工单、n8n 流程编排全部塞进同一个抽屉。它们解决的问题完全不同。真正构成一个新品类的，是同时满足下面四条的系统：

  1. 独立执行环境。任务不寄生在人正在用的终端里，而是跑在平台管理的容器/工作区里，可以跨设备、跨时段续跑。
  2. 角色上下文分离。写代码的和评代码的不是同一段上下文——否则就是「自己改、自己批、自己宣称通过」。
  3. 确定性门禁。「做完了」由退出码、托管方状态或人签字来判定，而不是由模型自述判定。
  4. 可查留痕。任意一次交付都能回溯：谁在什么 SOP 版本下、由哪个角色、在哪个沙箱、经过哪几次打回、由谁放行。

这四条缺一条，系统就退回成「更花哨的聊天框」或「更贵的 CI」。以此为尺，各派产品的落位就清楚了。

一处坐标系错位

README 的 FAQ 主动把自己与 Dify / n8n / Flowise 对比，但这个对比其实削弱了它：通用工作流平台根本不是它的替代品（没有编码语义），真正的替代品是「托管编码智能体」和「团队自建的 CI + CLI 脚本」。前者赢在零运维，后者赢在完全掌控——LoopForge 的全部设计张力，都在这两者之间。

02演进动机：五个阶段，五次把「依赖人」换成「机制」

官方叙事是一条五级阶梯。这一节把叙事与代码证据对齐：哪些阶段有实现支撑，哪些说法需要打折扣。

腾讯轻量云团队在发布文章中把自己的演进拆成五步，并明确说「不是第一天就设计了一套庞大架构，而是顺着团队真实落地的痛点，一步步跨过五道坎」。这个自述值得认真对待，因为它解释了产品为什么长成这样——每一层能力都对应一个具体的失败模式，而不是功能清单上的一个勾。

需要打折扣的两处说法

「已服务内部 20+ 业务、单月自动完成 200+ 需求与单据」——这个数字来自官方公众号，没有任何第三方审计或可复现口径（是「自动完成」还是「自动跑到人工关口」也没有区分）。按证据分级属于厂商自报，可以作为量级参考，不能当作已证实的生产能力。

「自动改写 SOP 节点 / 进化流程拓扑」——发布文章的表述容易读成「系统能自己重写流程图」。但 runeval/apply.go 的 update_node 只允许改 maxAttempts、maxReworks、onFailure、retryStrategy 四个标量字段，且提示词明确写「不要改边或删节点」。两者不是同一个东西，详见第 06 章。

把这两处折扣打完，剩下的部分反而是更硬的结论：这个系统真正的创新点集中在第 ③ 层——把「角色、门禁、产物契约」做成可版本化的资产，并让失败有结构化的去处。第 ① ② ④ 层是必要的产品化外壳，第 ⑤ 层目前是参数层面的微调器。

03架构：五层分离，以及「冻结」这条暗线

从目录职责能读出一个系统真正的切分方式。LoopForge 的切分很规整，但它真正的设计意图藏在数据结构的注释里。

为什么切得这么规整

docs/architecture.md 给出一张极短的职责表，值得整段引用它的切分逻辑：cmd/ 下四个二进制（API/worker 合体、runner、公开 MCP、结构化门禁 MCP）；internal/engine 管图、租约、调度、沙箱生命周期与交付；internal/repo 管持久化且「一个业务域一个仓储」；internal/httpapi 同样「一个业务域一个 handler」；internal/runtime+internal/runner 管执行器协议、凭据、隔离与产物；internal/tracker 管远程 issue/PR 适配。

这套切法的直接后果是：「换一个编码 CLI」和「改一条 SOP」互不影响。前者只碰 runtime/runner，后者只碰 domain/engine。这也是它能同时支持十个 CLI 的结构性原因——不是适配做得多，是适配被关在了一个足够小的盒子里。

一个反直觉的数字：整个 Go 后端 go.mod 的直接依赖只有 12 个（gin、gorm、mysql、sqlite、websocket、pty、yaml、compress、crypto 等），没有任何 LLM SDK。模型能力百分之百通过子进程调用 CLI 获得。这意味着它不处理 token 流、不实现 function calling、不管采样参数——这些全在执行器黑盒里。

「冻结」：读注释才能看见的设计意图

如果只看功能列表，会以为核心抽象是「工作流图」。但 internal/domain/workflow.go 的注释反复指向另一件事：把「当时的样子」冻住。

  • SOPCheckpoint 的注释是「frozen in the run JSON, never in a catalog definition」——检查点属于那次运行，不属于模板。
  • SandboxSnapshot 只在 Run.WorkflowSnapshot 上填充，冻结解析后的 profile 与 Dockerfile/环境载荷，「so retries can reconstruct the original environment after catalog definitions change」——模板改了，重试仍重建原来的环境。
  • Preview 契约「frozen into the run snapshot so later SOP edits cannot change an in-flight archive」——正在跑的归档不会被编辑影响。
  • DefinitionRevision 是 workflow/agent 的不可变快照，用于 diff 与回滚。
  • MetricCategory 在 Run 创建时随 WorkflowSnapshot 冻结，「历史执行不受后续编辑影响」。

这五处指向同一条原则：运行中的一切以快照为准，模板只影响下一次。多数「AI 工作流」产品做不到这点——它们把流程存在一张会变的表里，于是「三个月前那次交付到底按什么流程跑的」永远说不清。对需要审计的团队交付来说，这条比任何 Agent 能力都重要。

证据强度说明

上面五处「冻结」全部来自源码注释与结构体字段，属于一手实现证据；「多数产品做不到」属于分析者判断，未做竞品逐一核验，标注为观点。

快速迭代留下的痕迹

工程卫生上有几处值得记录的粗糙边缘，它们不影响正确性，但能反映节奏：migrations/ 里 016 和 024 各出现了两个不同内容的文件（016_mr_delivery_merged_at 与 016_public_optional_repositories 并存），说明并行开发时编号撞车；而 033_generic_sop_mr_node.sql（22 KB）要在升级时手工执行才能给已有安装补上「发起 MR」节点——因为 gorm 的 AutoMigrate 建不出生成列，这类迁移只能显式写 SQL。这个约束在 0.4.0 的变更日志里被反复提及，也成了自托管运维的主要摩擦点之一。

04执行模型：门禁是三种异构证据，不是一个「通过」按钮

这一章是 LoopForge 最值得抄的部分。它把「做完了」拆成三种互不替代的判定，并给失败设计了四个有区别的出口。

五类节点，各管一件事

节点类型谁来执行成功的判据典型用途
Agent一个角色：提示词 + 执行器 + 模型 + 规则 + Skills + MCP 工具产出声明的产物，并通过该角色的门禁澄清、设计、实现、评审、测试
Script确定性 Shell / Python退出码构建、单测、Lint、生成报告
Approval人点通过，或打回到指定节点验收、上线前签字
Sub-SOP另一条 SOP 作为子流程子流程终态复用一套既定流程
Preview build平台静态站点构建并归档前端交付物供人评审

值得单独说的是 Script 节点。它在宣传里最不起眼，却是设计上最清醒的一处：不需要推理的地方就不放模型。测试要么过要么不过，这件事交给退出码比交给模型便宜三个数量级，也可靠三个数量级。多数「Agent 工作流」产品的失败，恰恰是把「跑测试」也做成了一次模型调用，然后收获一段「我已经运行了测试，看起来都没问题」。

MR 门禁：把「我真的提了 PR」变成可外部验证的断言

v0.4.0 新增的 mr 门禁是全系统最锋利的一处设计。它的判定条件写得非常具体（以下为变更日志的实质内容）：

  • 对运行中每一个可写仓库：如果它的工作分支在 origin 上已超出目标分支，就必须存在一条从该工作分支指向该目标分支、且 head 为已推送 tip 的 MR/PR；
  • 「开放且 head 是这次 tip」可以，「已合并且 head 是这次 tip」也可以；
  • 「Agent 报告通过但其实没提」「提到错的分支」「复用旧工作分支从而只留了一个早先合过的 MR」——三种都到不了交付汇总；
  • 查询以运行的身份执行：GitHub 用运行推送时的 Git Token（责任人的），退化到项目 Owner；工蜂走项目 MCP 作为责任人；
  • 平台查不到的主机（SSH 仓库、查询失败）直接转 human，不猜。

这段逻辑的价值不在复杂度，而在它承认了「Agent 会谎报」这个前提。绝大多数 Agent 编排系统把「请提交 PR」写在提示词里，然后相信模型的复述。LoopForge 选择再花一次网络请求去托管方核实——这是把可信度建立在协议而不是模型品格上。

可迁移的设计

「门禁必须在系统外部找到证据」这条原则可以套到任何场景：不是问 Agent「你跑测试了吗」，而是看 CI 的 job id；不是问 Agent「你改了几个文件」，而是 git diff --stat；不是问 Agent「需求理解对了吗」，而是让人在一张结构化报告上签字。每一条都可以照抄。

并行、取消与恢复：并发语义写得很细

架构文档里有一句容易被忽略的话：「Ready branches execute together in the run workspace; rerunning one branch after a cancel restores cancelled siblings」。翻成工程语言是：同一张图里互不依赖的分支并发执行，共享同一个运行工作区；取消后再重跑其中一条，被取消的兄弟分支会被恢复，而不是留下半截状态。

配合执行侧的租约设计——默认 TTL 30 秒、会话心跳 45 秒、且「心跳年龄按写它的数据库时钟计算，所以 API 主机与 MySQL 的时钟偏移既不会误杀活着的轮次，也不会让死掉的轮次赖着不走」——可以看出这套东西是在多副本、可崩溃的环境里被真实打磨过的，不是单机 demo 的延伸。

05沙箱与凭据：三次被自己的编排层咬到

编排层的安全风险不在模型，在「它必须同时掌握宿主机、仓库和密钥」这件事本身。LoopForge 的公开记录里有三处真实的踩坑与修复，比任何架构图都更有说服力。

边界声明写得很直白

官方部署文档的原话是：默认 Compose 安装下，SOP 运行与对话工作区都使用 Docker 沙箱容器，由平台通过宿主机 Docker socket 启动；而 Docker socket 赋予平台控制宿主机 Docker 的权限，因此「只适用于可信团队，不构成不可信多租户隔离边界」。同一处还写明新安装默认监听所有网卡、已登录用户可以读取实例内各项目数据、团队成员可自助注册。

第三方评测在独立读过代码后得出同样结论，并额外指出两点：容器内的 Agent 以完全权限运行（包括 Claude Code 的 permission-bypass 模式）；绑定的仓库如果自带 agent 配置或 hooks，那段代码会被执行——所以只能接可信仓库。这三点加在一起，画出的边界很清楚：它是一台放在内网里的团队工具，不是一个可以直接暴露到公网的 SaaS。

这种「主动写清边界」的做法本身值得记一笔

大多数自托管项目会把「Docker socket 等于 host root」这类事实藏在脚注里。LoopForge 把它写进 README 的部署边界段，并在 0.3.8 专门加固了 header 身份认证（带转发头的请求默认忽略身份头，除非网关同时提供共享密钥）。这是一种「先承认攻击面，再逐条收窄」的工程态度。

踩坑一：加固把沙箱自己锁在门外

公开验证记录里有一个非常具体的故障：宿主上的平台服务以非 root 用户运行，工作区目录权限是 0700；而沙箱镜像以 root 启动并丢弃全部能力（all capabilities dropped），结果连 cd /workspace 都失败——因为 root 在无 DAC_OVERRIDE 能力时，并不能越过权限位进入别人的目录。

修复方式不是放宽权限，而是让默认/root 镜像在宿主服务为非 root 时改用该服务的 UID/GID，同时保留显式指定非 root 用户的情形。回归测试以 UID 1001 真实复现了原始失败，并验证了修复后「宿主可读输出、0700 权限不变、有效能力为零、NoNewPrivs=1」四条同时成立。

这个小故事的技术含金量在于：它证明了加固是真的，不是文档里的一句形容词。零能力 + NoNewPrivs + 属主严格匹配，代价是几乎所有「先跑起来再说」的脚本都会在这里翻车。

踩坑二：密钥出现在自己的运行日志里

v0.4.0 的变更日志里有一条自我披露：运行日志与遥测此前会打印完整的 docker exec 命令行，里面包含 DEEPSEEK_API_KEY、以及配自定义 Base URL 时用的 AGENTFLOW_CLI_API_KEY，明文，且项目成员可读。修复是把所有以 _API_KEY、_TOKEN、_SECRET、_PASSWORD 结尾的环境变量统一脱敏，并明确建议「在此版本之前跑过 SOP 角色的密钥请轮换」。

同一版本还修了另一条同源问题：仓库的 cloneUrl 里如果带用户名密码（形如 https://user:token@github.com/...），此前会被接受并落进每个工作区的 .git/config，Agent 可以读到；现在保存时直接拒绝并提示改用个人 Git Token，而历史数据在 API 返回时也会被剥离。

这两条值得所有做编排层的人抄在墙上

编排层是密钥的必经之路。它必须把凭据交给子进程，所以「命令行的完整展开」天然就是一条泄漏通道——而这条通道恰好最容易被日志、遥测、错误上报三件事同时捕获。默认策略应该是：任何进入 exec 参数的东西，先过一遍脱敏白名单，再考虑要不要记。

踩坑三：每个会话一个 HOME，磁盘被自己吃光

为了让十个 CLI 的凭据与 MCP 配置互不污染，每次运行都跑在私有 HOME 里。这带来一个直接的副作用：CodeBuddy 会在每个 HOME 里下载内置插件市场，一个会话约 72 MB；删除会话时，它的共享原生根目录没被清掉，每个约 73 MB，于是「一个定时任务每轮替换上一次运行」就变成每轮涨一个目录。修复后新会话占用降到 1 MB 以下，并加了每日 janitor 清理已删会话遗留的根目录。

这三个坑有一个共同结构：它们都不是算法问题，而是「编排层同时拥有太多权限」的必然副作用。这也解释了为什么第 03 章那张图里接口层会有 430 个文件——产品化的成本几乎全部花在处理这类「耦合产生的长尾」上。

06「自进化」到底能改什么：一份白名单的完整解读

官方称之为「工程级 RSI」。这一章把它的实现完整拆开——包括那些它明确不允许自己做的事。

闭环的形状

每次 SOP 运行结束后，复盘引擎会把这次运行压缩成一组结构化事实（不是原始日志），交给模型按固定维度打分并开处方，处方以「待批准」状态入库，人审后由 runeval.ApplyRecommendation 写回 SOP 或角色定义，产生新版本。下一轮运行用新版本。

六维评分：评的是「流程健康」，不是「代码质量」

把维度名称读一遍会发现一件事：这六个维度全部可以被埋点直接测出来，模型在这里的作用是「把数字讲成原因」，而不是「凭感觉打分」。control 对应 attempt/reworkCount 与 pingPong 列表；tools 对应 toolRepeats（同工具调用次数与失败数）；latency 对应墙钟与执行时长之差；delivery 对应产物数与门禁事件数。这是一个「先用埋点把事实结构化，再让模型做归因」的正确顺序——反过来（先让模型读日志自由发挥）几乎必然产出无法验证的空话。

白名单：它拒绝改什么，比它能改什么更重要

ApplyRecommendation 的 switch 一共就四个分支。把 update_node 内部的字段校验展开，就是这张表：

提示词侧的约束写得更死，原文是：

「不要整份重写 SOP 或角色，不要改边或删节点。」
「门禁只属于角色；改门禁用 target=agent + upsert_gate/remove_gate。」
「recommendations 可为空。可应用时 action 只能是：update_node、upsert_gate、remove_gate、append_task_prompt。」
判断

这就是「受限自我修改」（bounded self-modification）：系统可以调整自己的参数、增加自己的检查、延长自己的经验，但不能重画自己的流程图。所有结构性问题——少了一个评审环节、两个节点该并行、某个角色该拆成两个——都必须由人改。这个边界选得很准：能自动化的部分恰好是「可枚举、可校验、可回滚」的那部分，而拓扑改动最容易引发不可预期的连锁反应，成本也最高，留给人最划算。

它的两处真实局限

  • 不能做结构性优化。如果一次交付的根因是「需求澄清和方案设计之间缺一个接口评审」，复盘只能说「control 维度低、建议加一条门禁」——它无法在图上插入一个节点。官方文章举的例子（缺权限校验 → 加一条「必须写数据权限」的规则 + 加一条「越权检查」门禁）刚好落在能力边界之内，所以效果看起来很好；一旦问题真出在拓扑上，这套机制就会退化成「加更多检查」。
  • 评分口径与账单真值有距离。Token 成本按公开标准价核算，官方文档自己说明这不等于发票金额（企业折扣不同）。因此 tokens 维度只能用于相对比较（同一 SOP 的两个版本谁更省），不能用来做预算承诺。

一句话总结这一章

LoopForge 的 RSI 不是「AI 自己改进自己」的科幻叙事，而是一套「把人肉复盘固化成可审计补丁」的流水线：埋点负责给事实，模型负责写归因和补丁，人负责批准，版本系统负责回滚。它真正的贡献是把「复盘」从一次会议变成一条有数据结构的流程——这比它能自动改多少东西重要得多。

07Local 版：把同一套语义压进一个文件状态机

平台版需要 Docker、MySQL、账号体系；Local 版只需要 Node 20+、Python 3.8+ 和一个已经装好的编程助手。它的设计取舍比平台版更值得学。

两条产品线，一个发布合同

Classic（默认）Portable
事实源.codebuddy/ 是参考行为，.codex/ 原生适配，.cursor/ 与 .claude/ 由 build-classic-hosts.py 生成skills/ 是唯一事实源，manifest.json 管跨宿主清单

互斥规则同一项目里同一宿主只允许启用一种 edition；切换必须 install --force。这是发布合同，不是运行期开关——因为两套工作流同时加载会争抢状态与产物目录。

「生成器 + 单一事实源」这个选择看起来平常，但它解决了一个真实痛点：同一套工作流要装进 Claude Code 的 commands/、Codex 的 skill 目录、Cursor 的规则目录、CodeBuddy 的 agent 目录，四者的文件格式与发现机制都不同。如果每个宿主各维护一份，三个月后它们一定会分叉。LoopForge 的做法是把「逻辑」留在唯一事实源，把「格式」交给生成器与 adapter。

路由：先定规模，再定阶段

Local 版的状态机写死了两条路由，规模判定按影响范围而非代码行数：

small

PHASE-0 → SOLO → SUMMARY

单模块、预计不超过 3 个文件、无接口/数据/架构影响。SOLO 内部仍须完成计划、实现、自审与针对性测试，只是合并为一个阶段。

medium / large

PHASE-0 → REQUIREMENT → DESIGN → IMPLEMENT → REVIEW → TEST → [KNOWLEDGE] → SUMMARY

跨模块或 4–10 个文件为 medium；涉及接口、数据模型、迁移、架构或高风险发布为 large。KNOWLEDGE 是条件阶段，没有可复用知识时须显式写「跳过 + 理由」。

三处值得抄的细节

① 越界必须显式升档。SOLO 阶段一旦发现超出 small 的边界，状态机要求以 overflow 结果结束并升级到 medium 路由，而不是「先做完再说」。范围蔓延被建模成一个状态转移，不是一次心照不宣的妥协。

② 不支持的能力不许伪造。medium/large 默认用 isolated 模式（每个阶段一个独立子 Agent）。宿主不给 subagent 工具时，adapter 必须记录具体原因并把流程降级为 single-context；Hermes 缺 delegate_task 时同理。文档原话是「不会伪造 isolated 执行器」。

③ 只有拿到真实执行器 ID 才允许登记。assign 的前置条件是宿主真的返回了 executor ID。这条防的是「提示词里写了要开子 Agent，实际上还是同一个上下文在硬干」——而这恰好是单 Agent 冒充多 Agent 最常见的失败模式。

产物契约比流程更硬

一次 Local 流程会在项目里固定生成一棵产物树：artifacts/<task-slug>/ 下按阶段分目录，需求报告、技术设计、执行计划、变更报告、审查报告、测试报告、知识报告、总摘要各就各位。每个阶段只接收 manifest 声明的精确产物，提示生成器从已验证产物里确定性抽取当前角色需要的章节作为交接，默认不再打开上游全文。

这条规则解决的是长链路 Agent 最常见的退化：上下文越滚越长，上游对齐的边界条件被淹没在几十轮对话里。用文件做交接，等于给每个阶段划了一条「你只能看这几份已冻结的结论」的边界——既压缩了 token，也让「下游漏改」有了可归因的对象（是交接物没写清，还是下游没读）。

实现规模：核心状态机 workflow_state.py 约 57 KB，只依赖 Python 3.8+ 标准库。连 PyYAML 都没有时，Classic 的 hook 仍保留人工门禁而不是静默放行。这种「零依赖 + 缺依赖时降级但不放水」的组合，是它能塞进任意仓库的前提。

08开源工程：一次带哈希的对账，而不是一次代码搬运

这个仓库最不寻常的地方不是代码，是它把「从内部系统开源」当成一次可审计的迁移来做，并把过程记录一并交出来。

三个决策，每个都能省下未来几百小时

  1. 不改模块名。go.mod 第一行是 module agentflow，环境变量全是 AGENTFLOW_ 前缀，架构文档明说这是为了「reduce ongoing merge conflicts」。放弃品牌一致性换同步成本，这个取舍在企业开源里经常被做反（改名很爽，之后每次同步每个文件都是冲突）。
  2. 把审计做成工具链。check-upstream.py 会拿记录里的 1,715 个源文件哈希去比对真实 Git blob，并确认记录的 commit 与 origin/master 一致；公开内容检查器另跑一遍。审计不是一份文档，是一条能复跑的命令。
  3. 把「不公开的部分」也讲清楚。部署密钥、生产数据、私有基础设施被排除；企业 tracker 的 Web 入口默认隐藏但兼容代码保留；公开的 SOP 定义是显式的 catalog 数据（migrations/seed/001_public_catalog.sql 约 44 KB），官方明确说明「不是对包含私有生产项目或提示词的声明」。

代价与它的必然结果

这套机制的直接后果是：最核心的演进发生在私有侧。社区可以提 PR、可以修 bug、可以加执行器适配，但「下一次同步把哪些上游变更带过来」由维护者私有清单决定。所以它更像「一条长期主干的公开出口」，而不是「一个由社区共同演进的项目」。这不是缺陷，是选择——但它决定了你不能把自己的产品路线押在它的社区节奏上。

一条元证据

这个仓库最有说服力的一件事，是它自己披露了自己的事故：API Key 出现在运行日志、clone URL 里的凭据落进 .git/config、非 root 宿主的 0700 目录让沙箱进不去、删除会话残留 73 MB。这些细节只有真正跑过生产的人才会写进 changelog。对评估者来说，这种自我披露的密度，比任何「生产级」形容词都更有信息量。

10代价：它把复杂度从「模型」搬到了「运维」

任何编排层都不是免费的。LoopForge 的成本几乎全部落在部署、升级和人身上，而不是算力上。

成本项具体表现谁来承担
部署门槛需要 Docker + Compose + Python 3 + curl；./start.sh 拉取 pin 住的 GHCR 镜像，不在本地构建。国内拉取常中断，需设 MIRROR——而设 MIRROR 等于信任该主机，因为镜像会被标回官方名，只能靠核对 digest 兜底平台 owner
升级摩擦gorm 的 AutoMigrate 建不出生成列，部分迁移必须手工执行 SQL；已有安装要补「发起 MR」节点得跑 033，且该脚本只在模板「仍是出厂原样且未被编辑」时改写平台 owner
镜像与磁盘平台镜像内置 CodeBuddy / Codex / Claude / DeepSeek Harness，加 dsh 后下载体积增加约 180 MB；为无 Node 的自定义镜像准备的 toolchain 目录每构建一份约 200 MB，旧构建目录不会自动清理运维
对话可用性对话工作台目前仅中文；需求澄清、通知汇总、Bot 回复、运行评测四个入口只接受 CodeBuddy 模型（服务端对其它 CLI 的模型返回 400 而不是静默替换）使用者
组织成本十条 SOP 谁维护、角色提示词谁审、处方谁批准——这些不是技术问题，是需要指派的岗位职责团队负责人

一条 90 天的落地路径（可执行物）

第 1–2 周 · 只验证一件事

不配任何 Key，先跑内置「脚本 + 审批」体验 SOP，确认三件事成立：产物能生成、关口能拦住、批准后能继续。再配一个 Key 让 Main Bot 修一个小 bug。

退出条件：你能指着运行详情页说清「哪个节点花了多久、哪一步在等谁」。

第 3–6 周 · 把你自己的 DoD 变成脚本

拿团队现有的「完成定义」清单，逐条映射成 Script 节点（lint / 单测 / 构建 / SBOM）。先只建 4 个节点的 SOP：澄清 → 实现 → 脚本门禁 → 人工验收。

退出条件：同一条 SOP 连跑 3 次，第 2 次起不再需要人解释「该做什么」。

第 7–10 周 · 接真实仓库，跑够「打回」

绑一个低风险仓库，开 MR 门禁，按责任人配各自凭据。刻意制造一次评审不通过，观察 reject 是否真的退到指定上游而不是原地打转。

退出条件：至少一次真实打回、一次从中间节点重跑、一次从快照恢复。

第 11–13 周 · 只采纳一类处方

开启复盘，但只采纳「加/改门禁」类处方，暂不采纳改重试次数与追加提示词——后者需要更长时间才能判断是改善还是过拟合。

人力配比

0.5 个平台 owner（部署、升级、迁移、镜像）；每条在用 SOP 配 0.2 个评审人（审角色提示词与门禁变更）。合计约 1 人日常维护。

停止条件

如果第 6 周你还没能稳定跑通一条 4 节点 SOP，或者团队里没人愿意当门禁的签字人——问题不在工具，先回去修流程与责任人。

上线前必须做的四件事

① 不暴露公网，或至少 AGENTFLOW_ALLOW_SIGNUP=false 并只放行固定 IP；② 只连可信仓库（仓库内的 agent 配置与 hooks 会被执行）；③ 若曾在 0.4.0 之前跑过 SOP 角色，轮换当时用过的所有 CLI 密钥；④ 拉镜像后核对 RepoDigests 与 release 记录一致。

11反模式：三层各四条，附症状与修正

这些不是 LoopForge 独有的毛病，而是「引入 Agent 交付流水线」这件事本身的高频翻车点。它的设计已经防住了一部分，剩下的要靠使用者。

战略层

反模式症状修正
把 SOP 当收藏品三个月建了二十条模板，实际每月只跑两条；模板越建越复杂，没人敢改只留「本月跑过 ≥3 次」的 SOP，其余归档。SOP 的价值在复用次数，不在数量
用复盘分数当 KPI为了 90 分而砍掉必要的人工关口，或让 Agent 把检查项写得更容易通过分数只用于同一 SOP 的两个版本之间比较；对外汇报用「一次通过率 + 返工率 + 人工介入次数」三个原始量
指望工具替代评审文化上了平台，但没人愿意当签字人；关口永远秒过先把「谁有权放行」写进制度，再上工具。工具只能固化已有的责任，不能创造它
一上来就全自动把权限模式设成「完全自动」，第一次事故后全团队退回手工按「每次确认 → 智能代批 → 完全自动」三挡逐步放开，每一挡至少跑两周

工程层

反模式症状修正
门禁写成祈使句门禁内容写「请确认所有测试通过」——这仍然是一次模型调用，不是门禁凡是能用退出码判定的，一律用 command 门禁；不能判定的，转 manual 让人签字
同一个角色自审实现与评审用同一个角色定义、同一个模型、同一段上下文评审角色必须换上下文，最好换模型或换执行器——同模型自查的漏检率显著更高
能脚本的也上模型每个节点都是 Agent，包括「跑测试」「生成变更列表」先问「这一步有没有确定答案」。有，就用脚本；成本差三个数量级，可靠性更是
直接改线上模板运行还在跑，就编辑了它用的 SOP；重试时环境或流程变了依赖快照语义：改模板只影响新运行；重试与恢复必须走运行快照，不要「顺手修一下」

治理层

反模式症状修正
把 Docker socket 当沙箱边界平台暴露在公网，任何人注册后都能通过 SOP 在宿主机上跑代码内网部署 + 固定 IP 白名单；把平台主机当作「可被完全攻陷」的资产来隔离
接不可信仓库接了外部仓库，其 hooks 或 agent 配置在沙箱内被执行只接团队自控的仓库；对外部代码用只读检出、禁用 hooks
密钥经过日志为了排查问题打开全量日志，密钥随 docker exec 命令行落盘默认脱敏；排查期间也保持脱敏，需要复现时用占位符替换
无人认领的 Runner为扩容量接了多台执行机器，但凭据归属混乱，出事查不到是谁的 key 跑的凭据一律按责任人绑定，执行机器只提供算力不提供身份

12结论：值得抄的三件事，不该照搬的三件事

以下为分析者判断，不是社区共识。判断依据已在前面各章给出。

值得抄 ①　门禁必须去系统外取证

MR 门禁的精髓不是「查 PR」，而是「不信任 Agent 的自我汇报」。任何「Agent 声称做完了」的地方，都该问一句：这个「完了」能不能在系统外部找到一条记录？ 找不到，就还不是门禁。

值得抄 ②　运行快照 vs 模板的两分

模板会变，运行不能变。把「这次运行实际用的流程、环境、角色定义」冻进运行记录，是「三个月后还能解释那次交付」的唯一办法。这条对任何长链路 Agent 系统都成立。

值得抄 ③　让模型只打维度分

总分由服务端按权重重算、忽略模型自报的 score、缺维度直接报错——这三个小动作把「模型打分」从主观印象变成了可校验的仪表。做任何 LLM 评审/评分系统都可以直接照搬。

不该照搬 ①　十种执行器的适配长尾

十个 CLI 意味着十套凭据模型、十种输出格式、十类安装失败。除非你有专职人力吃这条长尾，两到三个执行器是更合理的起点。

不该照搬 ②　「自进化」的叙事强度

受限自我修改已经很有用，但把它讲成「系统自己会变聪明」会误导使用者，也会让团队把结构性问题当成参数问题——结果是不断加门禁，而不去修流程。

不该照搬 ③　公版/私版双轨

这个模式对「已有内部系统、要开源」的团队是最优解，但对从零起步的项目是纯负担：它要求你维护两套同步工具与一份私有审计清单，而收益只有在大规模存量代码时才显现。

最终判断

LoopForge 解决的是一个真实且昂贵的问题：当团队里有十个 Agent 会话同时在改代码，谁来保证每一次交付都经过同样的检查、留下同样的证据。它的答案——角色分离、异构门禁、运行快照、受限自进化——在工程上是站得住的，而且难得地诚实披露了自己的边界与事故。

但它不是「装上就提效」的工具。它把复杂度从「让模型写对代码」搬到了「维护一套交付基础设施」，因此只有当你的团队已经在为「Agent 交付质量不稳定」付出可观测的成本时，它才开始划算。在那之前，先把完成定义写成脚本，比先装平台更有价值。
